## What actually changed in `fetch.py`

- `SEARCH_SYSTEM` gained one sentence: *"If you cannot find a direct PDF link, a URL for the company's
  investor-relations or annual-report page is also acceptable."* The model still only ever replies with
  the same JSON shape; nothing else about level 4 changed.
- `_stub_pages`'s host→guessed-IR-path list is now the named `_IR_PATHS` constant behind a small
  `_ir_guesses(hosts)` helper (pure refactor, same five paths, same behaviour) so the new `_host_guesses`
  can reuse it for a *dead* direct link's own domain (Shell-style) instead of only a stub PDF's text.
- New: `_host_guesses`, `_ir_links`, `_crawl_ir_page`, `_ir_page_report` (fifth source itself).
- `fetch_report`'s two existing candidate loops (the plain-candidate loop and the model-candidate loop)
  each gained two bookkeeping lines: on a request exception, guess IR paths for the URL's own domain
  (`_host_guesses`); when a fetch succeeds but the payload isn't a PDF at all, remember the URL itself
  as a page to crawl. Both are pure list bookkeeping — no new network calls, so a fetch that succeeds
  anywhere in levels 1–4 is completely unaffected (same candidates tried, same latency). Only once *both*
  loops are exhausted does a new block call `_ir_page_report` on whatever got collected.

## Follow-up — BAD_URL's filename carve-out (same branch, after review)

Reviewer diagnosis (confirmed correct): Shell's model candidate in round 1 genuinely was the real
annual-report PDF (`.../sustainability/reporting-centre/.../shell-annual-report-2025.pdf`) — `BAD_URL`'s
`sustainab` term matched the *IR section name* in the path, not the file, and dropped it before any
fetch was attempted. Fix, exactly as specified: a hit in the URL's last path segment (the actual
filename) is still decisive and rejects outright; a hit *earlier* in the path is now ignored once the
filename itself names an annual report (`IS_AR`) and is itself clean. New `_filename_clear(label,
*patterns)` in `fetch.py`, applied at the two hard-reject sites that use `BAD_URL`/`NOT_REPORT` as an
outright filter: `_model_candidates` (both the raw and the %-decoded-twin check) and `_ir_links` (the
fifth source's own page-harvest gate). The three *scoring* uses of `BAD_URL` (`_nasdaq`'s filename-only
check, `_ddg`'s and `_harvest`'s score penalty) and `_validate`'s content-based `NOT_REPORT` check are
untouched — they either already operate on a bare filename (nothing to carve out) or are a soft ranking
signal shared by every company including the Swedish directory, and touching them was not the
reviewer's ask and carries real regression risk the "minimal fix" framing was explicit about avoiding.

**Tests** (`test_fetch.py`, 2 new groups, 15/15 total, all against the loopback server / direct calls,
zero model calls):

- **14.** End to end: a model candidate shaped exactly like Shell's real URL — `/sustainability/
  reporting-centre/nestle-annual-report-2025.pdf` — now survives `_model_candidates` and downloads
  successfully on the first try (no crawl needed), registered as `note: "model search (codex)"`.
- **15.** Counter-example, both as a `_model_candidates` call and a direct `_filename_clear` check:
  `https://ir.example.com/annual-report/interim-q3.pdf` — the filename `interim-q3.pdf` is itself bad,
  so it is still dropped even though an earlier segment reads "annual-report".

**Live Shell re-test (call 5/5)**: still **404**, for a *different* reason than round 1 — and this
result is itself proof the fix works. This time the model returned the exact same expired token URL
v074 originally recorded (`.../item0.stream/1773292272508/.../shell-annual-report-2025.pdf`, no
"sustainab" anywhere in it), so `BAD_URL` was never the obstacle for *this particular* candidate; it

`/investor-relations.html`, `/en/investors`, `/investors`) matches Shell's real site structure (its own
stale URL's own prefix, `/investors/results-and-reporting/annual-report/`, suggests the real path looks
nothing like the generic guess list), so nothing was found there either. Round 1's exact failure mode
(a good candidate dropped pre-fetch by `BAD_URL`) is confirmed fixed — the `_filename_clear` logic was
exercised live only in the sense that it *let this candidate through*, which round 1 would not have
done had it drawn this same URL; Shell's live 404 today is now down to two independent, harder problems
outside a "minimal fix" scope: the model's persistently stale idea of Shell's own URL, and the generic
IR-path guess list not matching Shell's actual site layout. Both are documented, neither is invented —
genuinely two different failure shapes were observed across the two live Shell attempts this lane made
(round 1: good link, bad filter; round 2: filter fixed, but a stale link and a generic guess list that
doesn't fit this particular issuer), which is itself informative about how much of "fix Shell" is left.
