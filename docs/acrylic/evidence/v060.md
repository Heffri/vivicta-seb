## The three mechanism changes

**1. `header_synonyms`** (schema, per bucket field) — read only by `_bucket_synonym_hits`
(`extract.py`'s own `sf.get("synonyms", []) + sf.get("header_synonyms", [])`) and therefore only by
`_bucket_header`; `_label_known` (row-label matching, used everywhere else in the file) reads `synonyms`
alone and was not touched, so this is structurally incapable of loosening row matching — proven by
`label_regression.py` below, not just asserted. Every entry is a wording that actually appears (verified
by grepping `_page_rows`-processed text, not just the raw PDF text — pymupdf sometimes prints a header
word-wrapped, e.g. Boozt's "twelve\nmonths", and `_page_rows` rejoins that before this lane's code ever
sees it) somewhere in seed1-5, per-field:

- `due_within_1_year`: `within 12 months` (Ependion p.155, Bergman & Beving/Catella/Cloetta/… — 32 hits
  across seed1-5), `< 1 month` / `1-3 months` (Ework p.70), `3 months` / `three to twelve months` (Boozt
  p.121, the two column-header fragments `_page_rows` did not rejoin into `within 3 months`/`3-12
  months`'s existing phrasing), `-30 dgr` / `31-90 dgr` / `91-360 dgr` (XANO p.83-84 — the work order's
  own example text says "91–365 dgr"; the report actually prints 91-**360**, corrected here), `inom 12
  månader` (Alligo/Nelly/MedCap/Fasadgruppen), `summa inom 1 år` / `total within 1 year` (named by the
  work order's own step 3 for XANO's subtotal column — kept per that instruction even though, as Finding
  1 below details, it does not fire end-to-end for XANO specifically; general mechanism, not dead code
  for every future company).
- `due_1_to_5_years`: `3-5 years` (10 hits: Better Collective/Cloetta/Acast/Arjo/…). Everything else the
  work order listed for this bucket (`between 1 and 2 years`, `2-5 years`, `mellan 1 och 3 år`, …) was
  already in the schema's `synonyms` before this lane — no duplicate added, per the work order's own "no
  need to repeat what's already in synonyms" instruction, and because a duplicate would double-count a
  column (see Finding 3).
- `due_after_5_years`: `five to nie years` (Boozt p.121, its own PDF's typo for "nine" — kept verbatim,
  it is what the report prints), `after nine years` (Boozt p.121). The work order's `later than 5 years`
  etc. were already in `synonyms`.

Four of the work order's own example phrases were dropped after failing the attestation grep against
every seed1-5 page (`0-6 months`, `0-3 mån`, `91-365 dgr`, `five to nine years` — none appear anywhere in
seed1-5, `page_rows`-joined or not): kept out per "only wordings that really appear," not silently added
on the work order's say-so alone.

**2. Debt-row fallback** (`_bucket_total_row`): when no row's label is a `total_debt` synonym or a bare
Total/Totalt/Summa, falls back to rows whose label is a debt synonym (`_DEBT_ROW_SYNONYMS`, a private
extract.py word list, never used for direct field-row matching) *and* that read a real bucket header
above them with a column count matching their own printed amounts. The fallback candidates are
*appended* to, not a substitute for, the existing bare-Total hits — a page can have a bare "Total" row
that turns out to be the wrong scope (Ework's own all-liabilities "Total" row) and the real debt row
further down; `_fill_bucket_columns`'s own loop already tries each candidate in order and moves on when
one fails, so appending costs nothing and lets that existing fallthrough reach the fallback candidates.
Multiple survivors narrow by `known_total` (the model's own already-sourced `total_debt`, when present)
— the row that itself prints that figure wins; still ambiguous after that is a warning, not a guess
(`_bucket_total_row` returns nothing further, per the work order's own "don't guess" instruction).

Final word list: `borrowing`, `borrowings`, `bank loans`, `bank loan`, `interest-bearing liabilities`,
`interest bearing liabilities`, `short-term interest-bearing liabilities`, `lease liabilities`, `lease
liability`, `upplåning`, `räntebärande skulder`. Bare `loan`/`loans` — in the work order's own example
list — is deliberately **not** in it: Finding 2 below is why.

**3. Within-1y subtotal column** (`_bucket_header`): a header hit whose matched synonym is
`summa inom 1 år` or `total within 1 year` (`_SUBTOTAL_PHRASES`) is tagged distinctly during collection;
once the full per-window hit list is built, every earlier hit for the *same* bucket key (to its left,
i.e. already counted) is reclassified to an inert `_excluded` marker and the subtotal position itself
becomes the real key — so a table with both the finer day/month columns and their own printed subtotal
sums the subtotal only, never double-counts. Implemented per the work order's own step 3 instruction;
Finding 1 explains why it doesn't reach XANO's own table despite that.

## Findings

**1. Ework and XANO's headers are matrix-transposed across two physical lines, not simply word-wrapped
— `_bucket_header`'s row-by-row hit collection cannot recover column order from that shape.** Both
tables' column headers print as two *lines* where line 1 holds every column's first fragment and line 2
holds every column's second fragment (`pdf` reading order is row-major over what is visually a
column-major two-line header) — Ework p.70: `"Total undis- Carrying"` then `"kSEK Due < 1 month 1-3
months 3-12 months 1-5 years > 5 years counted value amount"`; XANO p.84: `"...Summa Mellan 1 Mellan 3
Efter 5 år Totalt"` then `"inom 1 år och 3 år och 5 år"`. `_page_rows` either merges these two lines into
one row (Ework, since the second line happens to start with a lowercase word) or keeps them as two
separate rows (XANO, since the second line starts with a digit-adjacent capital) — either way, the text
order of the merged/concatenated hits does not match the true left-to-right column order, and no
per-row or per-window reordering *within this lane's six functions* can recover it without knowing each
word's original x-position, which `_page_rows`' plain-text rows do not carry. Confirmed empirically, not
just diagnosed: I extracted PyMuPDF word-level bounding boxes for Ework p.70 (`ework_p70_words2.txt`, not
committed — scratch) and the true column order (verified by summing each of the three data rows and
matching every column against the printed "Total" row, all 8 positions reconciling to within Swedish
rounding) is `Due, <1 month, 1-3 months, 3-12 months, 1-5 years, >5 years, Total undiscounted value,
Carrying amount` — 8 real columns, one more than the 7 phrase-groups a naive header-word count sees,
because "Due" prints as its own column (a genuinely separate, sometimes-nonzero bucket: the "Accounts
payable" row's own "Due" figure is 91,284) that the work order's own reading list did not anticipate as
a live column. Given the header text itself cannot be un-transposed within this lane's scope, and the
row's real column count (8) forces every hit to land somewhere, the mechanism's own safety valve (column
count must equal the row's own amount count, v036) correctly declines every column reading it tries for
both companies rather than guess — confirmed via direct `_bucket_header`/`_bucket_total_row` calls
(scratch, not committed): Ework's fallback finds the right row (`"Short-term interest-bearing
liabilities*"`) but its column reading is rejected by the `over` check (`due_1_to_5_years`/
`due_after_5_years` both computed as 156,410, exceeding the row's own 153,761-based total — the safety
valve doing exactly its documented job); XANO's row is found via the *existing*, non-fallback mechanism
(its label, `"Summa räntebärande skulder"`, is already a `total_debt` synonym) but its header reads 7
columns against the row's own 8 amounts and is dropped by the length-mismatch guard before `_bucket_assign`
is ever called. **This also means the work order's own target for Ework (154,732 = 0 + 153,761 + 971,
excluding the 1,677 "3-12 months" figure) does not reconcile with the true 8-column structure**: with
"Due" as a real column, the schema's own stated convention ("if the report splits the first year
further... sum those columns") would sum `Due + <1month + 1-3months + 3-12months = 0 + 153,761 + 971 +
1,677 = 156,409` — i.e. *including* the 1,677 the work order's target excludes, leaving `due_1_to_5_years`
at 0 (the report's own `1-5 years` column is nil for this row) rather than 1,677. `eval/labels.csv`'s
hand-verified figure (154,732/1,677 split) appears to have been transcribed by reading the flattened page
text without checking the PDF's own column geometry, missing the extra "Due" column — flagging this for
whoever owns `eval/labels.csv` next, not correcting it myself (out of this lane's territory); either
reading reconciles to the same total (156,409 or 156,410 ≈ total_debt either way) so the dispute is only
about which two buckets 971/1,677 belong to, not about total_debt itself.

**2. Bare `loan`/`loans` in the debt-row fallback list matched the wrong side of a bank's balance sheet
— caught by the replay gate, fixed before delivery, not a lingering risk.** First draft included bare
`loan`/`loans` per the work order's own example list. `replay_check.py` against `seed4-kb` caught it
immediately: Norion Bank's `total_debt` (already correctly 2,896, sourced from its own "Debt securities
issue" row) flipped to 8,328 because `"Loans to credit institutions"` and `"Loans to the public"` — the
bank's own *asset*-side rows (money it lent out, not borrowed) — matched the bare `loan(s)` synonym and
out-competed the real row once `known_total` narrowing didn't apply (nothing on the page prints 2,896
inside a different row, so narrowing left a single, wrong survivor rather than an ambiguity warning).
Fixed by dropping bare `loan`/`loans` from the list (`bank loans`/`bank loan` stays — a company's own
bank borrowings, not the reverse direction, and did not reproduce this failure mode anywhere in
seed1-5/data/kb). Re-ran the full replay after the fix: Norion Bank returns to `same`. Named here because
it is exactly the kind of thing a company-count-1 manual read would not have caught — the corpus-wide
replay gate is what did.

**3. Boozt's row and header are now read correctly — a separate, pre-existing `_row_amounts` limit
(outside this lane's six-function territory) is what still blocks the fill.** Direct calls (in the new
test case) confirm `_bucket_header` now reads Boozt's row 15 (`"Lease liabilities 441 26 78 273 63 -"`)
as a clean 6-column header (`total, due_within_1_year, due_within_1_year, due_1_to_5_years,
due_after_5_years, due_after_5_years`) — the debt-row fallback correctly identifies "Lease liabilities"
as the debt row (the report's *entire* interest-bearing debt is leases; no other candidate on the page
prints the known total 441 once `Liabilities to credit institutions`'s own 0/380 rows are excluded) and
correctly reads the word-wrapped "Maturity within" / "3 months" header split. But `_row_amounts(row, 6,
nil=None)` returns `[441, 26, 78273, 63, None]` — five values, not six: the same ambiguity the file's own
comments already document for `"Total sales 6, 10 155 113 161 921"` (a Swedish thousands-grouping regex
that cannot distinguish two adjacent small table columns, "78" then "273", from one space-grouped
78,273) fires here too, merging `due_within_1_year`'s own two sub-columns into one token. Column count
then never matches the header's, and the safety valve declines rather than guess — exactly the same
mechanism that (by the same coincidence, since Boozt's *other* rows share the same 2-then-3-digit
adjacency) also protects against the page's own all-liabilities "Total" rows ever corrupting the already-
correct `due_1_to_5_years`/`due_after_5_years`/`total_debt`. `_row_amounts` is not one of this lane's six
functions (`backend/pipeline/extract.py` territory line explicitly scopes to `_bucket_synonym_hits`/
`_bucket_year_hits`/`_bucket_header`/`_bucket_total_row`/`_bucket_assign`/`_fill_bucket_columns` only) —
named here for whoever picks it up next, not attempted.
