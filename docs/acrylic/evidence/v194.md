## 1. The contract, exactly as specified

`backend/pipeline/jobs.py` (new): `JOBS[job_id] = {stage, started, updated, done, error, events}`,
`step(job_id, stage, text, **data)` a no-op when `job_id` is falsy, lazy TTL sweep (1 h) on every
`step()`/`get()` call — no background thread, matching the rest of the backend's single-process,
in-memory-table style (`reports`/`extractions` in app.py). `GET /api/jobs/{job_id}` (app.py) returns
the table entry or 404. `job_id` is now an optional field on `DiscoverBody` (inherited by
`FetchBody`), threaded straight through to `fetch.discover()`/`fetch.fetch_report()`. Stage names are
exactly the fixed vocabulary: `directory / mfn / nasdaq / ddg / model_search / ir_page / download /
verify / done / failed`. `pipeline/test_jobs.py` (new, 1 file, `demo()`-style self-check like
`test_llm.py`/`test_fetch.py`): the no-op-without-job_id case, event ordering, `data` kwargs riding on
the event only, `done`/`error` semantics for `done` vs `failed`, and the TTL sweep firing lazily off
an unrelated `step()`/`get()` call.

## 2. Where every stage actually gets stepped (fetch.py — only step() calls added, logic unchanged)

- **`directory`** — `discover()`'s and `fetch_report()`'s own cache/saved-report checks.
- **`mfn` / `nasdaq` / `ddg`** — `_candidates()` (the traditional-fallback generator): its one
  expression (`dict.fromkeys(_mfn(...) + _nasdaq(...))[:MAX_TRIES]`, then the crawl+DDG half minus
  the feeds) is unchanged, just split into named locals with a step() wrapped around each half so the
  computed URLs and their order are provably identical (verified in `demo_candidates_events()`,
  §4 below — this file's main `demo()` mocks `_candidates` out entirely, so it never exercised the
  real body before).
- **`model_search`** — wraps `_model_candidates()`/`_model_discover()` in `fetch_report()`/`discover()`:
  one step before the call ("asking the connected model…"), one after with the candidate count and
  the candidates/urls themselves as `data` (this is the "候选 URL" half of the ask — already-parsed
  data fetch.py had anyway, no new parsing needed).
- **`ir_page`** — wraps `_ir_page_candidates()` (the second, targeted model ask) and `_ir_page_report()`
  (the crawl itself, now also `job_id`-threaded: one event per seed page read).
- **`download`** — `_get()` grew optional `job_id`/`label` kwargs: with a `job_id`, it streams the
  read in 64 KB chunks and steps progress every 8 chunks (~512 KB) plus one final event with the true
  total read; without one (every pre-v194 call site, and every internal helper's own `_get()` calls
  that don't care about progress — `_mfn`/`_nasdaq`/`_crawl`/`_harvest`/page-scraping inside
  `_crawl_ir_page`) it still does one unbuffered `r.read()`, byte for byte as before. Only the
  candidate-PDF download sites in `fetch_report()`'s own three loops and inside `_ir_page_report()`
  pass `job_id` through — HTML page-scraping during IR crawling stays silent (small, fast, not what
  a byte-progress bar is for).
- **`verify`** — right after every `_validate()` call at those same four sites: `"{url} -> ok (N
  pages)"` or the rejection reason, the same wording `print(f"{url} -> ...")` already used everywhere
  in this file.
- **`done` / `failed`** — every `return` in `fetch_report()` (there are seven) now steps `done` first;
  the single `raise LookupError` at the end steps `failed` with the same detail the `/fetch` route's
  404 shows. `discover()` never raises (zero candidates is an existing, different UX, not a failure)
  so it only ever reaches `done`.

`llm.py`: `web_lookup()`/`_codex_chat()` grew an optional `job_id`, threaded only as far as
`_codex_search_events()` — parses codex's `--json` event-stream (already captured on `p.stdout`,
previously unused beyond an error tail) for `item.completed` events of `type: "web_search"`, and
steps their `action.queries` as one `model_search` event. Consecutive identical query lists (see the
real probe below) fold into one event. `claude`'s `--output-format json` is a single object, not an
event stream — `job_id` is a no-op on that path; `fetch.py`'s own step() calls around the call are
what a claude-backed search still shows.

## 3. What the real codex --json event stream actually looks like (probed before writing the parser)

`codex -a never --search exec ... --json -o reply.txt -` (same flags `_codex_chat` already builds),
run directly once against a real discover-style prompt (`gpt-5.6-terra`, outside the app, before
touching `llm.py`): 9 JSON-Lines events — `thread.started`, `turn.started`, an `agent_message`
narrating what it's about to do, **two** `item.completed` events of `type: "web_search"` sharing the
identical `action.queries` list, the final `agent_message` (the JSON reply itself — never shown, it's
the payload, not narration), `turn.completed`. The duplicate-queries shape is real, not a bug in this
lane's reading of it — `_codex_search_events` folds consecutive identical lists into one event so the
trace doesn't show the same search twice (verified in `pipeline/test_llm.py`'s new assertions,
replayed through a fake codex CLI extended to emit the same event shape).

## 4. Frontend: state lifted the same way v171 lifted batch state

`frontend/src/hooks/useReportSearch.ts` (new): `query`/`year`/`discovery`/`discovering`/`trace` now
live here, called once in `App.tsx` — not inside `UploadView` — for the same reason v171 lifted
`useBatch`: `UploadView` unmounts when the user leaves Extract, and `setDiscovery` on an unmounted
component is a silent no-op, so a search that outlived a tab switch used to look "interrupted" even
though the network call itself was never aborted (nothing here ever used `AbortController`). The hook
exposes `trackJob(kind, label, run)`: mints a `job_id`, resets the trace, polls `GET /api/jobs/{id}`
every 1.5 s, and — critically for "失败时轨迹保留" — leaves the final trace in place on both success
and failure (a rejected `run()` promise force-sets `done: true, error: e.message` even if the job
table itself never saw a `"failed"` step, e.g. a raw network error before the backend could run at
all). `UploadView.tsx`'s `useCandidate` (the AI-search-confirmed-candidate path) wraps its
`fetchReport` call in `trackJob('fetch', ...)`, so the *same* panel follows straight through from
"resolving the company" into "fetching its report" — discover and fetch share one continuous trail,
just a new `job_id` and label. Plain directory picks (`picked.map(...)`) stay untracked, unchanged —
that path is typically an instant cache hit and isn't the "AI is searching" scenario this P0 is about;
the backend capability (`job_id` on `/fetch`) exists regardless, so wiring a second UI in there later
is a prop, not a redesign.

`frontend/src/components/upload/SearchTrace.tsx` (new): the panel itself — icon + label + stopwatch +
current stage, the last 8 events, a byte-progress bar specifically when the *latest* event is a
`download` stage with a numeric `bytes`/`total` (disappears once the stage moves on), and on failure
an `ErrorBlock` + Retry (discover failures only — a failed fetch already has its own "Retry this one"
in `BatchProgress`, unmodified and untouched by this lane; two Retry buttons for the same failure
would be confusing, so this one isn't offered there).

`CompanySearch.tsx` gained one prop (`trace`) and swapped its old bare `discovering && <LoadingLine>`
line for `{trace && <SearchTracePanel .../>}` — everything else (candidate cards, "None of these",
the hint flow) is untouched. `UploadView.tsx`'s own diff is almost entirely deletions: its local
`query`/`year`/`discovery`/`discovering`/`discover` are gone, replaced by one destructure off the new
`reportSearch` prop threaded down from `App.tsx`, mirroring exactly how `batch` already arrives.

## 5. A pre-existing bug this lane found and fixed (not scope creep — it broke my own new test)

`pipeline/test_fetch.py`'s `demo()` saved `(original, replacement)` **tuples** for `fetch._candidates`
and `fetch.llm.web_lookup`, then its own restore loop did `setattr(fetch, attr, original)` where
`original` was the *whole tuple*, not just the first element — silently leaving both attributes
corrupted (set to a 2-tuple, not a callable) once `demo()` returned. Harmless as long as nothing in
the same process called either attribute again after `demo()` — which held until this lane's own
`demo_candidates_events()` (§2's `_candidates` unit test) did exactly that and hit
`TypeError: 'tuple' object is not callable`. Fixed by storing just the original callable (the
replacement was already being reassigned on the very next line either way — the tuple's second
element was dead weight). Reproduced red (the exact `TypeError` above) before the fix, green after;
recorded here per "grep 到那行还在 ≠ 缺陷还在" — this was demonstrated, not theorized.
