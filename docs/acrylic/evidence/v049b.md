# v049b —— `_stack_cells` 的堆叠单元格链接跨 PyMuPDF 版本一致(1.27.2.3 与 1.28.2)

Lane `v049b`,基线 `origin/acrylic`(派工时最新,交付前已 fetch+merge 一次,20 个新提交都不碰本单文件,无冲突)。全程离线:没起服务、没调模型;`test_confidence`/`test_kb` 里的 LLM 调用全走 `x.call_llm = lambda...`/env 桩,零真实推理。35 份 PDF 从共享目录复制进 `data/reports/`(gitignored)。两套环境:`venv127`(pymupdf==1.27.2.3)、`venv128`(pymupdf==1.28.2),其余依赖照 `backend/requirements.txt`。

## 起因(v049 acceptance note)

v049 验收时发现:同一份 PDF、同一份 parse.py,Ependion p.155 的表头在 PyMuPDF 1.27.2.3 下被 `_stack_cells` 链接成 `Between 1 and 2 years`,在 1.28.2 下仍是撕裂/交错的 `Between Between` / `Within 12 1 and 2 and` / `SEK 000 months 2 years 3 years Total`。主管临时钉了 `pymupdf==1.27.2.3`。

## 真因(不是 `_stack_cells` 的链接判定本身算错)

`_stack_cells` 的链接测试(x 重叠、竖直间距、链深)在两版下都正确——用 `_merge_baselines` 单独调用(绕开 `page_text` 的路由)验证:1.28 下这块表头仍然逐词顺序正确,只是碎得更细,**不交错**:
```
1.27 直接输出:'SEK 000 Within 12 months' / 'Between 1 and 2 years' / 'Between 2 and 3 years Total'
1.28 直接输出:'SEK 000' / 'Within 12' / 'months' / 'Between' / '1 and 2 years' / 'Between' / '2 and 3 years Total'
```
真正的交错来自 `page_text` 的路由。1.28 下 `get_text("dict")` 把这块表头从 1.27 的 3 个 block(`dict-127.txt` 的 BLOCK 41/42/43)拆成 5 个更小的 block(`dict-128.txt` 的 BLOCK 46-52,同样的字形 bbox)——这本身不致命(见上)。**致命的是页面别处同一原因导致的另一处撕裂**:`Recognized i other comprehensive income` / `-9,751 -2,991` 这一行,1.27 下两半在同一个 block(bbox 跨 x515-756),1.28 下拆成两个 block(x515-628 与 x674-756)。`_merge_baselines` 逐 block 处理、`rows` 逐 block 重置,这一撕裂让 1.28 下 `_split_rows(merged)=1`(1.27 为 0)。`page_text` 见到残留撕裂就试 `_best_words`(词级重建),发现它把这一行撕裂降到 0(词级重建对 side-by-side 内容更宽容),**改用整页的词级重建**——而词级重建(`_lines_from_words`/`_columns_from_words`)完全没有 `_stack_cells` 这类竖直链接机制,只按纯 y 坐标横向拼接同一基线上的所有内容,于是把该表头三个单元格的片段拼花成交错文本。

即:**版本差异的落点是 `get_text("dict")` 的 block 分组,链条是"block 更碎 → 别处一个不相关的撕裂 → 整页路由换到无链接能力的词级路径 → 表头被拼花"**,不是 `_stack_cells` 内部判定错。诊断用 `page_text` 路由探针(绕开/命中 `_merge_baselines` vs `_best_words`)证实,不是靠读代码猜。

## 改法:`_stack_cells` 的触发条件从"同一个 pymupdf block"改成几何分组

`backend/pipeline/parse.py`,`_stack_cells` 本身零改动(内部链接算法不变);新增 `_group_blocks`/`_blocks_link`/`_tabular`,`_merge_baselines` 按前者的分组喂 `_stack_cells`:

1. **`_tabular(lines, width, page_w)`**:从 `_stack_cells` 里抽出来的表形判定(某条基线上有 ≥2 个 x 不相交的行,或整体是窄列)——保持它原来的语义,只是抽成共享函数,供下面两处复用。
2. **`_group_blocks`**:并查集,只把 ≤`_CHAIN_MAX`(3)行的"短" block 纳入候选(段落 block 行数远超此值,永远独立,散文的 block 级隔离与 v049 之前完全一样)。两个短 block 之间存在下列任一关系时提议合并:
   - `_blocks_link` 测试(a):其中一行与另一行满足 `_stack_cells` 自己的竖直链接判据(x 重叠 ≥ 窄者一半、间距在 `_CHAIN_GAP` 容差内、**且两行行高之比 ≤ `_LINE_RATIO`(2.0)**);
   - `_blocks_link` 测试(b):一行是纯标签、另一行是纯数字(`_PURE_VALUE` 二选一为真)、共享基线(±2.5pt)、且 x 间距 ≤ `_ROW_GAP`(3.0)× 窄者宽度。
   - **但提议合并不等于真合并**:只有当两组已池化的行**合并后**仍能通过 `_tabular`(即合并结果本身还像一张表或一个单元格),这次 union 才提交;否则两组保持独立,恰好等价于 `_group_blocks` 不存在时的行为。这一步在并查集的**每一次候选合并时**增量检查(而不是只在最后检查一次整个连通分量),因为一个还不够"表形"的两块可能在第三块加入后才达标(Ependion 的两片段列组正是先各自吃进第三个片段才通过表形门)。
3. `_merge_baselines` 按 `_group_blocks` 的分组(池化后的 lines、组合 bbox 宽度)喂 `_stack_cells`,其余逻辑(链后按基线分行、行内 x 排序、组间保持"先出现的 block 靠前"的阅读序)不变。

### 门的取值(实测,不是拍的,方法同 v049)

- `_ROW_GAP=3.0`:Ependion 三个真实"该合并"间距/宽度比 1.76–2.30x;唯一撞见的"不该合并"案例(同页 TOC 词条 "Contents" 与正文标题 "Loan, interest and maturity structure" 恰好同基线)比值 4.93x——两端都有余量,取中间偏保守的 3.0。
- 去掉 `_stack_cells` 原链接测试里"新片段宽度 ≤ 链宽 1.5 倍"这一条(未搬进 `_blocks_link`):那是对**累积链宽**的单向判定,两个尚未链接的 block 之间做**成对**判定时,对称化后恒真、按原方向搬又会踩线误杀 "Between"(32pt)~"1 and"(20.9pt)这一真实链接对(32 > 1.5×20.9=31.35)——而这条正是 v049 已验收的 "Between 1 and 2 years" 短语本身依赖的链接。`_CHAIN_MAX` 已把可参与的行数卡在 3 行内,宽度失控的风险本来就小。

## 校准过程中额外揪出的两个假阳性(先红后绿,和 v049 的方法论一致)

第一版实现(只有测试 a/b,没有 `_LINE_RATIO`、没有增量 `_tabular` 门)在 8 定向页上修好了 Ependion,但对 35 份 PDF 全量跑 `--dump-all` 逐页 diff 后发现两类新的误伤,都是"block 更碎"这同一版本差异触发的、`_stack_cells` 本身从未遇到过的场景(因为它以前只在单个 block 内运行):

1. **大号装饰数字把间距容差撑大(Acast p.5)**:一个 53pt 高的信息图数字 "460" 后面紧跟一段正文首行 "co-workers and consultants."——`_blocks_link` 测试(a)照搬了 `_stack_cells` 的 `gap <= _CHAIN_GAP * span` 公式,`span` 取两者较高的一个,53pt 的高度把允许的竖直间距/重叠容差同比例撑大,导致这个大号数字"够得着"下方本来毫不相关的段落。以前这两者永远在不同 block、永远不会被同一次 `_stack_cells` 调用看到,block 边界替它们挡住了这个巧合;跨 block 池化把这层意外保护拆掉了。**修法**:`_blocks_link` 新增 `_LINE_RATIO=2.0` 门,两行行高之比超过此值直接跳过——真实堆叠片段的行高几乎相等(Ependion 全部案例比值 1.0),这个门不影响任何已验证案例。
2. **连续简历字段被误合并(Academedia p.33)**:一页董事简历,"教育背景"、"现任其他职务"、"曾任职务"、"持股情况" 四个字段各自是一个两行 block,行首都在同一 x、行距相近——`_blocks_link` 测试(a)把这四个无关字段串成一条链(和 Ependion 的表头列使用同一套竖直相邻判据,几何上确实相似)。合并后单个字段自己原本能过的窄列判定(单独 131.8pt ≤ 页宽 15%=143.9pt)被合并后的整体宽度(176pt)冲垮,导致 `_stack_cells` 的门反而**整体失效**、四段全部退化成散开的单行——比不合并更差。**修法**:`_group_blocks` 的每一步候选合并都增量核验 `_tabular`(见上"改法"第 2 点),核验后这四个字段各自单独成组,输出恢复到与 v049 基线一致。
3. **诊断方法**:两次都是靠 `--dump-all` 全语料两版 diff 抽样核对"改动前后差异最大的若干页",而不是逐页通读——840 处候选合并里这两类是**唯一**观察到的负面案例,门加上后复跑同样的抽样未见新的负面案例(下面全量指标不退步是更强的证据)。
