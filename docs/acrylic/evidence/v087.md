## 6. Findings

### 6-1. The generic-title window-hittest check can grab a *different* app instance's window on this shared machine — fixed to scope by process tree

The drag-hittest PowerShell snippet (inherited from v071/v077's driver unchanged) matches
`Get-Process` by `MainWindowTitle -like '*Annual Report Parser*'` system-wide. On the very first
run this round, that matched the **still-running 0.3.2 portable** (PID 25816, §6-3 of v077,
still alive here — see §6-3 below), which happened to be minimized: `GetWindowRect` returned the
Windows minimized-window sentinel (`RECT:-32000,-32000,-31840,-31972`), and the check correctly
failed loudly rather than silently passing on the wrong window. Root cause confirmed (not
assumed): re-ran with the process-tree scoped to this run's own spawned PID only
(`Get-CimInstance Win32_Process`, BFS over `ParentProcessId` from the spawned PID, intersected with
`Get-Process` for `MainWindowHandle -ne 0`) — the very next run passed cleanly against the correct
window (`RECT:240,126,1680,1026`, `TITLEHIT:2`, `CONTENTHIT:1`). This is a test-harness bug, not an
exe defect; v071/v077 never hit it only because no other same-titled window happened to be open
at their own check time. Fix carried in this lane's copy of the driver only (not committed —
`uaw-lanes/vivicta-seb-70/driver.cjs` is lane scratch, per common.md, same as every prior driver).

### 6-2. A driver re-run reusing the same `--user-data-dir` fired real Codex calls — caught, root-caused, remediated before any evidence was recorded

Fixing 6-1 required re-running the driver. The first re-run reused the **same** isolated
`electron-userdata` profile from the aborted first attempt, which had already gone through step
(b) (Settings → Codex → Save) before the hittest failure was even noticed, so `config.json` inside
that profile carried a live `provider: codex`. On the re-run, steps (e)/(i)/(l) — meant to run in
**pristine, no-provider** fixture mode — instead launched with Codex already configured
(`_llm_configured()` true), so `POST /api/reports/{id}/extract` took `app.py`'s real-extraction
branch instead of the fixture branch: backend.log recorded
`[extract] up-dde3e00e408c income_statement: candidate pages [64, 65]` and a `200 OK`, with
`two-pass: 1` active — i.e. at least one real `codex exec` call (`llm.py`'s `_codex_chat`,
page-select), very likely two (page-select + extraction), against the synthetic fixture PDF. This
directly breaches the WO's own 不做 ("不真调模型") and common.md's "零真实推理". **Caught before
any of that run's screenshots or numbers were used**: reported to the supervisor immediately on
discovery (before any further driver runs), root-caused via `app.py`'s own `run_extract` gate
(`_llm_configured()` branch) and `llm.py`'s `_codex_chat` (real `subprocess.run` to the installed
codex CLI). Fix: the driver now `fs.rmSync(USERDATA, {recursive:true,force:true})` **before every
launch**, so a profile can never carry a saved provider across runs. Re-ran clean immediately
after (§6-1's own passing run *is* this clean run — the fixes landed together, one full pass): its
backend.log has zero `candidate pages` lines and zero codex/claude subprocess occurrences (grepped,
not eyeballed), which is what §5's table and the header above report. No screenshot, number, or
claim anywhere in this file comes from the contaminated run. Lane scratch only
(`uaw-lanes/vivicta-seb-70/`), not the repo — no cost to the shipped artifact, but a real cost
against the shared Codex budget the supervisor tracks; flagged in the delivery message too.
