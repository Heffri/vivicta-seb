## Rules scored (labels never enter a rule — scoring only)

- **R0** take run2 (status quo: the second `/extract` write wins).
- **R1** take run1.
- **R2** union, per field: the non-null side wins; both non-null and disagree → the run whose
  `maturity_sums_to_total` passes; both same check state → higher conf; still tied → run1
  (tiebreak counted — see sensitivity below).
- **R3** consensus: keep a field only if run1 and run2 are both non-null and equal, else null.
- **R4** conditional two-run: if run1's check passes **and all four schema fields are non-null**
  → 1 call, take run1; else run run2 and merge per R2. (The work order's "标签有的字段都非空"
  cannot use labels, so it is read as "all four schema-labeled fields" — the strictest
  label-free completeness test available.)
- **R5** (this lane) **corroborated union**: a non-null value needs ≥2 agreeing non-null votes
  among {stored, run1, run2} — the *stored* value is the pipeline's own earlier answer for the
  same document (the snapshots above), not the label, not the curated `kb` state; absent for a
  first-ever extraction → degenerates to R3 consensus there. Trigger (exact, not heuristic):
  skip run 2 when run1 is value-identical to stored on all four fields — under the majority
  merge, run 2 is then provably a no-op (every field already has 2 votes or two nulls), so the
  skipped calls buy nothing. Fresh runs have no stored → always 2 calls.

### Trigger and cost

- R4's trigger (check pass + all four non-null) fires on **9/72 (12.5%)** — all-four-non-null
  is rare because most reports print no >5y bucket; the check itself passes on only 9/72
  run1s. R4 saves 9 of 144 calls — conditional two-run under this trigger is nearly
  pointless cost-wise.
- R5's trigger (run1 == stored) fires on **34/72 (47%)** → 110 calls instead of 144. On the
  104-stem universe (the rerun rate extrapolated): always-two = 208 `/extract` calls, R4 ≈
  195, **R5 ≈ 159** (each `/extract` = page-select + main = 2 model invocations, so ≈ 416 →
  ≈ 318). First-ever extractions (no stored) always pay 2 calls under R5.

## Conclusion

**Recommend R5 — corroborated union with the stored answer as the third vote — for any rerun
or republish flow**, where a stored answer exists by definition: it is the only rule that
gains companies (+2) while *reducing* wrong published values (−4, zero new ones) and it cuts
~24% of the calls via an exact (not heuristic) skip trigger. Expected effect on a rerun of
this shape: **+2 to +3 companies ✓, +4 to +5 fields ✓, wrong non-null values −4 to −8 vs the
status quo, no new wrong values**. Risks: (1) the stored vote is only as good as the stored
answer — a wrong stored value plus one agreeing run keeps the wrong value (byggmax, tangen,
bergman_beving total here); the subset property is empirical on n=72, not a theorem; (2) a
truly-new single-run find with a null stored answer is *not* imported (academedia here) — the
price of not importing kabe/cellavision-class noise is losing academedia-class lucky wobbles;
(3) the trigger's no-op proof holds only under the majority merge — pairing R5's trigger with
an R2-style union merge would be wrong. For fresh runs (no stored), R2-union is the defensible
choice: +2..3 companies, 0 company regressions in this sample, at +4..5 wrong values in
already-failing stems; R3-consensus is the alternative if wrong-value aversion dominates
(−3 companies, +10 misses, wrong non-null 13 → 7).

Implementation notes (nothing changed this round):
- The merge is a pure function of two (or three) per-field value/conf/check/evidence sets —
  it belongs beside `_select_pages` in `backend/pipeline/extract.py`, which already owns the
  EXTRACT_TWO_PASS flag and the widen fallback; `extract()` would loop its main window call
  twice (or skip the second per the trigger) and merge, behind e.g. `EXTRACT_MERGE_RUNS=off|
  union|consensus|majority`. Doing it in `app.py`'s `/extract` instead is possible but that
  handler currently *returns the stored file when one exists* (the drivers had to work around
  that to rerun at all), and the driver layer (`random_check.py`/rerun drivers) only sees
  post-extraction JSONs — extract-level is the one place with both runs and the stored value
  in hand.
- **Per-run records are not persisted today** — only the last extraction is saved, and raw
  model answers are stripped by post-processing (`scripts/replay_check.py` docstring spells
  this out). A rule like R5 needs the stored answer, which exists, but future merge work
  needs per-run values: write `extractions/<section>.run1.json`/`.run2.json` (raw-field shape)
  next to the merged section JSON, and carry the merge decision (`how` per field) in a
  top-level block so offline audits stop depending on lane-dir snapshots.
- The stored vote must be the **pipeline-generated** stored answer, never the curated publish
  state (the v118 publish deliberately kept earlier values for 7 pass-unstable stems — that
  curation is label-informed and would smuggle labels into the rule).
