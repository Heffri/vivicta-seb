## 6. Real bugs hit this lane

### 6-1. Test-harness step-ordering bug caused one real Codex call (caught, then fixed)

The driver's first draft ran (c)/(d)/(g)/(h) *before* (b) selected Codex, on the theory that
matching v061's evidence-table letter order (a,b,c,...,h) meant matching *execution* order. It
does not: v061's own (e) is explicitly "fixture mode (first-launch default)" — that check must run
*before* any provider is selected, no matter where it sits in the lettered table. Running (e)
*after* (b) (the bug's actual first-run order was a,c,h,d,g,b,f,e,i) meant `_llm_configured()` was
already `true` when the fixture upload ran, so `app.py`'s `/extract` endpoint took the **real**
branch: `locate.candidate_pages` → `extract_mod.extract()` → `call_llm()` → an actual Codex CLI
subprocess call, on the synthetic 70-page fixture PDF's fabricated numbers. Caught immediately, not
silently: the step then timed out waiting for "Export JSON" past 30 s. Confirmed from
`backend.log` (`[extract] up-<hash> income_statement: candidate pages [64, 65]` followed by a real
`extract` 200, not a fixture short-circuit) and from the saved
`data/kb/up-<hash>/extractions/income_statement.json` in that run's now-discarded isolated
profile, which held **real** (not fixture-confidence) values — `confidence: 1.0` throughout, vs.
the fixture's own stated 0.91–0.97, and a `two_pass` warning that only fires on the real path.

No lasting effect: the data sent was this lane's own synthetic fixture PDF (fabricated numbers,
not a real report, not the owner's data), and the discarded profile (`electron-userdata`,
`electron-userdata2`) was never used again after this was found — the run recorded above used a
fresh `electron-userdata3` profile from a clean first launch. Fixed by re-deriving the true
dependency order from the code, not from the table's display order: **(e)/(i) must precede (b)**
(pristine, no provider) and **(c)/(d)/(g)/(h) must follow (b)** (need Codex/bm25 active, or — for
c/g specifically — need a report registered against the *post-restart* backend process; see §6-2).
Reported here per this project's "如实报" convention (v061 §6, v069's "premise overturned"
precedent), not raised as a supervisor message: no WO premise was wrong, no territory boundary was
crossed, and the fix needed no decision beyond re-reading the code — it is a driver bug, entirely
inside this lane's own test harness, with zero shipped-code effect.

### 6-2. Settings Save's backend restart invalidates any report opened before it

`applySettings` (main.js) kills the old backend process and starts a new one on Save; each
backend process keeps its `reports`/`extractions` dicts in memory only. A report opened via
`register_library`/`/api/reports/from-library` *before* a Save is gone from the *new* process's
memory after it — confirmed live: the first corrected-order attempt still opened Atlas Copco
*before* (b), and (g)'s `POST /api/reports/lib-atlas_copco_2025/index` 404'd against the
post-restart backend. Not a shipped-code bug (the frontend's own `results` state is unaware of a
backend restart, same class of staleness v061 §6-5 named for the status bar, just for a different
piece of state) — worked around in the driver by moving (c)'s KB-open to *after* (b), so the
report is registered against the backend that stays alive for the rest of the run. Named here, not
fixed in `desktop/main.js` or `frontend/src`: out of this lane's territory (packaging + evidence
only), and the WO's own step 2 asked for v061's checks "全部重做" with an addition, not a shipped
fix for this.

designed around from the start in this lane's driver, per those write-ups — no new instance of any
