## The rule

`_bucket_total_row`'s candidate list (rows whose label is a `total_debt.row_synonyms` debt word and that
read a real bucket header above them) now narrows by year *before* it narrows by `known_total`: when more
than one candidate survives, drop every candidate that `_bucket_row_prior_year` (v066, already trusted at
the write gate in `_fill_bucket_columns`) proves belongs to the fiscal year's predecessor. If that leaves
exactly one row, it wins outright. If it still leaves more than one — both candidates name the same year,
or neither names one at all — nothing is dropped and the existing ambiguous-decline fires exactly as
before. `_bucket_row_prior_year` itself is untouched; a header run naming both years side by side (a
different table shape, two-year columns rather than two stacked one-year tables) already makes it return
False on both sides of that comparison, so that shape was never in this round's scope and needed no change.

## Counter-example — two same-labelled rows, neither year decidable, still ambiguous

Per the work order's own explicit regression bar (Byggmax Group, v082: "two same-labelled `Borrowing`
rows, ambiguous, none used — the guard is working as designed"): a synthetic case built the same way as
the Tången one above, but with **both** blocks headed "31 december 2025" (neither is provably last
year's), asserts `_bucket_total_row(...) == []` with the unchanged ambiguous warning — the new narrowing
step must not fire when it cannot single out exactly one candidate.

### Byggmax Group's real page (seed8-kb, p.87–88) — traced, not assumed

Byggmax's real IFRS 7 liquidity-risk table (p.88) has the *same* two-candidate shape as Tången at the
`_bucket_total_row` level: "Borrowing 375 – – –" (Group, "At 31 December 2025") and "Borrowing 653 – – –"
(Group, "At 31 December 2024"), both under the same 4-word bucket header, both `total_debt.row_synonyms`
hits. (The table's own two "Parent Company" `Borrowing` rows are not candidates at all — `_bucket_header`'s
nearest-header walk reads their own header as 8 keys, not 4, so their amounts-length never matches and
they never entered `candidates` before or after this lane.) The new year-narrowing step *does* resolve
this pair to the single 2025 row internally, exactly like Tången — but that row is then rejected two
lines later, unchanged from before this lane: `_fill_bucket_columns`'s own pre-existing "one recognised
column proves nothing about the row's shape" gate (`sum(v is not None for v in derived.values()) < 2`)
drops it, since a row that only prints one real bucket amount (375; the other three columns are dashes,
and there is no total column in this table's header to prove a dash means 0) was never trustworthy on
its own — that gate is untouched by this round and is what keeps Byggmax safe, not a special case added
for it. Confirmed empirically, not inferred: replaying Byggmax's real stored `debt_maturity.json` through
`extract()` (`pages=[87, 88]`) before and after the fix gives byte-identical fields, confidences and
checks; the only observable difference anywhere is `warnings: 1 -> 0` (the "ambiguous, none used" message
no longer fires, because the row-picker itself is no longer ambiguous — the sparse-row gate downstream
rejects the sole survivor silently instead). This is the one `CHANGED` line in the debt_maturity replay
below, and it is exactly this: no field, confidence, or check moved.
