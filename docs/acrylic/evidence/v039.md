## Premise checks (things the work order guessed that turned out different)

1. **The work order's guessed fallback install dir, `%LOCALAPPDATA%\Programs\claude\`, does not exist
   anywhere in UAW's real discovery code.** `process-transport.ts`'s `discoverClaudeLaunch` (the function
   `adapter.ts` actually calls) is: a configured override, then PATH (bare `claude`), then `%APPDATA%\npm`
   directly (its own comment: for an Electron app's stale login PATH), then `~/.local/bin/claude.exe` (the
   native installer's default), then `discoverManagedClaudeExecutable` — the **Claude desktop app's own
   bundled CLI**, versioned directories under `%APPDATA%\Claude\claude-code\`, newest-that-validates wins
   (an upgrade leaves the old version behind, so more than one is normal). Its comment warns explicitly:
   `%LOCALAPPDATA%\AnthropicClaude` is the desktop **GUI's** own `claude.exe`, never to be driven as the CLI.
   Rewrote `_claude_executable()` to this real order minus the `%APPDATA%\npm` step (skipped for the same
   reason `_codex_executable()`'s own docstring already gives: a backend process inherits a shell's PATH, npm
   shim included, unlike an Electron app launched from Explorer), plus a simplified
   `_claude_managed_candidate()` for the versioned desktop-bundle fallback (numeric-tuple sort, no 256-entry
   cap or malformed-name ranking — disproportionate for a fallback-of-a-fallback that just raises if nothing
   validates). Confirmed for real on this machine: `shutil.which("claude")` resolves
   `~/.local/bin/claude.EXE`, and `_claude_managed_candidate()` independently finds
   `%APPDATA%\Claude\claude-code\2.1.271\claude.exe` (Claude Desktop is installed here too) — both real, both
   correctly ordered.
2. **`--tools ""` is confirmed, not just guessed** — UAW's own `CLAUDE_CATALOG_ARGUMENTS`
   (`process-transport.ts`) reaches for the identical `"--tools", ""` pair to take a headless catalog-fetch
   call down to plain text in, text out. Adapted its choice for our one-shot `-p --output-format json` call
   (simpler than UAW's `stream-json`/resumable-session protocol, which exists to drive an interactive,
   tool-permission-aware chat session — `llm.chat()` needs one prompt in, one text reply out, no tools, no
   session to keep alive, same reasoning v031 gave for using `codex exec` over Codex's `app-server` protocol).
3. **Anthropic's OpenAI-compatible endpoint silently ignores `response_format`** — not in the work order at
   all, found while writing the API-key documentation (Anthropic's own docs, cited below). `_openai_chat()`'s
   `response_format={"type": "json_schema", ..., "strict": True}` becomes a no-op over
   `https://api.anthropic.com/v1/`; Anthropic's docs say outright: "For JSON output, use Structured Outputs
   with the native Claude API." Documented in `backend/README.md` as a caveat, not a blocker — the model still
   answers from the prompt's own instructions, the same way `codex_cli`/`claude_cli` already do without any
   schema enforcement either.

## Provider selection

`LLM_PROVIDER` = `openai` (default) | `codex` | `claude`, validated in `llm.provider()`. `claude_cli` never
uses `LLM_BASE_URL`/`LLM_API_KEY`; it needs `LLM_MODEL` (`--model`, default `claude-sonnet-5`; `claude-opus-5`
and `claude-haiku-4-5-20251001` also work, nothing else attempted) and optionally `LLM_TIMEOUT` (shared
default 120s) and `CLAUDE_BIN`.

**Embeddings never go through Claude** — `kb.embed()` untouched, same as Codex. `/api/reports/{id}/index` and
`/api/ask` still gate on `LLM_BASE_URL` regardless of provider; that gate is correct as-is (v031 already
established this for Codex) and wasn't touched.

**Claude API key path: no new code.** `LLM_PROVIDER=openai` + `LLM_BASE_URL=https://api.anthropic.com/v1/` +
`LLM_API_KEY=<key>` + `LLM_MODEL=claude-sonnet-5` is the existing `openai_compatible` path, unchanged. Not
exercised against a live call — this environment has a Claude Code subscription, not a separate Anthropic API
key (`env | grep -i anthropic` empty besides the CLI's own OAuth session; `claude auth status --json` reports
`authMethod: "claude.ai"`, not an API key), and minting a new billable credential just to spend one of this
lane's two allowed calls on the already-well-trodden `openai_compatible` path (Ollama/Azure/OpenAI/OpenRouter
already exercise it) would have traded a `claude_cli` real-call for a lower-value one. Verified the request
*shape* instead, against Anthropic's own OpenAI SDK compatibility docs
(`platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk`, fetched 2026-09-16): base URL, bearer
key via the SDK's normal `api_key` param, model name passed through as-is, and `temperature=0` within
Anthropic's supported 0..1 range all check out; `response_format` does not (previous section).

## Findings

- The work order's guessed Windows fallback dir (`%LOCALAPPDATA%\Programs\claude\`) isn't in UAW's real
  discovery code; the real fallback chain is PATH → (skipped: `%APPDATA%\npm`, redundant for a
  shell-launched backend) → `~/.local/bin/claude.exe` → the Claude desktop app's own versioned, bundled CLI
  under `%APPDATA%\Claude\claude-code\<newest version>\claude.exe` — confirmed present on this machine.
  Never `%LOCALAPPDATA%\AnthropicClaude` (the desktop GUI's `claude.exe`, not the CLI) — UAW's own comment
  calls out that exact confusion as a silent-failure trap.
- `--tools ""` is UAW's own choice too (`CLAUDE_CATALOG_ARGUMENTS`), not just this lane's guess, for the same
  "headless call, no tools needed" reason.
- **Anthropic's OpenAI-compatible endpoint silently ignores `response_format`** (Anthropic's own docs) — a
  teammate using the API-key path should not expect the `strict` JSON-schema guarantee that a real
  OpenAI/Azure/Ollama endpoint gives; the prompt's own instructions are all that's enforcing JSON shape there,
  same as `codex_cli`/`claude_cli`.
- The real end-to-end result matched the local-model baseline on every field, byte for byte, on the first
  attempt (28.3s, one call) — no second extraction call was needed, leaving the 2-call budget spent exactly
  on (1) settling the CLI flag shape empirically and (2) this end-to-end check.
