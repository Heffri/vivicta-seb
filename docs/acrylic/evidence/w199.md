## 1. The defect, restated as a mechanism

Two halves feeding each other (QA w195 saw 44/206 rows "Building" for 45 minutes, `/api/kb` taking
2 s per call during the storm vs instant when quiet):

- **Frontend** (`frontend/src/components/KbView.tsx` 42–49 pre-w199): the poll effect re-fetched the
  whole KB every fixed 2 000 ms whenever *any* entry had `status === 'building'` — no backoff, no
  attempt cap, no stop.
- **Backend** (`backend/pipeline/kb.py`): `index_status` acquired the stem's **write** lock
  (`report_lock(stem)`, the same RLock `index()`/`save_report`/`fill_ocr_pages` hold for real
  writes) non-blockingly around its hash/validate. Under overlapping listings — exactly what a 2 s
  poll against a slow (seconds-per-call) listing produces, with uvicorn's threadpool running several
  `/api/kb` at once — one listing's slow hash made every sibling listing's `acquire(blocking=False)`
  fail, and those siblings returned `status=building, reason="Report update in progress"`. Worse,
  `entries()` **cached** whatever status it had computed into `_entry_cache` keyed by a file
  fingerprint; contention manufactured building entries, and after contention ended the fingerprint
  was unchanged, so the cached building was served **forever** — the poll never had a reason to stop.

In fixture mode (no model configured) no index task can even start, so every row should sit on a
terminal non-building status (`missing`/`outdated`/`invalid`) and the page should never poll.

## 2. Backend change — red then green

`backend/pipeline/kb.py`, four touches, no retrieval or data-format changes:

1. **`index_status`** now decides "building" from a single question: *does a real write hold the
   stem's write lock right now?* — answered by probing the lock via the existing `_index_in_progress`
   helper (`index()`/`save_report`/`fill_ocr_pages` are the only writers). Readers never take that
   lock any more, so overlapping listings cannot manufacture the status off each other. The
   same-thread property `index()` relies on is preserved: its own `index_status(stem)` call while
   holding the lock succeeds reentrantly (RLock) and therefore still hashes and sees the true
   ready/outdated status.
2. **`_index_status`** and **`inspect_chunks`** dropped their `with report_lock(stem)` — they are
   readers, and a reader holding the write lock was both the false-building source and a queue in
   front of real writers. Torn reads against a concurrent write stay detectable: writes are atomic
   (`atomic_write`/`os.replace`), and the caller's stat-signature changes on any real write, so a
   transient mismatch shows as a one-listing "invalid" that recomputes away on the next poll.
3. **`entries()`** never caches a `building` entry — it describes the listing that observed it, not
   a state of the files. This kills the persist-forever path outright.
4. No changes to `index()`, `save_report`, `fill_ocr_pages`, `search()`, chunking, or `data/kb`.

**Tests** (`backend/pipeline/test_kb.py`, two new, self-check style, wired into `__main__`):

- `test_status_building_only_during_real_writes` — quiet fixture stem must be `missing`; a thread
  holding the stem lock (standing in for a real write) must give `building` /
  `"Report update in progress"` through both `index_status` and `entries()`; after release with
  nothing written, both must be `missing` again. **Red before** (the last assert saw the cached
  building served back: `{'stem': 'acme_2025', ..., 'status': 'building', 'reason': 'Report update
  in progress'}`), **green after** — deterministic, no timing reliance.
- `test_concurrent_reads_never_report_building` — the storm's shape: 8 barrier-synchronised threads
  × 4 rounds of `index_status` + `entries()` over a fresh cold cache, against a real, valid, fat
  index (a 400-page saved report built through the fake embedder, status `ready`, plus the un-indexed
  3-page seed at `missing`). Every one of the ~64 status observations must equal its stem's quiet
  status. **Red before** (`concurrent reads manufactured other statuses: ['building', 'missing',
  'ready']` — building from lock collisions, exactly the production mechanism), **green after**.

Both red observations were captured by running the new tests against the unfixed `a35b802~1` code;
both green on `a35b802`.

## 3. Frontend change — poll cadence and the give-up notice

`frontend/src/components/KbView.tsx`:

- Polls only while some entry says `building` (unchanged), but the gap now doubles per attempt —
  2 000 → 4 000 → 8 000 → 16 000 ms (capped) — and stops for good after 10 attempts.
- Any response with no `building` row stops the polling immediately (the effect's own condition);
  the attempt counter and delay reset whenever a listing arrives building-free, so a *new* real
  build gets a fresh backoff cycle.
- After the 10th attempt a `role="status"` line appears above the table: **"Indexing did not finish
  — refresh the page to retry."** (the work order's 索引未完成/刷新重试, in the UI's English).
- A manual row Rebuild still refetches through `build()` regardless of the polling state.

## 5. Dev repro — before/after cadence on a real build

Method (scripts and logs in the lane temp directory, not the repo): a fake OpenAI-compatible
embeddings endpoint that sleeps `HOLD` seconds and then returns 500, given to the backend as
`LLM_BASE_URL` (so `retrieval=hybrid` and a rebuild really calls `embed()`); one
`POST /api/reports/{id}/index` fired **out of band** so the rebuild holds Atlas Copco's stem write
lock for the hold duration (the row truthfully shows building in both the old and new backends);
the page opens in a fresh browser context (clean first boot) on ports 5106→8106; every `/api/kb`
request is timestamped client-side. Reload lands a listing *during* the hold — the only way a
listing observes the row as building (with the old frontend, a Rebuild click alone never does: it
awaits the POST and refetches only after the lock is free — which is why the storm needed
*concurrent* listings to ignite, and why the backend half of the fix is proven by the unit tests
above rather than this single-client scenario).

- **Before** (old frontend + old backend): building observed; 18 consecutive `/api/kb` re-fetches at
  a uniform ~2.2 s cadence (gaps 2 231 / 2 321 / 2 206 / 2 199 / 2 173 / … / 2 306 ms) — the storm
  shape; it continues for as long as any row says building, which under the old backend's cached
  building could be forever (QA's 45 minutes).
- **After**: quiet phase = 2 initial listings, then silence; the during-hold listing observes
  building; poll gaps 2 402 / 4 171 / 8 170 then 16 187 × 7 — exactly the 2→4→8→16 backoff, exactly
  10 attempts, then the give-up notice renders and the tail is silent (`silentTail: true`, no
  further requests for the rest of the observation window).
- Screenshots (`docs/acrylic/evidence/w199/`): `before.png` (Atlas row "building"/"Building…", all
  other rows "missing" — the Embeddings column converged), `after.png` (same mid-storm, fixed
  build), `after-notice.png` (the refresh-to-retry notice visible above the table).

## 8. Not settled / risks

- The 45-minute QA storm itself was not replayed in dev (it needs a loaded multi-client backend to
  ignite; a single-client repro cannot manufacture cross-request lock contention honestly). The
  backend half is covered deterministically by the two unit tests; the dev repro demonstrates the
  frontend cadence half before/after on a real build.
- A real index build longer than ~126 s (2+4+8+16×7) will finish without the page noticing; the
  notice says to refresh, and a manual Rebuild still refetches on completion. Bumping
  `POLL_MAX_ATTEMPTS` is a one-constant change if the owner wants a longer tail.
- While a real write runs, each poll recomputes that stem's status (cache bypass) — a cheap
  non-blocking lock probe plus, at most, one hash per file revision; no measurable cost at 206 stems.
- `EMBED_BASE_URL`/`EMBED_MODEL`-driven identity, the entry-cache warm-read guarantee (v173's
  "warm entries() reads no file contents" test), and the retrieval three-state are all unchanged and
  still asserted by their existing tests.
