# v117 — window caption buttons follow theme and tone — evidence

Branch `ao/vivicta-glm-60/v117-window-controls` (lane `vivicta-glm-60`), baseline `origin/acrylic`
at dispatch (`76828f6`), delivery on the merged tip including v116+v121 (merge commit on the
branch). Owner complaint: the three top-right window buttons are the native `titleBarOverlay`
with colors hardcoded per tone (`#14141b` / `#f7f7fa`), a flat block in **both** themes; required:
same color as the titlebar under Solid, the same transparency as the glass under Acrylic, and to
follow theme/tone switches instantly.

## 0. The cause, in one paragraph

`toneOverlayOptions()` gave the native overlay an **opaque** `color` per tone. But the window's
own titlebar is not one flat color in any theme×tone: Solid dark keeps the v006b wallpaper glass
(v100 §0), Solid light paints the strip opaque white, Acrylic is the one glass pane over the OS
material. An opaque overlay of *any* color therefore reads as a block against the strip it sits
on — the work order's premise was only about which color to pick, and the pick could never win.

## 1. UAW prior art (the 15:10 standing rule)

Read before writing anything (read-only, `demo` branch):

- `src/workbench-shell/electron/main.ts` — UAW builds its window with `frame: false` and draws
  its own caption buttons in the renderer; no `titleBarOverlay` anywhere.
- `src/workbench-shell/window-control-bridge.ts` + `electron/preload.ts` — the IPC shape for
  self-drawn buttons (`minimize` / `toggle-maximize` / `close` actions, a `maximized` state push
  on the window's `maximize`/`unmaximize` events, a dispose subscription).
- `src/workbench-shell/renderer/chrome.tsx` + `styles.css` §4b — the caption button component
  (10px stroke glyphs, 46px-wide buttons, Windows-convention red close hover, forced-colors rule).

So UAW's answer to this exact problem is **path B** (`frame: false` + self-drawn buttons). The
work order orders two paths: A (keep the native overlay, color it per theme×tone, try alpha under
Acrylic) then B, "选能过验收的那条". **Path A was tried first and passed, so B was not needed.**
The measured reason is §2 — and it is a premise flip worth recording: the work order expected
"Windows 把透明 overlay 画成黑色/不透明(很可能)"; on this stack (Electron 37, Windows 11
26100) that is **false** — the overlay color composites over the page with its alpha, so a fully
transparent overlay makes the page's own titlebar show through under the OS-drawn glyphs.

If a future requirement needs *styled* buttons (custom hover, snap-layout flyouts, anything the
WCO cannot do), UAW's bridge + `chrome.tsx` + `styles.css` §4b listed in this section is the
recipe to port; nothing here closes that door.

## 4. How the captures were made (and why)

The work order requires window-rect captures: `webContents.capturePage()` cannot see the native
overlay, so it cannot prove anything about v117. First attempt used a screen grab of the DWM
frame bounds — and captured the **owner's** maximized desktop-app window instead (the test window
could not be raised without stealing focus, and stealing the owner's focus on a live machine is
worse than a failed capture). Those first captures were deleted in place and are not in evidence.
Final harness: `PrintWindow(hwnd, PW_RENDERFULLCONTENT)` — the window's own composited surface by
HWND, occlusion-independent, no focus or cursor involvement, and unlike `capturePage` it includes
the native caption area. State assertions ran before every capture; nothing was kept from a state
that failed its assertion.

## 5. Packaged verification (LESSONS 42)

`refresh-app.ps1 -Src <this worktree>` (fresh unpacked app dir under the lane scratch; BUILD.txt
records the branch/sha it came from) → the packaged exe launched once with an isolated
`--user-data-dir`:

- data sync on launch: `+206 kb entries, +7 files` (v107 merge, from this branch's bundled data);
- `GET /api/kb` on the packaged backend's port answered with the full index: **206 entries**;
- each caption button was exercised the way its click ends up: a physical caption-button click
  ends in `DefWindowProc` posting one `WM_SYSCOMMAND` (`SC_MINIMIZE` / `SC_MAXIMIZE` /
  `SC_RESTORE` / `SC_CLOSE`), so those were posted straight to the window's HWND — v038's
  message-level method, no cursor movement, no global input on the shared machine. Asserted on
  the real window: minimize → `isMinimized() true`, restore → false; maximize → `isMaximized()
  true`; restore → false; close → the process tree exits. Recorded numbers in the lane's
  `packaged-record.json`.

One finding on the way, for whoever drives these buttons next: coordinate-based
`WM_NCLBUTTONDOWN` with `HTMENU` at a computed button rect **mis-routed** — the window closed
instead of minimizing (Chromium evidently re-hit-tests the lParam, and a DWM-borders offset puts
the computed point on the wrong glyph). The per-button `WM_SYSCOMMAND` is deterministic; don't
synthesize non-client clicks by coordinate against a WCO.

Two environment traps hit on the way there, for the next lane:

1. `-SkipBackend` does **not** mean "keep the existing packaged backend" — `prepare-resources.js`
   stages `backend/dist` only when it exists, so the first refresh **replaced the shared app's
   working backend with an empty directory** and the app quit at startup (backend spawn → early
   exit, no crash log; the launcher's log stopped right after the data-sync line). A full refresh
   (backend build included) restores it.
2. `refresh-app.ps1` only installs `requirements-build.txt` when it *creates* the venv; a venv
   that already exists (this worktree's did) hits `No module named 'PyInstaller'` — and the PS
   pipeline in the script swallows the nonzero exit, so the "refresh" reports done. Install
   `requirements-build.txt` into a pre-existing venv before refreshing.
