### 5-b. exe-内 codex 可执行发现 (the WO's fetch.py fourth-level concern) — ✓ by chain, no inference fired

The fourth level's gate (`fetch.websearch_provider()` → provider ∈ {codex, claude}) and its
executable resolution (`llm._codex_executable`: `CODEX_BIN` → `shutil.which("codex")` →
`%LOCALAPPDATA%\OpenAI\Codex\bin\codex.exe` → `…\Programs\OpenAI\Codex\bin\codex.exe`) are in
`pipeline/llm.py`, bundled with the exe (app.py imports `pipeline.fetch` → `pipeline.llm` at module
level — the exe serving the acceptance run at all proves that import graph loads). Every link of
the discovery chain then verified **live on this machine**:

1. `desktop/main.js` spawns the packaged backend with `{ ...process.env, ...env }` — the backend
   inherits the shell's environment; a double-click launch inherits Explorer's, i.e. the registry
   PATH.
2. `codex` resolves to `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`; that directory **is
   present in the User registry PATH** (`[Environment]::GetEnvironmentVariable('Path','User')`) —
   so `_codex_executable`'s `shutil.which` step hits for a double-click-launched app.
3. Belt-and-braces: that same path is byte-identical to llm.py's **second fallback candidate**
   (`Test-Path` → True), so resolution survives even a stripped PATH.
4. In the packaged app itself, Settings → Codex shows `codex-cli 0.153.4 · logged in` (shots
   03/08) — the shell's own zero-model CLI status check (`codex --version` + `codex login status`)
   succeeding in the packaged environment.

Honest limit, stated plainly: the fourth level itself was never fired — under codex a firing **is**
a real web-search call, which the WO forbids. What this proves is everything up to the final
subprocess spawn: the code is in the exe, and the resolution it performs resolves here.

## 6. Findings

### 6-1. WO wording vs implementation on (j) — imprecise, not overturned, intent satisfied

The WO reads "fixture 模式下点它 → 提示需选提供方". The shipped v074 UI never renders a button in
fixture mode: the button *is* the codex/claude face, and fixture/openai get the muted hint instead
(`UploadView.tsx` line 237's conditional). So there is nothing to click in fixture mode — the hint
**is** the "提示需选提供方", verified in shot 10, and the button itself verified in shot 11 under
codex (unclicked). The WO's intent (fixture can't web-search; the user is pointed at Settings; zero
real inference) is exactly what ships.

0.3.2). `README-0.3.3.txt` therefore lists only what actually changed: v074's web search and
v076's carrying-amount slot. Check (f) re-verified the status-bar behavior live anyway.

### 6-3. The 0.3.2 portable exe could not be deleted from the shared dist — it is running

process: PID 25816, started 12:47 today, image path the shared dist's own 0.3.2 portable — i.e.

not this lane's process, so it was **not** killed (only own PIDs, always). The 0.3.2 **Setup** exe
and `README-0.3.2.txt` were removed; the 0.3.3 pair and `README-0.3.3.txt` are in place; the
0.3.2 portable remains alongside until whoever runs it closes it. Flagged in the delivery message.

### 6-4. One sentence in v071's evidence misattributes the 0.3.2 version-line commit (historical)

version-line edit"; git shows that range's version-line change is v061's 0.3.1 bump landing,
while v071's 0.3.2 bump (`2f0faac`) merged **after** `e216fd4` — meaning v071's build content was
`e216fd4` + its own one-line version bump, exactly the shape this lane's build has (stated in the
header above). Zero shipped impact either way; recorded so the pattern is written down correctly
somewhere.
