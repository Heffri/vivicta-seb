# v158 — mechanism-only replay: extract() with the model's four answers nulled, on the pages the model picked (debt_maturity, zero model calls)

Lane `ao/vivicta-glm-91/v158-mechanism-only-replay`, from `origin/acrylic` `9c5c365`. **Zero model
calls**: `call_llm` is stubbed; every number below is the current `extract()` run offline over the
stored KB. Question: model variance is now the largest residual (v141's same-model rerun lost value,
v152 flipped window values 3/14). If the model's four debt_maturity answers are thrown away and only
the deterministic mechanisms read the pages the model selected, what survives? This decides whether an
`EXTRACT_TABLE_FIRST` mode (model only picks the page, table readings preferred, model values only as
null-fill) is worth building.

## Setup (`scripts/mechanism_only.py`, new; nothing else changed)

- Per stem, the stored `extractions/debt_maturity.json` fields are fed back as the model's own answer
  (MODEL_KEYS only — the replay_check/publish_kb convention), then stripped: the **mechanism** answer
  keeps each schema field's key/label with value/unit/period/raw_label/source all null; the **total**
  answer keeps the stored total_debt verbatim (the model's best field; the buckets are where the
  instability lives) and nulls the rest.
- Window = publish_kb's own construction (imported, not re-derived): the two_pass selection recorded in
  the stored warnings (selection first) UNION the stored fields' cited pages. 101/105 stored records
  carry a two_pass line. `--pages locate` swaps it for `pipeline.locate.candidate_pages`' ranking — the
  deterministic locator standing in for the model at page-pick.
- Scoring uses eval/run.py's own `values_match` (null-aware) against `eval/labels.csv` (271 rows:
  total_debt 105, due_within_1_year 84, due_1_to_5_years 43, due_after_5_years 39), plus a per-field
  comparison against the stored record itself (same / lost / found / different). Per field the run's
  own warnings are mapped to a writer by eval_breakdown's vocabulary; per stem a **shape** class comes
  from the stored record's own markers (which repair family produced it), with the no-marker default
  split by whether ≥2 buckets were read at all (plain bucket rows vs a total-only shape — balance-sheet
  totals, bank liability rows, lease tables).
- `oresund_2025` is not replayable on the stored window (no two_pass line, no cited pages — the
  locator-dead stem since v090): its 2 label rows drop out of the window denominators (269/104), and
  the locate run (whose candidate pages do reach it) carries 271/105. Full per-stem output:
  `v158/replay-window.md`, `v158/replay-locate.md`; per-field rows in `v158/fields-*.csv`.

Three facts carry the answer:

1. **The mechanisms' own reads are a strict subset of the stored record — and tiny.** 34 non-null
   values across the corpus (8% of the 416 field slots), all 34 repr-identical to the stored value, all
   34 label-correct, and all 51 null-labeled fields correctly declined: precision 100%, but recall on
   non-null labels is 34/220 = 15.5%. What mechanisms would lose against the stored record: **137
   fields the model+mechanism read right** go null — and 0 turn wrong. The model's per-row reads are
   the recall; the mechanisms alone mostly have nothing to read.
2. **"Mechanism right where the stored record is wrong" — the set the work order hypothesized — is
   empty at company level and 1 field at field level.** The one field is net_insight's
   due_after_5_years: label null, stored 0 (the self-consistent wrong-scope sibling table, v115's open
   scope gap), the mechanism declines and thereby matches the label. That is a refusal beating a wrong
   model value — not a table reading the model had carried away. On these pages there is no company
   whose correct deterministic read the model misleads the mechanisms away from.
3. **Even handing the mechanisms the model's best field changes the picture quantitatively, not
   qualitatively.** total-only reaches 58.7% fields / 35.6% companies — the model's total arms the
   identity gates, but the bucket machinery still finds little: 26 non-null buckets against the
   stored 82. And it introduces the experiment's only wrong values on stored-right fields:
   enea total_debt 305555 → 136403 and fagerhult 3449.5 → 6.3 — the segment-column re-read replacing a
   correct total with another column of the page's segment table (a current-code replay firing the
   Volvo repair where the run that produced the stored record had not). A mechanism-preferred policy
   has its own override risk, not just a recall ceiling.

## Where the 34 reads come from, and which mechanisms are dead without the model

Writers of the mechanism variant's 34 values: `_fill_bucket_columns` 19 (the one-row/bucket-columns
table), `_subtotal_pair_fill` 10 (non-current + current section subtotals), statement-spread null fill
5. **Zero** from `_finer_split_rows`, `_between_rows`, `_date_bucket_derive`, and v156's on-null
window family: every identity-gated mechanism gates on a verified total_debt or on an identity check
with real operands — all model products. The "on-null" family is on-null only after the model has read
something to close against. The mechanisms that fire alone are the ones that prove a table's structure
by itself: a bucket header naming its columns, two Summa rows each closing on their own rows, or a
synonym row on the statement spread.

## Conclusion — `EXTRACT_TABLE_FIRST`: no

The deterministic layer on the model's pages is precise but nearly empty: 34 reads that the stored
pipeline already contains, plus one refused wrong 0. Preferring table readings would risk 137 stored-right
fields to chase that 1-field upside; keeping the model's total as well still caps at 59% fields / 36%
companies against the status quo's 82%/70%, and its only new wrong values are mechanism overrides of
correct model totals (enea, fagerhult). Dropping the model's page choice too makes everything worse
(locate sensitivity: 69 fields / 9 companies). **The model's contribution on these pages is not a
noisy re-reader of tables the rules can read — it is the only reader most pages have** (86% of stems),
and where the rules can read, they already agree with the pipeline.

What the numbers do support instead: the mechanisms' 100% precision on their own reads and the
net_insight refusal say the current architecture — model reads with mechanism verification, guards and
null-fills on top — is the right division of labour; and for the variance problem itself, v129's R5
(corroborated union against the stored answer) remains the measured remedy. A narrower takeaway worth
keeping if table-first is ever revisited: the only fully mechanism-readable shapes are the
bucket-column table and the subtotal pair — together 10 stems (13.5% companies), where a mechanism
cross-check of the model's answer is already what the pipeline does.
