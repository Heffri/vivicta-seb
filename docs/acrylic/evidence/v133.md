## What landed

- **`backend/pipeline/merge.py` (new)** — pure functions, no model calls, no disk:
  - `mode()` — `EXTRACT_MERGE_RUNS` as `off|union|majority`; anything else (unset, `off`, a typo)
    is `off`, so a typo can never silently turn the second run (and its cost) on.
  - `matches_stored(run1, stored)` — v129 R5's **exact** skip trigger: run1 value-identical to the
    stored answer on every one of run1's fields (±2 band, null == null). Under the majority merge
    the second run is then provably a no-op (every field already has two agreeing votes or two
    nulls), so the skipped calls buy nothing.
  - `merge_runs(run1, run2, stored, mode) -> (merged, decisions)` — the per-field merge. Inputs are
    only what each run reports: value / confidence / evidence / source, plus whether the run's
    identity check passed (named `maturity_sums_to_total`, else the first check — both shipped
    schemas put an identity check first: debt_maturity's `maturity_sums_to_total`,
    income_statement's `gross_profit_arith`). Labels never enter a rule. `merged` is run1's shell
    with per-field winner fields (full field: source/evidence/confidence), warnings prefixed
    `run1:`/`run2:` and closed by one `merge: <mode>, per-field: <key>=<how>, …` summary, and a
    top-level `"merge": {"mode", "runs": 2, "decisions": {key: how}}`. Inputs are never mutated
    (asserted). run1 keeps its `prior_year`/`buckets_by_year` extras — a documented simplification,
    those blocks are run1-derived by definition here.
  - `recheck(merged, schema, texts, pages)` — recomputes `merged["checks"]` over the merged values
    with `extract._check`, the same inputs as `extract()`'s final check pass (defaults from the
    schema, `stated_zeros` rebuilt from the merged fields' evidence). The winner run's own checks
    would misdescribe a field mix, and taking them verbatim "would be misaligned", so they are
    never reused. Note per the work order: this imports extract's *private* `_check` — extract
    exposes no public alias, and `workbench.checks` already calls the same private function.
- **`backend/pipeline/kb.py`** — `save_run(stem, section, n, result)` writes
  `extractions/<section>.run<n>.json` (the raw per-run answer, *before* `workbench.decorate`,
  via the same atomic write as `save_extraction`). The work order asked to confirm existing code
  does not mistake a run record for a section — **it did**: `entries()` (sections list),
  `chunks()` (fact chunks), `index()` (embeddings cache deps) and `_bm25()` (cache key) all
  globbed `extractions/*.json`, so `<section>.run1.json` would have shown up as a section,
  doubled fact chunks and bust embedding caches. Fixed with one `_section_files()` helper (bare
  `[a-z0-9_]+` stems only — a section name can never contain a dot) used by those four call
  sites; `fewshot_examples` and every app.py path already used exact `<section>.json` names.
- **`backend/app.py`** — only the `run_extract` body, real-model branch (fixture branch and the
  `reuse_saved`/409-review gates byte-identical). After run1: read the stored answer
  (majority only; `has_reviews`-gated — though the 409 gate already refuses to re-extract a
  reviewed section, so this is defense in depth), exact-trigger → skip, else run2 on the **same
  pages**, `kb.save_run` × 2, `merge_runs`, `recheck`, log
  `[extract] … merge=<mode> runs=<n>`, then the unchanged decorate/save tail. With `off` the only
  executed additions are the env read and the branch check — no second call, no run files, no
  `merge` key (route test asserts exactly that).
- **`backend/pipeline/test_merge.py` (new)** — 14 tests: the rule unit tests below on v129's real
  field shapes, purity/shape, `mode()` parsing, the kb section-exclusion, and four route-level

## Rules as implemented (the work order's parameters, applied per field)

- **union** (fresh; `stored` ignored): both null → null; one non-null → it; two answers → the run
  whose identity check passed, else higher confidence, else **run2** — whether the two values
  agree within ±2 or conflict changes only the recorded reason (`agree:`/`conflict:`), not who
  wins.
- **majority** (usable stored): three votes {run1, run2, stored} by value (±2, null votes as
  null), ≥2 votes win and the field comes from the winning value's own run (run1 → run2 →
  stored); three mutually distinct answers fall back to union over the two fresh runs. `stored`
  is only the **pipeline-generated** stored answer (no `human_review`/`basis_history`, via
  `has_reviews`); without one, majority decides exactly like union (asserted over three cases).
- **exact trigger** (majority only): `matches_stored` → one call, merged = run1, warnings gain
  `merge: run1 matches the stored answer field by field; second run skipped`,
  `"merge": {"mode": "majority", "runs": 1, …}`.
- A ±2 near-miss still votes together (100 vs 101.5 is one answer; 100 vs 103 is a conflict) —
  absolute band per the work order, not eval's relative `values_match` (that one is for scoring).

**Deviation from v129's measurements, kept as ordered:** the work order pins the confidence tie
to **run2**, while v129 scored tie→run1 one company higher (academedia: 12103 run1 vs 12114 run2,
both checks failing, conf 0.9 = 0.9 → union lands on 12114 here, and its real three-way majority
shape — null stored, two disagreeing runs — falls back to that same union tie, where v129's R5
had nulled the field). Same for the union of two disagreeing answers. The tiebreak is one constant
(`_pick`) if the owner wants it flipped; the unit test records today's behavior.
