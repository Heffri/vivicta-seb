## 5. The Claude-provider gap: real at dispatch, resolved by merge

At dispatch, `backend/pipeline/llm.py`'s `provider()` only accepted `"openai"`/`"codex"` —
`LLM_PROVIDER=claude` raised `ValueError` immediately. The owner's follow-up message assumed this would
degrade gracefully ("后端不认时 /api/config 会回 fixture"); reading the actual code (not the assumption)
showed otherwise: `_llm_configured()`'s `bool(LLM_BASE_URL) or llm.provider() == "codex"` calls
`llm.provider()` unconditionally whenever `LLM_BASE_URL` is unset (the common "pure subscription, no
base URL" case), so the raise wasn't contained — it propagated out of the `/api/config` route handler
as an unhandled exception. **Verified live, not just read**: saved a Claude config with no base URL,
watched `applySettings()`'s health-check loop exhaust its full 30 s (every poll of `/api/config` 500'd,
never once healthy), then confirmed directly — `GET /api/config` → `500 Internal Server Error`, not a
fixture response.

This was going to ship as a documented rough edge (30 s wait, then a clear error, no crash — the app
keeps running on whatever backend process exists, per `applySettings`'s design) until `git fetch` +
`git merge origin/acrylic` partway through this lane picked up `cb07a68`/`cd65878`
(`docs/acrylic/evidence/v039.md`): a real `LLM_PROVIDER=claude` backend (`claude -p`, non-interactive),
landed independently while this lane was in flight. Re-verified live after merging: Claude card → Save
→ `GET /api/config` → `{"model":"claude-sonnet-5","embed_model":"bge-m3","base_url":null,"llm":true,
"provider":"claude"}` — a real, working save, no 500. Screenshot: `settings-claude-saved.png`. The
30 s-wait-then-error path is still real and still what a *config that genuinely doesn't work* looks
like (e.g., `codex`/`claude` selected without ever running `codex login`/`claude login` at all, or an
`openai` card with a wrong port) — kept as-is; a fast-path 500-detection special case for one provider
would have been solving a problem that, post-merge, no longer exists for Claude specifically.

## 6. Real bugs found live, not from reading the code

Four, each the kind LESSONS #10/#12 warns source-reading alone won't catch:

1. **`codex login status` prints to stderr, not stdout.** `testCodex()`'s `/logged in/i.test(status.
   stdout)` always missed it — a real, logged-in Codex CLI showed "not logged in" in the UI. Found by
   replaying the exact `execFile` call standalone and printing both streams separately (a plain
   terminal `codex login status` merges them onto the screen with no visible distinction, which is
   presumably how this got written wrong the first time). Fixed by checking `stdout + stderr` together
   rather than hardcoding which stream, in case a future Codex version moves it back.
2. **The radio's accessible name swallowed every field caption below it.** `ProviderCard`'s wrapping
   `<label>` gives its `<input type="radio">` an implicit name from *all* content inside the label —
   including, once a card is selected, the field captions rendered inside it ("Base URL (optional)",
   "API key (optional)..."). A screen reader would have announced that whole blob as the Claude radio's
   name. Found by Playwright's own strict-mode error when a locator by accessible name matched both the
   radio and a text field; not something reading the JSX would have caught, since the bug only exists
   once a card *renders its children*. Fixed with an explicit `aria-label={title}` on the input, which
   overrides name-from-content outright.
3. **A failed Save left "Running now" showing stale, wrong data.** `save()`'s error branch never called
   `refreshStatus()`, so after a failed restart the status row kept showing whatever the *last
   successful* config was — implying the old provider was still live when the backend had actually
   already been killed and replaced with a broken one. Two-part fix: call `refreshStatus()` on failure
   too, and make `refreshStatus()` itself clear `status` to `null` on a failed fetch (its `.catch` only
   used to set `statusError`, leaving stale `status` to win `StatusRow`'s `status ? ... : error` branch
   forever). Verified: the row now reads "500 Internal Server Error" immediately after a failed save.
4. **`fetch failed` alone is not an actionable error message.** Node's `fetch` collapses every network
   failure (refused, blocked port, DNS) to that one string and puts the real reason on `.cause`. Testing
   against an unreachable local port surfaced `.cause.message === "bad port"` (Node/undici blocks a
   short list of ports outright, port 1 among them) — a financial-analyst user seeing bare "fetch
   failed" would have no idea what to do next. Fixed by appending `.cause.message` when present; now
   reads `fetch failed: bad port`.

## 7. Cross-lane finding: Electron's `userData` isn't session-isolated

`app.getPath('userData')` resolves to `%APPDATA%\annual-report-parser-desktop` — fixed by `package.json`
name, not parameterized by port or session the way the backend/frontend dev servers are (`common.md`'s
800N/520N convention doesn't cover this). Any two lanes running `desktop`'s Electron dev mode at the
same time collide on the same `config.json`, `data/`, and single-instance lock. Hit this directly: an
early launch attempt silently lost the singleton-lock race (clean exit, no error dialog, no new
`backend.log` entry — findable only by noticing the shared `userData` directory's own file timestamps
didn't match my launch time). Worked around it for this lane's testing with an isolated
`--user-data-dir` pointed at `uaw-lanes/vivicta-seb-28/electron-userdata/`; reported to the supervisor
mid-lane (`ao send`, since v038 was concurrently touching `desktop/` files and might also need to run
the shell). Also found, separately: the `.cmd` shim (`electron.cmd`) mis-splits a `--user-data-dir`
argument whose path contains the account name's space — invoking the real `electron.exe` binary
directly sidesteps it, same root cause as `main.js`'s own documented `spawn EINVAL` fix for the vite
dev-server spawn.

## 10. Not done / left for later

- The "revert to the previous config on a failed save" behavior the owner might expect — deliberately
  not built (§5): a failed save leaves the new (possibly broken) backend running and shows the error,
  rather than silently re-launching the old one. Flagged as a design choice, not an oversight, since
  auto-reverting adds a second env/port dance to get right for a case (misconfigured provider) the user
  can just fix and re-save.
- `CLAUDE_BIN`/`CODEX_BIN` overrides are read from `process.env` (the Electron process's own
  environment) for the Test button, same as the backend reads them for real calls — there is no UI
  field for either, matching the work order's config-model field list (no `codexBin`/`claudeBin` key).
