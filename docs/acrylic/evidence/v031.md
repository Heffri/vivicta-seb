## What changed

  every model call now goes through. `openai_compatible` is the previous `extract.call_llm` body, moved
  verbatim (Ollama-native `/api/chat` branch and the OpenAI-compatible `/v1` branch, byte-for-byte).
  `codex_cli` shells out to `codex exec` non-interactively.
- **`backend/pipeline/extract.py`**: `call_llm` is now `return json.loads(llm.chat(system, user, schema,
  name))` — same name, same default args, same call site in `extract()`. Removed the now-unused `openai`/
  `urllib.request` imports. Nothing else in the file changed (diff is 15 lines removed, 3 lines changed).
- **`backend/pipeline/kb.py`**: `ask()`'s lazy `from .extract import call_llm` (there to dodge a circular
  import — `extract` imports `kb` for few-shot examples) is now a top-level `from . import llm`, since
  `llm.py` depends on neither module. Call site: `json.loads(llm.chat(ASK_SYSTEM, user, ANSWER_SCHEMA,
  "answer"))`. `embed()` is untouched — embeddings never go through Codex (below).
- **`backend/pipeline/test_llm.py`** (new): fake `codex.cmd` + Python script, no network/install needed.
- **`backend/README.md`**, root **`README.md`**, **`backend/.env.example`**: document `LLM_PROVIDER`,
  `LLM_MODEL`'s new default, `CODEX_BIN`.

## Premise checks (things the work order guessed that turned out different)

The work order said to follow UAW's actual code over its own paraphrase wherever they disagree, and to
record it. Four places they did:

1. **UAW's Codex integration is `codex app-server --stdio` (a persistent JSON-RPC session), not `codex
   exec`.** Confirmed by reading `src/agent-runtime/codex/process-transport.ts`
   (`CODEX_APP_SERVER_ARGUMENTS = ["app-server", "--stdio"]`) and `codex-adapter.ts`. That shape exists to
   drive an interactive, multi-turn, tool-calling agent session inside a desktop app. `llm.chat()` needs
   one prompt in, one text reply out, no tools, no session to keep alive — exactly what `codex exec` (the
   CLI's own documented non-interactive/scripting entry point) is for. Used `codex exec`, not UAW's
   app-server protocol, and it's a deliberate mismatch, not an oversight: replicating a JSON-RPC session
   lifecycle for a single blocking call would be strictly more code and more failure surface for no
   behavioral gain here.
2. **`codex exec --help` (this machine, 0.153.4) has no `-q` and no `--json`-event-based way the work
   order assumed was necessary to find "the last assistant message"** — it has `-o`/
   `--output-last-message <FILE>`, which writes exactly that, directly, with no event-stream parsing
   needed. Used `-o`; kept `--json` anyway so a failure's stdout has some structure, but nothing parses it
   — a failure's message is just the last 2000 chars of stdout+stderr.
3. **`--skip-git-repo-check` is required, and wasn't in the work order's flag list.** `-C <dir>` points
   `codex exec` at a fresh empty `tempfile.TemporaryDirectory()` per call so it can't touch the repo; that
   directory is never a git repo, and `codex exec` refuses to run outside one without this flag.
4. **UAW's hardcoded Windows install root (`~/AppData/Local/OpenAI/Codex/bin`,
   `executable-discovery.ts`) isn't where Codex is installed on this machine** — `where codex` resolves to
   `~/AppData/Local/Programs/OpenAI/Codex/bin/codex.exe` (extra `Programs` segment, a different
   installer/version than whatever UAW's authors tested against). `_codex_executable()` checks PATH first
   (which is how discovery actually succeeds here and on any machine with a normal install), then both
   directories as a fallback.

Also checked and *not* overturned: `-a`/`--ask-for-approval` exists only on top-level interactive `codex`,
not on `codex exec` (confirmed via both `--help` texts) — consistent with `exec` being unattended by
design, so no approval flag is needed; `-s read-only` is the only safety knob used.

## Provider selection

`LLM_PROVIDER` = `openai` (default) | `codex`, validated in `llm.provider()` (unknown value raises
`ValueError` immediately rather than misrouting). Unset `LLM_PROVIDER` + unset `LLM_BASE_URL` still means
fixture mode, unchanged — that gate lives in `app.py`, not touched. `codex_cli` never uses
`LLM_BASE_URL`/`LLM_API_KEY`; it needs `LLM_MODEL` (`-m`, default `gpt-5.6-terra`) and optionally
`LLM_TIMEOUT` (shared with `openai_compatible`, default 120s) and `CODEX_BIN`.

**Embeddings never go through Codex** — `kb.embed()` is untouched and always dials an OpenAI-compatible
`/v1/embeddings`. So with `LLM_PROVIDER=codex`: `/extract` and `/ask`'s answer generation run on Codex,
but `/ask`'s retrieval (and `/index`) still need `LLM_BASE_URL` pointed at Ollama or a real
OpenAI-compatible host — without it, Ask stays unavailable in the same way it already is today (`app.py`'s
`/api/ask` and `/api/reports/{id}/index` both gate on `LLM_BASE_URL` before calling into `kb`, and that
gate is correct as-is: embeddings need it regardless of provider). Documented in `backend/README.md`.

## `app.py` suggestion (not applied — out of territory, v030 is mid-edit on it)

`POST /api/reports/{id}/extract` (`run_extract`) gates fixture-vs-real on `bool(os.getenv("LLM_BASE_URL"))`
alone. With `LLM_PROVIDER=codex` and no `LLM_BASE_URL` set at all (a fully Codex-only setup, no local
model, no OpenAI-compatible endpoint anywhere), that gate stays true forever and `/extract` never leaves
fixture mode — which is why the real run above needed a placeholder `LLM_BASE_URL` just to clear it.
Suggested fix: `if not (os.getenv("LLM_BASE_URL") or llm.provider() == "codex"):`. `/api/reports/{id}/index`
and `/api/ask` do **not** need the same fix — their gates are correct as written, since embeddings always
need `LLM_BASE_URL` regardless of provider. Separately, `/api/config`'s response (`model`/`embed_model`/
`base_url`/`llm`) could add a `provider` field (`llm.provider()`) so the frontend can tell `codex` and
`openai` apart instead of inferring it from `base_url`.

## Findings

- UAW's own Codex integration is JSON-RPC app-server, not `codex exec` — used `codex exec` anyway,
  deliberately, since it fits a single blocking prompt-in/text-out call and app-server doesn't buy
  anything here; see premise checks above.
- `-o`/`--output-last-message` makes `--json`-event parsing unnecessary for this use case; simpler and,
  since it's the CLI's own documented mechanism for "give me the final reply," probably more robust across
  Codex versions than parsing event shapes.
- `--skip-git-repo-check` is load-bearing (the sandboxed temp `-C` dir is never a git repo) and wasn't in
  the work order's flag list — would have been a 100%-reproducible failure on the very first real call
  without it.
- `codex exec` has no approval-policy flag at all (`-a` is interactive-`codex`-only); nothing to configure
  there beyond `-s read-only`.
- The real end-to-end result matched the local-model baseline on every field, byte for byte, on the first
  attempt — no second or third call was needed.
