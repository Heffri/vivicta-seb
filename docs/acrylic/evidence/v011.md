## Semantics (the one sentence to remember)

A schema check may carry `"null_as_zero": [<field key>, ...]`: **while a listed operand is null it
participates in that check as 0 — but only while at least one of the listed operands carries a real
value.** When every listed operand is null the sum proves nothing (`0 == total` would pass on
nothing), so the check stays `missing:` exactly as before. Checks without the key behave exactly as
before (`income_statement` has none). The flag is generic — any check, not just debt buckets.

## What changed (3 files, +34/−3)

- **`backend/schemas/debt_maturity.json`** (checks section only) — `maturity_sums_to_total` gains
  `"null_as_zero": ["due_within_1_year", "due_1_to_5_years", "due_after_5_years"]`. All three
  buckets are listed: any of them can be absent from a note (Ericsson has no >5y row; short-dated
  debt may have no >1y row). `total_debt` is deliberately **not** listed — without it the identity
  is meaningless and stays `missing: total_debt`.
- **`backend/pipeline/extract.py`** (`_check` only, the checks-evaluation block) — the eval
  namespace gets `0` for listed operands that are null, gated on at least one listed operand being
  real; the substituted `detail` renders each defaulted operand as `0 (<key> null)` so the UI shows
  which bucket was counted as 0. The `missing: <key>` detail format is unchanged (it is parsed
  elsewhere in `extract.py`), and the returned Check object keeps its `{name, passed, detail}` shape.
- **`backend/pipeline/test_confidence.py`** — the cases below.

Confidence consistency needed **no code change**: `score_field` grants `arith_ok` when no check
referencing the key failed, and a null-as-zero pass has `passed: true` — so a total verified across
its printed buckets earns `arith_ok` like any other pass.

## Findings (out of this lane's scope, reported not fixed)

**`label_known` can never fire for debt-maturity bucket rows.** `_clean_label` runs the quote
matcher's `normalize_ws`, which drops every space touching a digit ("Within 1 year" → `within1year`,
"1-5 years" → `1-5years`), while `_label_known` compares against the schema's synonyms verbatim
(`within 1 year`, `1-5 years`, …). Every debt_maturity bucket synonym contains a digit
(`income_statement` has none, which is why this never showed there), so a bucket row read perfectly
still misses `label_known` and caps at 0.9. Fix would be in `_label_known`/`_clean_label` territory
(clean the synonym the same way before comparing) — not the checks-evaluation block this lane was
scoped to.
