## The gap (why the currency/unit strip and the note-ref strip both miss it)

`_clean_label`'s currency strip is `,?\s*\(?\b(?:SEK|EUR|USD|NOK|DKK|ISK|GBP|CHF|kr)\b\)?` — it requires a
word boundary *after* the currency word. When a footnote marker sits glued to the word's tail with no space
("SEK1)"), the character right after "K" is a digit — both are `\w`, so there is no boundary there and the
regex never matches. The trailing note-ref strip a few lines down,
`(?:\s+[A-Z]{1,3}\.?\d{1,2}(?:[-–]\d{1,2})?,?)+$`, incidentally rescues some of these — a bare
`" SEK1"` with nothing after the digit *looks* exactly like a trailing note reference ("B1", "IE.3") and gets
swept up by that regex — but only by coincidence, and only for uppercase 1–3 letter tokens with nothing after
the digit. It cannot reach past a closing `)` (the required `$` anchor sits right after the digit run, and a
`)` after the digit breaks that), so the parenthesised shape ("SEK1)", "MSEK2)") falls through both regexes and
survives into the output; and it never fires for `kr` at all (lowercase, invisible to the `[A-Z]` class it
needs), so a superscript footnote on a lowercase unit (`kr¹`, which NFKC turns into the plain digit `kr1`
before the note-ref regex ever runs) is silently broken with **or** without a trailing paren.

## What changed (`_clean_label` only, +3/−1)

Two new statements, both ahead of the currency/unit strip as the work order specifies:

- A footnote **superscript** glued to a word (`⁰¹²³⁴⁵⁶⁷⁸⁹`) is stripped first, on the raw label before NFKC —
  NFKC's own normalization turns a superscript digit into a plain one, which would make it indistinguishable
  from a genuine digit already in the label; stripping it first, while it is still visibly a superscript, keeps
  the fix from depending on the note-ref regex's accidental uppercase-only rescue (this is what makes `kr¹`
  symmetric, not just the three-letter codes).
- A footnote **`\d{1,2})`** glued to a word (`(?<=[^\W\d_])\d{1,2}\)`) is stripped next, right before the
  currency/unit strip — this is the literal "SEK1)" shape. The lookbehind requires the character immediately
  before the digit to be a letter with *no* space in between, so it only fires on the glued shape; a
  space-separated `"Total 3)"` was never broken (step 6's existing trailing-punctuation strip already handled
  it) and is untouched by this change.

Both regexes anchor on "immediately after a letter, no gap" (`(?<=[^\W\d_])`, the same letter class `_page_rows`
already uses two functions up), which is exactly what keeps them from touching a label whose digits are its own
meaning: `_clean_label` calls `normalize_ws` a line later, which glues *every* space touching a digit closed
("Within 1 year" → `within1year`), so by the time the string reaches the end of the function a real digit-bearing
label and a footnote-glued one would look identical from the *right* side (trailing digits) — the requirement
that a `)` or an original superscript glyph be present is what tells them apart. Neither new statement is
anchored to the end of the string or requires a currency word nearby, so the same shape is caught wherever a
footnote sits in the label (SSAB's is at the very end; nothing in the corpus needed a mid-label case, but the
regexes don't special-case position).

`_row_label`, `_label_known`, `_statement_row`, the sum-repair call site and every other `_clean_label` caller
are untouched — they all inherit the fix automatically because they all clean through this one function.

## Findings (adjacent, not fixed — confirmed symmetric, not this lane's asymmetry)

The ticket's second example, `"MSEK2)"`, turns out to already be symmetric **before** this fix, for a different
reason than the one just closed: `_clean_label`'s currency regex only lists bare unit words (`SEK`, `EUR`, …,
`kr`) — `\bSEK\b` cannot match inside `MSEK` either (no boundary between "M" and "S"), footnote or not. So
`"Earnings per share, MSEK"` and `"Earnings per share, MSEK2)"` both keep `", msek"` in their cleaned form,
match each other, and neither needed today's fix. This is a *different*, pre-existing gap in the same function
(magnitude-prefixed units are never stripped at all, independent of footnotes) — no schema synonym contains a
magnitude-prefixed unit today (checked: `grep MSEK\|TSEK\|KSEK\|MEUR backend/schemas/*.json` hits only the
`value_convention` prose, no `synonyms` entry), so nothing in the corpus needs it, and it is out of this lane's
footnote-asymmetry scope. Flagging it since it sits one step away from the fix just made and follows the same
verbatim/normalized family v011b → v012 → v014 → this lane has been closing.
