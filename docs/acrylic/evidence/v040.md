## 1. Acast — column-bucket mechanism read the wrong table

**The bug (v037's diagnosis, reproduced offline against the real page text before touching any code):**
Acast's Note (real report, seed 2, p.65) prints two stacked calendar-year liquidity tables — this year's and
a prior-year comparative — each ending in a bare `"Total"` row. The current year's own Total row is glued to
trailing sidebar prose by `parse.py`'s line-based extraction (`"...19,250 approximation of fair value."` then
a lone `"2024"` line merges onto the same row), so `_row_amounts` called without a column count (inside
`_bucket_total_row`) sees only the trailing `"2024"` and the row never qualifies as a candidate (`len(amounts)
>= 2` fails). That leaves only the **prior year's** Total row as a candidate. Its 6-column count happens to
match a bucket header read from the **current** year's own header row (found first, scanning top-down over a
25-row lookback window that spans both tables) — a coincidence, not a real alignment — so the safety valve
(`len(amounts) == len(col_keys)`) passes on a genuinely wrong reading. Net effect: `due_within_1_year` (555370)
comes out **larger than** `total_debt` (45414) — a value no real maturity table can ever produce, since every
bucket is by definition part of the total.

**Confirmed red**, offline, against `origin/acrylic`'s own `extract.py`, using the real page-65 text (trimmed
to the load-bearing 5 lines, see the new test in `test_confidence.py`):
```
candidates (bare Total rows): [23]        # only the wrong-year row qualifies
matched (fiscal-year-nearby):  [23]       # its own header text contains "2025" too, coincidentally
col_keys: [due_within_1_year, due_1_to_5_years×4, total]   # 6 keys, from the *other* table's header
amounts:  [555370, 446990, 32692, 32404, 32404, 45414]
→ total_debt=45414, due_within_1_year=555370, due_1_to_5_years=544490   # due_within > total
```

**The fix** (`_fill_bucket_columns`, `backend/pipeline/extract.py`): after computing a candidate row's
per-column values, reject the whole row's column reading — not just the one field that looks wrong — if any
bucket value exceeds the row's own total by more than the schema check's own ±2 rounding tolerance. On
rejection: log a warning and leave every field at the model's own answer (`continue` to the next candidate,
never entering the per-field override loop). This is a general arithmetic sanity check (bucket ≤ total, same
row), not an Acast-specific branch — it would catch the same coincidental-column-count failure mode on any
report, regardless of cause.

**Column-header/numeric-column alignment, empty/dash columns:** the "-"/"—" nil convention (`_row_amounts`'s
`nil=` parameter, from v036) already keeps a dash's position in the row aligned with its header key — verified
this still holds for a dash **inside the total row's own bucket columns** (not just the instrument rows above
it, which is all the existing Cloetta test covers), both trailing (no >5y bucket) and mid-row (no 1-2y
bucket): two new offline assertions confirm the dash consumes exactly one column slot each time, so nothing
downstream of it shifts. Both were already green before this lane's change (they're a confirmation of
existing, correct behaviour, not a second fix) — kept as regression coverage since the risk ("空列/破折号列会
把索引偏") is exactly the kind of thing a *future* change to `_row_amounts`/`_bucket_header` could break
silently.

**Confirmed green**, same trimmed real text, after the fix: `total_debt=135382` (the model's own page-67
lease-liability read, untouched), `due_within_1_year`/`due_1_to_5_years`/`due_after_5_years` all stay null
(the model's own answer — it didn't find them), with warning `"total_debt: column reading of 'Total 555,370
... 45,414' rejected -- due_within_1_year 555370, due_1_to_5_years 544490 exceed its own total 45414; model's
own values kept"`.

## 2. Nelly Group — `_derived_value`'s neighbour-sum repair had no label guard when the row's own label was unrecognised

**The bug (v037's diagnosis, reproduced offline against the real page text):** Nelly's only debt is IFRS 16
lease liabilities (real report, seed 2, p.89): `"Kortfristiga 36,2 35,7"` (current) / `"Långfristiga 250,9
251,5"` (non-current). The model correctly reads `due_within_1_year = 36.2` from its own `"Kortfristiga"` row
— but the schema has no bare `"kortfristiga"` synonym (only the compound `"kortfristiga räntebärande
skulder"`, added in v037, which doesn't match a bare `"Kortfristiga"` row). `extract()`'s own_row test in the
`_derived_value` call site requires **three** things: the value printed in the quote, the row's label matching
a *known* synonym, and the model's raw_label matching the row's own label. The middle condition fails here,
so `own_row` comes out `False` and the caller passes `own_syns=None` — no restriction — into
`_derived_value`. With no restriction, its "value fails the check, sum of neighbouring rows might explain it"
fallback is free to combine **any** nearby rows that make the identity pass, and finds `"Kortfristiga 36,2
35,7"` + `"Långfristiga 250,9 251,5"` summing to `287.1` (the report's grand total) — overwriting a correct,
already-verified `36.2` with the current+non-current total, at a false `1.0` confidence.

**Confirmed red**, offline, against `origin/acrylic`'s own `extract.py`, using the real page-89 text (trimmed
to the 5 load-bearing lines): `due_within_1_year` goes from the model's correct `36.2` to `287.1`, warning
`"due_within_1_year: 36.2 fails maturity_sums_to_total; 'Kortfristiga 36,2 35,7 Långfristiga 250,9 251,5'
sums to 287.1 in every column, which passes"` — byte-identical to the corpus's own stored (buggy) extraction,
including the soft-hyphen character in the real quote.

**The fix** (the `own_row` computation in `extract()`, same file): drop the "label is a *known* synonym"
condition, keep the other two (value literally printed in the quote, and the model's own raw_label names the
exact row it quoted — not a heading above it). A row the model already read and labelled faithfully is its
own row whether or not the schema happens to recognise that label as a synonym yet; that's a schema-coverage
gap, not evidence the row is up for grabs. This targets exactly the shape of this bug (own row genuinely
correct, just unrecognised) without loosening the guard for the shape it must **not** touch: IPC's own
`own_row` is `False` for a different reason (the model's raw_label — "Cost of sales", a section heading — does
not match the row it quoted, "Production costs"), so IPC's neighbour-sum still runs unrestricted, unchanged.

**Confirmed green**, same trimmed real text: `due_within_1_year` stays at the model's own `36.2` (confidence
capped to 0.5 by the still-failing identity check, since the other two buckets are genuinely missing — a
correct, honest signal, not a masked one), zero warnings (no repair fires at all).
