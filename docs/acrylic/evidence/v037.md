## Two schema ideas tried, found unsafe by test, reverted (before ever committing)

Tried two more additions in the same batch, both **broke `pipeline.test_confidence`** and were
reverted before any commit — recorded because the *reason* they broke is a general, reusable
finding, not specific to this schema file:

1. **`due_within_1_year` synonym `"< 1 year"` / `due_after_5_years` synonym `"> 5 years"`** (the
   English digit-symbol forms, mirroring the schema's existing `"< 1 år"` / `"> 5 år"`). This
   directly regressed the Cloetta test in `test_confidence.py` — `due_1_to_5_years` fell back to
   `null`, and the other three fields lost the confidence lift v036 gave them. **Cause**: `extract.py`
   already has an internal `_BUCKET_BOUNDARY` regex patching exactly this English-symbol gap (v036's
   own comment: "these patch the one gap HANDOFF's examples use that the schema only states in
   Swedish"), consulted **only** inside the column-bucket mechanism's `_bucket_synonym_hits`. Adding
   the same phrase as a literal schema synonym makes `_bucket_synonym_hits` match it **twice** at the
   same text position (once via the literal-synonym loop, once via `_BUCKET_BOUNDARY`), inflating
   `_bucket_header`'s column-key count past the row's real column count — which trips the mechanism's
   own safety valve (`len(amounts) != len(col_keys)` → decline) and silently disables the whole
   Cloetta fix. **Lesson for the next lane touching this schema: don't add a schema synonym for any
   phrase `_BUCKET_BOUNDARY` (in `extract.py`) already covers — the two layers double-count.**
2. **`total_debt` synonym `"interest-bearing liabilities"` (bare, no "total" prefix) / Swedish
   `"räntebärande skulder"` (bare)**. This broke the Ework test — the *model's own* raw_label for
   `total_debt` in that fixture is the bare paraphrase `"Interest-bearing liabilities"` (not the
   row's real label), sourced from the **same row** as `due_1_to_5_years`/`due_after_5_years`. Once
   the bare phrase became a recognized `total_debt` synonym, the model's paraphrase started passing
   `_label_known`, which triggered the *twin-row* disambiguation in `extract()` ("two fields share a
   row; the one whose label is recognized owns it") and **dropped** the other two fields entirely.
   **Lesson: a short/generic synonym is riskier than a long compound one specifically because it's
   more likely to match a model's own loose paraphrase of some *other* field's row, not just the
   real row it was meant for** — reverted, not shipped. (`kortfristiga räntebärande skulder`, the one
   that *did* ship, is long/specific enough that this risk didn't materialize — verified by the same
   corpus scan.)

## Real bugs found, precisely diagnosed, **not fixed** (out of this lane's territory)

### Acast — a real correctness bug in the column-bucket mechanism (v036's territory, not touched)

Page 65 has two stacked liquidity tables (2025 and a 2024 comparative), both ending in a bare
`"Total"` row — a known, pymupdf-merged two-column layout: the 2025 section's own Total row
(`"Total 690,785 592,113 34,980 33,467 21,826 19,250 approximation of fair value. 2024"`) has trailing
sidebar prose glued onto it by `parse.py`'s line-based extraction, which makes `_row_amounts` (called
without a column count) see only the trailing `"2024"` as its amount — so `_bucket_total_row` doesn't
even consider it a candidate (`len(amounts) >= 2` fails). That leaves the **2024 (prior-year) row**
as the only candidate: `"Total 555,370 446,990 32,692 32,404 32,404 45,414"`. Ran the real functions
directly (`backend/pipeline/extract.py`, offline, no model call) against the real page text to
confirm exactly what happens:

```
candidates (bare Total/synonym rows): [23]   # only the 2024 (wrong-year) row qualifies
matched (fiscal-year-nearby filter):   [23]  # its own header ("...2025 2026 2027 2028 After 2028")
                                              # contains the literal string "2025", passing the
                                              # nearby-fiscal-year heuristic even though this is
                                              # the *prior*-year comparison block
col_keys: ['due_within_1_year', 'due_1_to_5_years', 'due_1_to_5_years', 'due_1_to_5_years',
           'due_1_to_5_years', 'total']       # 6 keys
amounts (ncols=6): [555370, 446990, 32692, 32404, 32404, 45414]
```

Root cause of the 6 keys: `_YEAR_TAIL` (the regex that recognizes a calendar-year table's closing
"later/thereafter" column) only matches `later|thereafter|senare|övriga år` — **not** the very common
English `"After <year>"` phrasing this report uses (`"After 2028"`). Because the tail marker isn't
recognized, `_bucket_year_hits` classifies the row's *second* occurrence of "2028" (the one inside
"After 2028") as a fourth ordinary forward year instead of the after-5-years tail, producing one
extra `due_1_to_5_years` key that happens to make the header's key count (6) match the row's raw
amount count (6, since this row also carries the leaked "2024" merge artifact as index confusion) —
passing the safety valve on a table that is (a) the wrong year and (b) misread besides. Net effect:
`total_debt` = the "after" column of the *wrong year's* table (45414), `due_within_1_year` = the
carrying-amount column misread as a bucket (555370, larger than total_debt itself), `due_1_to_5_years`
= a nonsense sum (544490). This is a genuine, reproducible defect in the already-merged v036
mechanism — not a company-specific one-off (the "After `<year>`" tail phrasing and pymupdf's
two-column line-merging are both general shapes) — but per this work order's explicit boundary
("不要在本单里改 extract.py 的列向机制，另开单"), **not touched here**. Flagging with the exact
repro above so the next lane doesn't have to re-derive it.

### Nelly Group — a real bug in `_derived_value`'s neighbour-row search, also not this lane's territory

Nelly's only debt is IFRS 16 lease liabilities (`"Leasingskulder som ingår i rapporten över finansiell
ställning"`, p.89): `"Kortfristiga 36,2 35,7"` / `"Långfristiga 250,9 251,5"`. The model correctly
read `due_within_1_year = 36.2` (the `Kortfristiga`/current row) — but the schema has no
`due_within_1_year` synonym for `"kortfristiga"` (bare; only the compound
`"kortfristiga räntebärande skulder"` this lane added, which doesn't match a bare `"Kortfristiga"`
row), so `own_row` in `_derived_value` comes back `False` and its `own_syns` guard never engages.
With no guard, `_derived_value`'s "value is not printed / sum of neighbour rows" fallback is free to
combine **any** nearby rows that make the failing identity check pass — and it finds
`"Kortfristiga 36,2 35,7"` + `"Långfristiga 250,9 251,5"` summing to `287.1` (the report's total),
overwriting the model's already-correct `36.2` with `287.1` (current **and** non-current combined) at
a false `1.0` confidence, instead of recognizing that the *actually* missing operand is
`due_1_to_5_years` (which should get `250.9`, the `Långfristiga` row, left null instead). This is a
correctness bug in a shared `extract.py` repair (`_derived_value`), the same mechanism income_statement
also depends on — out of this lane's "don't touch the column mechanism" boundary in spirit (it's the
row-derivation counterpart of it), and risky to patch without a full income_statement regression pass
this lane's budget doesn't cover. Flagged, not touched.

## The "coarser or two-basis bucket table" pattern — this seed's dominant failure mode (6/10)

Not the column-as-columns gap v035/v036 already own (only Acast/Cloetta-shape this seed), and not a
locator keyword gap either. Six of ten companies (Alligo, BICO, Humana, Boozt, Acast, Coor) print a
maturity table whose own bucket boundaries and/or basis conflict with the schema's ask, confirmed by
hand against the real page text in each case (full excerpts in this dir's `dump_*.txt`):

- **Alligo** (p.141): the *only* bucket breakdown is `Inom ett år / Inom fem år / Efter fem år`
  (spelled-out Swedish numbers, not "1"/"5" — a locator-relevant gap, out of scope, not touched) on
  an **undiscounted future-cashflow basis** (buckets sum to 3,841, not the 3,629 carrying total_debt);
  the only carrying-basis split available anywhere in the report is current/non-current
  (473 / 3,156, p.143) — no carrying-basis split finer than that exists to extract. Buckets 2 and 3
  are unfillable without inventing a split the report never prints.
- **BICO** (p.86): `<1 year | 2 years | 3 years | 4 years | >4 years` (undiscounted), a
  year-by-year grid whose own top boundary (4 years) doesn't align with the schema's 5-year line —
  the model saw this table and the carrying-amount note (p.113-114) both, in both attempts, and
  answered nothing rather than guess. Correct behavior per "prefer null over a guess," just not a
  fix.
- **Humana** (p.149): `<3 months | 3-12 months | 1-5 years | >5 years` — undiscounted (includes
  accrued interest and trade payables in its own Total), while the clean carrying current/non-current
  split (p.148, Note C19) reconciles exactly to `total_debt` but isn't in the candidate window.
- **Boozt** (p.121): same shape, and here the undiscounted buckets (26+78=104 / 273 / 63) *do*
  round-trip to the carrying total (441, ±1) — genuinely fixable in principle, but the clean carrying
  split lives on p.108 (5th-ranked candidate, never reached even after the 2-page-to-4-page widen).
- **Coor** (p.159): `Within 1 year | Between 1-2 | 2-3 | 3-4 | 4-5 years | More than 5 years` — a
  4-way split of the 1-5y range the model didn't attempt even after this lane's wording generalization
  (re-verified clean, no concurrency: unchanged).
- **AcadeMedia** (p.87): `1-12 months | 2-5 years | 6-10 years | >10 years` on a nominal/undiscounted
  basis that, hand-checked row by row, doesn't cleanly reconcile even *within itself* (e.g. one row's
  four bucket columns sum to more than its own printed nominal total) — looks like a `parse.py`
  two-column-layout artifact (HANDOFF's own known gap: "plain `get_text()` loses table structure"),
  not a keyword/schema problem.

All six are variants of HANDOFF's own two anticipated risks ("bucket boundaries vary" / "two tables
on one page") landing in shapes v008/v017/v035 hadn't specifically catalogued yet (spelled-out
numbers, month-based near-term splits, a 4-year top boundary, a 4-way 1-5y split, undiscounted totals
that include non-debt rows). None of them is a locator keyword miss or a missing label in the sense
the earlier lanes fixed — the schema-level wording generalization (commit 3 above) is the one lever
available without touching `locate.py` or the column mechanism, and it demonstrably didn't move any
of these six (verified, not just assumed — see the Coor re-check and the AcadeMedia ablation below).

## A methodology finding: single-call before/after isn't proof, at this model

Re-ran the same 10 companies (same schema, same pages, same candidate window) a second time to
verify the 3 commits above. Two results moved in ways the commits don't explain: Humana's `total_debt`
quote went from unverified (\@0.15) to verified (\@0.5) — a field none of the 3 commits touch — and
Storytel's `due_within_1_year` quote went from verified (\@0.9) to unverified (\@0.25) — also
untouched by any commit. Ran AcadeMedia a further two times, once with the wording commit reverted
(`git show <parent>:...json > schemas/debt_maturity.json`, tested, then `git checkout --` to restore —
no commit made for the reverted state): **null in both**, proving the wording change isn't the cause
of AcadeMedia's own before/after swing (\@0.85 → null) either — it's run-to-run Codex variance,
present regardless of this lane's edits. **A single before/after pair against this model is not
reliable evidence of a fix or a regression**; worth a repeated-trial (n≥3, majority vote) methodology
for the next hardening round if the group wants to trust small confidence deltas.
