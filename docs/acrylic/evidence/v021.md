# v021 — Extract view: drag/drop several PDFs at once (evidence)

## Premise check

The work order's two premises both held: the `run()` queue already treats the upload as one item among
many (directory picks + library selections + upload, sequential, shared `(i/n)` progress and `tried`
handling), and `Dropzone.tsx` was genuinely single-file (`file: File | null`, `dataTransfer.files[0]`,
`accept`d but not `multiple`). No premise-overturned report needed — implemented the work order as written.

## What changed

Confined to the `file → files[]` line, as scoped:

- `frontend/src/components/UploadView.tsx`
  - `const [file, setFile] = useState<File | null>(null)` → `const [files, setFiles] = useState<File[]>([])`.
  - `pickFile(f: File | undefined)` → `pickFiles(incoming: File[])`: partitions the incoming batch into
    accepted/rejected by `isPdf`, sets one error line naming only the rejected filenames (accepted PDFs
    still go through), then appends the accepted ones to `files` deduped by `name:size` against what's
    already staged. Cancelling the file picker (`incoming.length === 0`) is a no-op, same as the old `!f`
    guard.
  - New `removeFile(target: File)` — filters `files` by reference (safe: dedup on insert guarantees at most
    one array element per `name:size`, and each list row closes over its own `File`).
  - `count` now adds `files.length` instead of `file ? 1 : 0`.
  - `run()`'s queue: the upload segment maps every entry in `files` to its own `uploadReport(f)` item, in
    drop/pick order. The old `item.label === file?.name` check (which flagged "this queue item is the
    upload" back when there could only be one) doesn't generalize to an array of filenames without
    reintroducing a name-collision risk, so it's replaced with an explicit `fromUpload: true` field on those
    queue entries (mirrors the existing optional `prep` field's role of marking directory picks) — same
    semantics, works for N files. Everything else in `run()` — ordering, `(i/n)`, `tried`, the all-failed
    block, `onDone` — untouched.
- `frontend/src/components/upload/Dropzone.tsx`
  - `file` prop → `files: File[]`; `onPick(file: File | undefined)` → `onPick(files: File[])`; new
    `onRemove(file: File)`.
  - `<input>` gets `multiple`; `onChange`/`onDrop` now collect the whole `FileList`
    (`Array.from(e.target.files ?? [])` / `Array.from(e.dataTransfer.files)`) instead of indexing `[0]`, and
    the input's `value` is reset after each pick so re-selecting the same file after removing it still fires
    `onChange`.
  - Empty-state copy is untouched per the work order. The staged-state copy changes from "`<name>` · click or
    drop to replace" (replace semantics) to "`N` file(s) selected / click or drop to add more" (append
    semantics), since dropping again no longer replaces.
  - New file list below the drop label: one row per file (name, `fmtSize`, a `×` remove button —
    same visual recipe as the `Selected:` chips in `CompanySearch.tsx`), capped at `max-h-40 overflow-y-auto`
    so a long queue doesn't blow out the face's height.

Nothing else touched: `types.ts` (`Result` shape is unchanged — N uploads just produce N `Result` entries,
same as N library selections already did), `api.ts`, `App.tsx`'s `onDone`/tab routing, `Face.tsx`,
`CachedReports.tsx`, `CompanySearch.tsx`, backend, `data/`. Zero new dependencies.

## Red → green (Playwright, shared `vivicta-shared/tools`, local Edge)

Two synthetic 70-page PDFs (`sample_report_a.pdf` 29 kB, `sample_report_b.pdf` 32 kB — different filler
text so their bytes and sizes differ), page 64 carries the fixture's income-statement quotes verbatim, page
65 carries the EPS quote — built with PyMuPDF per `common.md`. Plus one `not_a_report.txt`. Scripts live in
`uaw-lanes/vivicta-shared/tools/v021_red_check.mjs` and `v021_green_flow.mjs` (ad hoc, not committed —
matches how v002 exercised its flow).

**Red** (`v021_red_check.mjs`, run against this same worktree with the two changed files reverted to
`HEAD` via `git checkout HEAD -- <path>`, so the running dev server briefly served the pre-fix single-file
`Dropzone`): `#pdf` had no `multiple` attribute, and `page.setInputFiles('#pdf', [A, B])` failed outright —
`Error: Non-multiple file input can only accept single file`. That's the gap the work order describes, not
a copy of the fix's own expectations.

**Green** (`v021_green_flow.mjs`, same two files restored):

1. `setInputFiles('#pdf', [A, B])` → Dropzone shows "2 files selected", lists `sample_report_a.pdf` and
   `sample_report_b.pdf` with sizes; button reads exactly **"Extract 2 reports"**. Click → lands on
   **Compare**, header "2 of 2 reports extracted", table has 3 `<th>` (Field + 2 report columns). ✅
2. `setInputFiles('#pdf', [A])` → button reads plain **"Extract"** (no count). Click → does **not** land on
   Compare; `h1` is the extracted company name ("Nordic Industrials AB (fictional fixture)", i.e. the
   Results view). ✅
3. `setInputFiles('#pdf', [not_a_report.txt, sample_report_b.pdf])` (mixed drop) → Dropzone ends up with
   **1 file selected** (`sample_report_b.pdf`, the `.txt` never enters the list); the error banner reads
   exactly `Only PDF files are supported: not_a_report.txt` — names only the rejected file, doesn't mention
   the accepted PDF. ✅

All three assertions ran as real `assert()`s in the script (not printed-and-eyeballed), full output: 12/12
checks passed, `ALL GREEN CHECKS PASSED`.

Both Compare columns show identical values/labels ("Nordic Industrials AB (fictional fixture)") — that's
the fixture backend returning the same canned JSON for every `/extract` call regardless of which PDF was
uploaded (`backend/app.py:213`, pre-existing, same for a single upload), not a bug in the queue.

## Not done / findings (out of scope, for the supervisor)

- Two uploaded files with the *same* name but different content (dedup key is `name:size`, not `name`
  alone) would carry the same `label` into `results`/`tried` — pre-existing ambiguity (library/directory
  items already share this risk if two entries had the same display name); not something this work order
  asked to fix, and the `count`/queue mechanics don't depend on labels being unique.
- No "clear all" affordance next to the per-file `×` — not in the work order's spec (name+size dedup,
  per-file remove, append-on-redrop); adding one would be scope creep for a one-line-of-logic task.
