## What changed (25 +/7 −, two files)

- **`App.tsx`** — `<SettingsView onConfigChange={setConfig} />`: the view hands the post-save
  config back and App's `setConfig` updates it, so `StatusBar` re-renders. Nothing else touched.
- **`SettingsView.tsx`** — `SettingsView`/`DesktopSettings` take an optional
  `onConfigChange?: (config: Config) => void`. In `save()`'s success branch the same payload the
  "Running now" strip already gets is forwarded up: `res.config` when the desktop shell resolved it,
  else a fresh `/api/config` fetch. For the else branch `refreshStatus()` now returns the config it
  fetched (or `null` on failure); the mount and save-failure callers are behaviorally unchanged.
- Failure path untouched, and now proven: a failed save refreshes only the strip (its pre-existing
  behavior) and must not move App's footer.

The trigger is real: `desktop/main.js`'s `applySettings()` kills and respawns the backend and
resolves `set()` from the restarted process's `/api/config` — so the forwarded payload is the
post-restart truth, and the no-`config` shape (`{ ok: true, port }`, its line-level fallback when
the nicety fetch throws) is genuinely reachable, hence both branches covered below.

### Rework note (why the first submission's after-shot was wrong)

The supervisor rightly flagged the first `statusbar-after-save.png`: strip codex/BM25, footer still
`fixture · bge-m3`. Not a timing window and not a dead fix — an evidence-pipeline mistake: the red
observation above was produced by re-running the same config-mode driver against
`git checkout origin/acrylic --` baseline files, and that run silently **overwrote both
screenshots** with the red state (on baseline code the strip still updates — via `res.config` —
while the footer stays stale). The green after-shot I had visually verified was thus replaced
before commit, and the commit went in unviewed. Re-run under the hardened ordering (assert footer
→ screenshot → re-read footer, all logged PASS: `footer asserted BEFORE the screenshot
(gpt-5.6-terra · retrieval BM25)` / `footer re-read AFTER the screenshot (…)`) produced the
committed pair; both files re-viewed at commit time.

### Timing between Save and the footer update (rework question 2)

- `res.config` present (the normal desktop path): `setStatus(res.config)` and
  `onConfigChange?.(res.config)` run synchronously in the same click handler; React commits them
  together — strip and footer change in the same render. No window.
- `res.config` absent (`{ ok: true, port }` fallback): one async `/api/config` fetch feeds both —
  the strip's new value and the `onConfigChange` forward happen inside the same `refreshStatus()`
  resolution, so the two surfaces move together when it lands. The only transient is *both*
  surfaces together showing pre-save values until that fetch resolves (tens of ms locally); the
  strip never leads the footer. Verified in green run 2; screenshots are taken only after the
  explicit footer assertion regardless.
- Failure path: the footer intentionally never moves (proved by the failure run above).
