## Same judgment as MaturityChart, reused not re-decided

The work order's central constraint: "same bucket judgment as the Results maturity chart." Two
places this could have drifted, both closed by reuse instead of a second implementation:

1. **Chart-vs-nothing.** `CompareView` computes `showMaturityRow = ok > 0 &&
   results.every(r => !r.extraction || isMaturitySection(r.extraction.fields))` — the exported
   `isMaturitySection`, not a re-derived field-key check. One non-bucket column among several
   bucket-shaped ones is enough to suppress the row entirely (`every`, not `some`).
2. **Sum-vs-total pass/fail.** `MaturityBar` looks up `extraction.checks.find(c => c.name ===
   IDENTITY_CHECK)` — the same `IDENTITY_CHECK = 'maturity_sums_to_total'` constant
   MaturityChart's header indicator uses — and takes `check.passed` as the authoritative verdict,
   exactly like MaturityChart's "never recomputed client-side" rule (v009). Only the *geometry* of
   the danger sliver (how wide) is computed locally, from the same three numbers already needed to
   size the three real segments — that's arithmetic for a pixel width, not a second judgment. If
   the check is absent (e.g. a hypothetical bucket-shaped section without this identity check), the
   bar renders with no danger indicator at all, mirroring MaturityChart's "check missing → indicator
   omitted, card still renders."

## The bar itself

- **Sizing.** Denominator = `max(total_debt, sum of the three buckets)`, so segments always read
  as "share of the bigger of what was stated vs. what was found." When they agree (the normal
  case), the three segments fill the bar exactly. A null bucket draws no segment (0-width) but
  still occupies a **6px minimum hit slot** (`min-w-1.5`, transparent) so it stays independently
  hoverable/focusable with its own "—" tooltip — never merged into a neighbor.
- **Mismatch (bucket sum ≠ total).** Backend check fails + a real shortfall (`total > sum`, above a
  2-unit tolerance matching the schema's own `±2 rounding`) → a **danger-colored sliver** appended
  at the right, sized to the shortfall, closing the bar back out to 100%. Backend check fails but
  there's *no* room for a sliver (sum ≥ total, or total missing) → **no sliver is drawn; the whole
  bar gets a `ring-1 ring-danger` outline instead** — the work order's explicit fallback for the
  case a sliver can't represent. Verified with a second, deliberately-broken fixture
  (`due_1_to_5_years` cut from 29 165 to 20 000, `due_after_5_years` set to an explicit `0`):
  `zoom-mismatch-dark.png` / `mismatch-hover-dark.png`. That same shot also shows the other null-vs-
  zero distinction: `due_after_5_years = 0` (explicit) draws a tiny colored nub; `null` (the primary
  fixture) draws nothing — same rule MaturityChart already uses for its own baseline bars.
- **Color — dataviz skill, "ordinal" job.** Bucket order carries meaning (swapping it would change
  what the chart says), so this is one hue in monotone steps, not categorical colors:
  `color-mix(in srgb, var(--ring) {50,28,12}%, var(--primary))`, near-term most emphasized. The top
  step (50%) sits close to MaturityChart's own hover/selected mix (45%) so the two views read as
  the same accent language. Danger sliver: `color-mix(in srgb, var(--danger) 65%, transparent)`.
  Both tones screenshot-verified (`zoom-dark.png` / `zoom-light.png`) — the ramp stays legible at
  both ends in both tones; no new hex values, only `--primary`/`--ring`/`--danger`, all pre-existing
  tokens.
- **Marks.** Each segment rounds *itself* (`rounded-full`) rather than the track clipping
  (`overflow-hidden`) — the first build had the track clip, which silently ate the hover tooltip
  (an absolutely-positioned child can't escape an `overflow-hidden` ancestor); switching to
  per-segment rounding fixed it and, incidentally, reads closer to the "2px surface gap between
  stacked segments" mark spec than one hard-edged clipped block would have. 2px gaps
  throughout (`gap-0.5`).
- **Hover/focus.** Per-segment tooltip (own small `glass`-styled popup, matching the existing
  floating-popup recipe from `ui/select.tsx`'s dropdown — `text-popover-foreground ring-1
  ring-foreground/10` — rather than inventing a new surface), shown on `group-hover` **and**
  `group-focus-visible`; each segment is independently `tabIndex=0`. Verified real keyboard-focus
  parity (not just `.focus()`, which Chromium doesn't always treat as focus-visible): primed
  keyboard modality with a `Tab` press, then focused a segment and asserted
  `el.matches(':focus-visible')` before screenshotting — `hover-focus-dark.png` shows the focus
  ring and the tooltip together. No native `title` used here (unlike MaturityChart/CompareView's
  confidence badges) because `title` never fires on focus, and the work order asks for hover *and*
  focus.
- **Total.** Small text line under the bar, `fmtValue(total) + unit`, or "—" if `total_debt` itself
  is null/missing.
- **≤900 width.** No new behavior needed — the bar lives in a normal table cell
  (`max-w-48` cap on the bar itself), so the table's pre-existing horizontal scroll carries it
  exactly like every other column.

## Suggestions for the group

- **`isMaturitySection`/`bucketSlots`/`numeric` now have two call sites** (Results, Compare). If a
  third bucket-shaped view ever appears, lifting the bucket rule into the schema itself (already
  suggested in v009's evidence) pays off twice as much.
- Same contract gap v009 flagged still stands: `Check.detail` is backend-computed prose, not
  structured data, so a UI wanting the *magnitude* of a failed identity check (not just pass/fail)
  has no choice but to recompute it from the raw field values, as `MaturityBar` does here. Exposing
  the check's operands (or at least its residual) in the API would remove that duplication.
