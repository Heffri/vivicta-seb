## The blocker, read precisely (the work order's own open question)

Not "carrying only activates alongside undiscounted" — the real gate, inside `_bucket_header`'s first per-row
loop (pre-v085): a `total:carrying`/`_ignore` hit survives only on a row that **also carries a real bucket
hit of its own on that same line**; the filter runs and strips the hit before `has_carry` is ever computed, so
a carrying/ignore phrase on a bucket-less line never gets a second chance. Instalco p.128's own liquidity note
wraps its column header across **three** lines, not one:

```
Total contractual cash flows
31/12/2025 Carrying amount receivables/ payables
Within 6 months 6–12 months 1–5 years Later than 5 years
Liabilities to credit institutions – – 3,209 – 3,209 3,122
```

The first two lines name no bucket at all — both hits are stripped — leaving only the third line's four bucket
words in the header, one short of the row's six printed amounts (v082 Finding 2, v083's own confirmation:
"adding the missing fourth word... changes nothing"). Declined, silently, no warning.

## The fix

`_bucket_header` now walks backward from the header's own last bucket-naming line through an **unbroken run**
of lines that each carry a recognised `total:carrying`/`_ignore` hit of their own, stopping at the first line
with neither a bucket word nor a carrying/ignore word (Instalco: the walk crosses both header lines above, then
stops at "Current Non-current", which has neither). Two guards, both load-bearing, confirmed by making each
one fail on purpose against the real corpus before keeping it:

1. **Admitted only when no bucket-naming line in the window already claims a carrying hit on its own** — the
   v076 same-line mechanism still runs first and unchanged; this fallback only fires when that mechanism finds
   nothing, so it can never double-count a hit v076's own read already found.
2. **Admitted only when nothing between the header's own last bucket-naming line and the candidate row itself
   prints its own amounts.** Instalco's own page prints a second bare-`Total` row nine lines below the real
   debt row — the whole table's grand total (debt + Accounts payable + Contingent consideration, wrong scope)
   — separated from the header by the four instrument rows in between. Without this guard, the newly-6-column
   header also fits that row's own six amounts, and it silently outranks the correct one (first real run,
   caught here: total_debt corrupted 3122 → 4802 before this guard was added).

Both guards were necessary, not precautionary — dropping either one moved a value on the real corpus:

- Without guard 2: seed8-kb/instalco_2025 itself regresses (`total_debt` 3122 → 4802, the grand-total row).
- Without the *contiguous-run* stop (an earlier, broader draft admitted a carrying/ignore hit from **anywhere**
  bucket-less in the whole 25-row window, not just an unbroken run touching the header): seed5-kb/ework_2025
  regresses (`total_debt` 156410 → 33525, `due_within_1_year` null → 10562, reading the *other* row, Lease
  liabilities, as the table's own total) and seed5-kb/ependion_2025 regresses (all three filled fields →
  null) — both real pages carry unrelated prose sentences containing "carrying amount" several lines above
  their own real bucket header (Ework: "...reflected in the carrying amount in the statement of financial
  position..."; Ependion: two "...correspond[s] to carrying amount..." sentences), which a whole-window scan
  wrongly treats as a second header tier. The contiguous-run stop excludes both: each page's own bucket-naming
  line's immediate predecessor names neither a bucket nor a carrying/ignore word, so the run never reaches the
  prose. Caught by the mandated full-corpus replay, not by inspection — recorded here as the reason the fix
  looks the way it does, not a simpler window-wide version.

`_bucket_header` now reads the row's own header correctly — confirmed directly:

```
_bucket_header(...) == ["due_within_1_year", "due_within_1_year", "due_1_to_5_years", "due_after_5_years", "_ignore", "total"]
```

six keys, matching the row's own six printed amounts (`–, –, 3209, –, 3209, 3122`) exactly. But the fill still
does not land, end to end — a **separate, out-of-territory** valve in `_fill_bucket_columns` (`extract.py`
line 1353, `over = {k: v for k, v in derived.items() if ... v > total_val + 2}`) rejects the whole reading:

```
total_debt: column reading of 'Liabilities to credit institutions – – 3,209 – 3,209 3,122' rejected --
due_1_to_5_years 3209 exceeds its own total 3122; model's own values kept
```

This is not a misalignment — it is the same undiscounted-vs-carrying gap v076's own Ework table has (this
file's header: "Total contractual cash flows" is the **undiscounted** sum, "Carrying amount" is the
**discounted** total; with future interest over the 1–5-year horizon, an individual undiscounted bucket can
legitimately exceed the discounted grand total). Ework's own case never tripped this valve only because its
own due_within_1_year (a *short*-horizon bucket, negligible discounting) came in one unit *under* its own
carrying total (156,409 vs 156,410); Instalco's due_1_to_5_years is a longer-horizon bucket where the discount
effect is large enough (3,209 vs 3,122, 87 apart) to cross the valve's own `+2` tolerance. Fixing this would
mean teaching `_fill_bucket_columns`'s `over` valve about the undiscounted/carrying split — a different
function, outside this lane's territory (`只限 _bucket_header 里 carrying 列的准入条件`), not attempted.
**Premise refined, not overturned**: the work order's own named blocker (the carrying admission condition) was
real and is now fixed, correctly and non-speculatively (confirmed against the header text, not assumed); a
second, previously-invisible blocker sat one layer further down and is named here for whoever picks it up
next, with the exact figures and line number needed to start there directly.
