## (a) Proact IT Group — an exactly-closing value must outrank a column-position guess

**Bug** (`docs/acrylic/evidence/v063.md` gap 2): Note 24's date-per-instrument maturity table lets the
model correctly sum `216,360` (16 Jul 2026) + `96,098` (2026) = `312,458` for `due_within_1_year`,
closing `maturity_sums_to_total` against the already-read `total_debt` (478,611) and
`due_1_to_5_years` (166,153) exactly. The same page also prints "Group | Parent company" twice (Note
24's *other*, unrelated sub-table), so `_segment_column`'s own Group/Parent branch fires and picks
column 1 of the page's 3-column year run; the single-instrument row that is `due_within_1_year`'s own
quote reads as `0` in that column, and `extract()`'s segment-column correction threw the correct
312,458 away for it — check failed.

**Fix**: before that correction overwrites a field's value, a new `_identity_closes(key, value,
snapshot, defaults, schema)` checks every identity check in the schema referencing `key`: if at least
two *other* operands already have real (non-null, non-boolean) values in a **pre-loop snapshot** of the
page's fields (frozen before this pass's own corrections start, so one field's guessed overwrite can
never prop up another's), and `_check` (unmodified, its own ±2 tolerance) says the identity holds with
the current value substituted in, the value is kept. Only one other real operand (a lone total, with
sibling buckets defaulting through `null_as_zero`) does not count — closing "against itself" proves
nothing, the supervisor's own named failure mode for this guard. The snapshot is taken once per page,
so the guard cannot pyramid a bad correction on the same page into a bad "confirmation" for a later
field in the same pass.

Kept values also get `"identity_kept"` **and** `"value_derived"` evidence (`WEIGHTS["identity_kept"] =
0.0`, a marker only, same shape as the existing `"identity_all_columns"` marker). The `value_derived`
tag turned out load-bearing, not decorative: a *separate*, pre-existing, unrelated guard later in
`extract()` (the "Sectra" rule — a non-null value that is not literally printed anywhere nearby and
cannot be re-derived is dropped as "computed, not read") would otherwise undo the keep a few lines
later, since 312,458 is a sum the model computed from two date-tagged rows and is not itself printed as
one token anywhere on the page. Tagging it exactly like every other identity-proven, not-literally-
printed value in this file (`_derived_value`/`_between_rows`'s own sums) is the same standing those
mechanisms already have, not a new concept — full confidence (1.0) instead of stalling. **This one
interaction was not in the work order's own text** — flagged here per "the supervisor's observation can
be overturned," but it did not need a ruling: the fix (one word: also tag `value_derived`) stayed
entirely inside this lane's one admission condition, so it is reported, not blocked on.

## (b) Net Insight — bucket columns never write a Total*/prior-year row without a total column

**Bug** (`docs/acrylic/evidence/v063.md` gap 7): Note 21's real maturity table (`<1 year` / `1-5 yeas`
[report's own typo] / `>5 years` / `Total`) sits right after an unrelated "financial instruments by
category" table whose own row also happens to be bare-labelled `Total`. `_fill_bucket_columns` finds
the maturity table's own `"Total 81,489 57,647"` row (2025's total, then 2024's, side by side) a
plausible bucket-column candidate: its header (the three bucket rows above it) carries only two
recognised bucket keys — the `"1-5 yeas"` typo keeps the third out — and **no "total" key at all**, so
`derived` never gets a `total_debt` entry and the pre-existing `over` valve (which needs a `total_val`
to compare against) never runs. Nothing stops the write: `81,489` (2025's own total) overwrites the
model's already-correct `due_within_1_year=50,379`, `57,647` (2024's total) overwrites the model's
already-correct `due_after_5_years=0`.

**Fix**, two independent valves, both gated to reject-and-`continue` (skip this row, "let the page's
own model answer or another candidate stand" — never a `return`, so a page's other candidate rows are
still tried):

1. If the selected row's own label is itself a Total\*/Summa\* variant (the same test
   `_bucket_total_row` already uses to classify a row as a bare-total hit: `_label_known(row_label,
   total_sf)` or `_clean_label(row_label) in ("total", "totalt", "summa")`) **and** `"total"` is not
   among the header's own parsed keys (so the row's own stated total can never be cross-checked), the
   write is rejected.
2. `_bucket_row_prior_year(rows, idx, fiscal_year)` (new, additive, mirrors `_row_year_column`'s own
   "nearest run above wins" walk but asks a narrower question): if the row's own year — read inline, or
   from the nearest `_year_run` above it — names the fiscal year's predecessor and not the fiscal year
   itself, the row is rejected even when it does carry its own recognised total column (so valve 1 alone
   would have missed it). No seed-6 company happened to hit this exact shape; covered by a synthetic
   case (below) since the work order named it as a required, independent second condition.

Net Insight's real bug is caught by valve 1 (its Total row's own header has no total key at all); valve
2 does not fire on it (the nearest year run above the row is `"2025 2024"`, which names the fiscal year,
not only its predecessor) — the two valves are independently necessary, not redundant on this company.
