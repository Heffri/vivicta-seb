(re-fetched at delivery: still the tip — no merge needed). Zero model calls (fixture backend and

`frontend/src/components/SettingsView.tsx`, `backend/app.py` (**only** one added `/api/config` key),
`docs/acrylic/README.md`, this file + screenshots. Not touched: ResultsView/KbView/

## What landed

- **`desktop/settings.js`** — `DEFAULTS.mergeRuns: 'off'`; `sanitize` accepts exactly
  `off|union|majority` (anything else — a typo, an older config — falls back to `off`, the same
  "a typo can never silently turn the second run on" rule as the backend's `merge.mode()`); every
  **non-fixture** provider branch (`ollama`, `openai`, `codex`, `claude`) adds
  `EXTRACT_MERGE_RUNS: clean.mergeRuns` — model-independent like `DEBT_BASIS` (v089), so Ollama
  passes it through too, unlike `EXTRACT_TWO_PASS`. Fixture stays `{}` (demo mode makes no model
  call either way). Cost note lives in the code comment next to the default: union means every
  extraction costs two model calls.
- **`backend/app.py` `/api/config`** — one new key: `"merge_runs": merge.mode()` (module imported
  locally in the route, the same shape as `run_extract`'s v133 import; the route never reaches the
  second-run path). This is the whole backend change.
- **`frontend/src/components/SettingsView.tsx`** — one new `MergeRunsControl` rendered **once** in
  `DesktopSettings`, as its own small card directly under the provider cards (the model-independent
  basis select repeats inside every card; this sits beside that block as one panel-level control,
  since the choice has nothing to do with which provider is picked). Same `Segmented` primitive as
  Results' PDF/Image toggle, options Off / Union / Majority, plus the work order's explanation
  line ("Union: run twice, keep the better-evidenced field. Majority: also count the saved
  extraction; skips the second run when the first matches it. Doubles model calls."). The status
  strip gains a `merge <off|union|majority>` segment sourced from `/api/config`'s `merge_runs` —
  the basis treatment (v089), not the two-pass one: because the backend echoes the live value,
  this segment renders in the plain-browser mirror too, and it always shows what the backend
  would actually run with rather than the in-progress form value.
- **Type support (one line each, flagged): `frontend/src/main.tsx`'s `DesktopConfig` gains the
  required `mergeRuns` field and `frontend/src/api.ts`'s `Config` gains the optional `merge_runs`
  field** (optional exactly like `maturity_basis`, so e2e route mocks and older backends without
  the key stay valid — verified: the whole e2e suite passes unmodified). Both sit on the type path
  the new control and status segment had to compile through; `api.ts`/`main.tsx` are the one
  place those types exist (v033 made the same call for `main.tsx`'s ambient declaration).
- `desktop/preload.js`, `desktop/main.js`, `ProviderCard.tsx` — untouched: `EXTRACT_MERGE_RUNS`
  flows through the existing generic `envForConfig()` spread into the backend spawn, and the
  control is not on the provider cards.

## Red / green (two observations, separate runs, per the house rule)

- **Red**: on the pre-v140 build (the running v138-era app instance; a read-only `GET
  /api/config`), the payload has no `merge_runs` key:
  `{"model":"fixture",…,"maturity_basis":"carrying"}` — and Settings has no merge control.
- **Green**: the echo is live and env-driven, not a literal — with `EXTRACT_MERGE_RUNS=union` on
  the backend, `/api/config` returns `"merge_runs":"union"`; unset it reads `"off"`; and the full
  desktop round trip below flips it both ways through the UI.
