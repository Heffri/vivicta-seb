# v173 — `GET /api/kb` 延迟:per-stem 文件指纹缓存(warm 1.2 s -> ~0.12 s)

工单:`v173-kb-list-latency`(上报 `vivicta-seb-72`)。基线 `origin/acrylic` = `cae29be`。
领地:`backend/pipeline/kb.py`、`backend/pipeline/test_kb.py`、本 evidence;app.py 的 `/api/kb` 路由未改(它自己不扫盘,见下)。

## 1. 红线(改前测量,206 个 stem,fixture 后端,本机)

`measure.py`(lane 临时目录)对 `/api/kb?collection=all|wallenberg` 各打 5 次:

| collection | 冷 (ms) | 热 (ms, 4 次) |
|---|---|---|
| all (206) | **8227** | 940 / 914 / 937 / 961 |
| wallenberg (11 行,但 entries() 全量算) | 948 | 1210 / 1124 / 1154 / 1217 |

cProfile(warm `kb.entries()`,206 stem,计 1484 ms profiled):

- `paths.kb_dir()` 每次请求被调 **1031 次**(`_meta`/`index_status`/`report_lock`/`_section_files` 各自重新解析),每次 `.resolve()` → `nt._getfinalpathname` 共 507 ms —— Windows 路径解析是最大头;
- `_meta` 每请求重读 206 份 meta.json(275 ms);`index_status` 每 stem 取锁+stat(846 ms);
- 290adfc 的 `_has_saved_text`/`_has_saved_figures` 本身已按 (path, mtime, size) lru 缓存,不是热点;热点在它周围的每请求重建。

## 2. 改动(kb.py,最小缓存)

- `entries()` 每 stem 的派生 entry 缓存在模块级 `_entry_cache[stem]`,键为指纹:
  `(fingerprint(embedding_identity()), ((path, mtime_ns, size) × {meta.json, pages.jsonl, embeddings.jsonl, index.json, extractions/<section>.json…}))`。
- 命中路径只做:**1 次 kb_dir() 解析 + 顶层 glob + 每 stem 一次 extractions 目录 glob + ~8 个 `os.stat`**,**零文件内容读**;`index_status`/`_meta`/`_has_saved_*` 都不再进 warm 路径。
- 失效全靠写入方改文件(save_report/save_extraction/save_run/索引重建都会动 mtime/size),无手动逐出。
- `_index_in_progress()`:warm 命中前查 index 操作锁,重建中的 stem 仍落到 `index_status()` 的 "building" 分支(与改前行为一致)。
- 命中返回 `dict(cached, sections=list(...))` 浅拷贝,调用方拿到的仍是独立 dict。
- embedding identity 进指纹:EMBED_MODEL/EMBED_BASE_URL 变化会使缓存失效(test_kb 的 `test_embed_model_invalidation` 场景)。
- `_section_files` 拆出接受路径的 `_section_files_in(d)`(v133 语义原样),`entries()` 用它避免每 stem 再解析 kb_dir。

返回 JSON 逐字节不变:`cmp` 前/后响应 `kb-all-*.json`、`kb-wallenberg-*.json` 均 **BYTE-IDENTICAL**(各 197,609 字节)。

## 5. e2e(kb.spec,前后各一次,本机当时状态)

- **改前(基线代码):10 passed / 0 failed(34.8 s)** —— v165 记录的 6 个 kb.spec 超时**今天在干净基线上没有复现**(当时 warm 2.6 s、机器多 lane 高负载;今天基线 warm ~0.94 s,能挤进 5 s 断言)。工单"6 失败应消失"的前提今天不成立,如实记录。
- **改后:10 passed / 0 failed(19.5 s)**;两个受 /api/kb 拖累最重的用例时长直接体现收益:collection switch 8.4 s -> 2.7 s、7.7 s -> 3.2 s。
- 结论:失败即使再出现(机器负载回到 v165 状态)也已无根因——warm 从 ~0.94 s(基线今天)/2.6 s(v165)降到 ~0.12 s,给 5 s 断言留出 40 倍余量。
