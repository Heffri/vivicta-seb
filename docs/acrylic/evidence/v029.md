## 1. Structure

```
desktop/                        new npm package, independent of frontend/backend
  main.js                       main process: single-instance lock, backend launch + health
                                 check, window creation, acrylic detection, titlebar-overlay
                                 tone sync, userData bootstrap
  preload.js                    exposes window.arp = {material, platform, version}; mirrors
                                 <html data-tone> to main over IPC (arp:tone-changed)
  electron-builder.yml          nsis + portable targets, extraResources from build-resources/
  scripts/prepare-resources.js  stages frontend/dist, backend/dist/backend, data/ (no PDFs)
                                 into build-resources/ (gitignored) before electron-builder runs
  icons/icon.ico (+make-icon.js) placeholder mark, hand-drawn, see §7
  package.json, package-lock.json, README.md

frontend/src/main.tsx           + reads window.arp?.material, sets <html data-material="on">
docs/acrylic/DESIGN.md          + one row for the material --bg-0 override, one for fonts
```

Nothing else touched — no other frontend file, no backend file (v030's lane).

## 2. Startup sequence

**Dev** (`cd desktop && npm run dev`): find `backend/.venv` → spawn
`python -m uvicorn app:app --port 8000` (reusing an already-listening one if the developer started
it by hand) → poll `/api/config` up to 30s → spawn `frontend`'s own `npm run dev` (again reusing if
already up) → poll `http://127.0.0.1:5173/` up to 30s → create the `BrowserWindow` → load
`http://127.0.0.1:5173`. Any failure at any step is a `dialog.showErrorBox` naming the log file,
then `app.quit()`.

**Packaged**: copy bundled `data/` into `app.getPath('userData')/data` on first run only (existing
`userData/data` is left alone on later runs, so uploads/index rebuilds survive an upgrade) → find a
free TCP port → spawn `resources/backend/backend.exe --port <port>` with
`ARP_DATA_DIR`/`KB_DIR`/`FRONTEND_DIST` set → poll `/api/config` → create the window → load
`http://127.0.0.1:<port>/` (the backend itself serves `frontend/dist` at `/` and the API at `/api`,
same origin, confirmed live — §5).

`before-quit` tree-kills (`taskkill /pid <pid> /t /f`) whatever this instance spawned. This turned
out to be load-bearing, not defensive: `spawn(pythonExe, ['-m', 'uvicorn', ...])` produces a
**3-level process chain** on this machine (venv `python.exe` → a second `python.exe` re-exec →
occasionally a third), observed directly while debugging §6.1 — killing only the immediate child
would have orphaned uvicorn. Never kills anything it didn't spawn (checked against other lanes'
processes throughout, by full command line, not by port or name).

## 4. Frontend material + font branch

`index.css`: `:root[data-material="on"]` drops `--bg-0` another 14pp (66%→52% dark, 76%→62% light,
matching `[data-tone="light"][data-material="on"]`) and sets `body { background-image: none }` (the
real OS blur replaces the painted `--wallpaper`). Numbers and rationale in `DESIGN.md`.

Fonts (owner's follow-up instruction, 2026-09-16 12:45, relayed by the supervisor): reuse UAW's own
font stack rather than inventing one. UAW's is (`renderer/styles.css:73-74`) `Inter, "Segoe UI
Variable Text", "Segoe UI", system-ui, sans-serif` / `"Cascadia Code", "Cascadia Mono", ui-monospace,
Consolas, monospace`. Ours drops the leading `Inter` — we don't bundle it, and the entire point of
this instruction (zero-download desktop font) argues against adding a web font just to keep it.
`--font-mono` didn't previously exist as an overridable token in this codebase; adding it doubles as
correctly wiring the `font-mono` utility already used in 4 files (`StatusBar`, `StatusCards`,
`SourcePanel`, `KbView`) to Tailwind's own documented default when `data-material` is off, instead of
silently relying on whatever Tailwind's built-in theme happens to default to.

**Found by inspecting the compiled CSS, not by inspection of the source**: `html { @apply font-sans;
}` compiles to a build-time-inlined literal (`font-family:Geist Variable,sans-serif`), never
`var(--font-sans)` — confirmed by grepping `dist/assets/*.css` before and after adding a second
`--font-sans` definition under `[data-material="on"]`; the literal didn't change either time.
`.font-mono { font-family: var(--font-mono) }`, by contrast, already compiled as a real variable
reference (nothing in this codebase previously redefined `--font-mono`, so Tailwind never inlined
it). Fixed by changing the one line to `font-family: var(--font-sans)` — same default value, but now
re-resolves under `[data-material="on"]` the same way every other overridden token already does.
Without this fix, the `--font-sans` override would have been dead: correctly defined, silently never
consumed, no visible failure — exactly the "unwired feature" shape flagged independently in §6.2.

## 6. Real bugs found fixing this, not hypothetical

Three separate failures, each looked like a different problem until isolated:

**6.1 `spawn EINVAL` spawning vite.** `child_process.spawn('npm.cmd', [...])` without `shell: true`
threw `EINVAL` on every attempt — Node wraps a `.cmd` target in its own `cmd.exe` invocation on
Windows, and that wrapping is broken when `cwd` contains a space (a stock, well-known Node/Windows
issue), true of any checkout under a user profile whose account name has one. Invisible until read
directly off the dialog text (`webContents` error dialogs render on a display this session's
`CopyFromScreen` can't see — see §3 — so a targeted `PrintWindow` capture of just that dialog was
what finally showed `spawn EINVAL` instead of a guess). Fixed with `shell: true` on that one spawn
call (not needed for the backend spawns, which target `python.exe` directly, no `.cmd` indirection).

**6.2 Vite bound to `::1` only.** Fixed 6.1 and the dialog changed to "did not respond" after the
full 30s — but vite's own log said `ready in 393ms`. `curl http://localhost:5173/` → 200;
`curl http://127.0.0.1:5173/` → connection refused; `Get-NetTCPConnection` confirmed `LocalAddress
::1` only. This machine's default hostname resolution for an unqualified `vite --port 5173` binds
IPv6-only. Fixed with an explicit `--host 127.0.0.1`, matching every other port convention already
in `common.md`/`vite.lane.config.mts` for the same likely reason.

**6.3 PyInstaller onedir nesting.** `prepare-resources.js` copied `backend/dist/` into
`build-resources/backend/`, but `build_exe.py` (v030) produces `dist/backend/backend.exe` — one
level down — so the packaged app ended up looking for `resources/backend/backend.exe` and finding
`resources/backend/backend/backend.exe`. Copy source corrected to `backend/dist/backend`. Caught by
actually building `backend.exe` and running the packaged app end-to-end (§5), not by reading
`build_exe.py`'s docstring, which does say the right path.

**6.4 (minor, not a bug) `dialog.showErrorBox`'s window title is always "Error" on Windows**,
regardless of the string passed as its first argument — the actual message is in the dialog body,
read via the same targeted `PrintWindow` capture as 6.1. Relevant only because it means
`Get-Process`'s `MainWindowTitle` can't distinguish *which* dialog is showing; had to capture and
read the body every time.

## 7. UAW follow-up instruction (owner, 12:45) — what transferred and what didn't

Reported live during the lane (`ao send`, `v029 [1/2]`/`[2/2]`); summarized here for the record.

**Ported**: `--font-sans`/`--font-mono` desktop branch (§4). Acrylic detection (`supportsAcrylic()`)
already matched UAW's `supportsAcrylicBackgroundMaterial()` gate before this instruction arrived —
confirmed, not changed.

**Not ported, with reasons**:
- `data-window="blurred"` (defocus degradation): UAW's **own** repository documents this as an
  unwired feature, not working code — `theme-acrylic.css` has the CSS branch, but `src/` has no
  producer anywhere (`main.ts` has no `blur`/`focus` window listeners), and three separate pieces of
  UAW's own evidence say so explicitly (`issues/85`, `evidence/worker-386-f148-material-drop.md`,
  `evidence/worker-393-board-audit-claude.md` — one even calls it "dead code" before a later note
  corrects that to "unwired feature", i.e. never implemented rather than implemented-then-broken).
  Nothing existed to copy.
- `window-placement.ts`: not "window position memory" as the instruction assumed — it's
  `--window-placement=offscreen`, a mechanism for placing a window off every monitor so an
  *automated agent or test launch* doesn't steal the owner's foreground focus, gated on also carrying
  `--user-data-dir` (UAW's marker for an isolated profile). A multi-instance-orchestration concern;
  this app is a single-user double-click launch with no such concept.
- `native-window-material.ts` + `native-window-frame-persistence.ts`'s DWM caption/border
  suppression ("F204"): real and wired in UAW, unlike the above two. It works around Windows
  repainting a `frame: false` window's native caption/border in the desktop accent color, by
  spawning PowerShell to run embedded C# (`DllImport dwmapi.dll`) and re-running that suppression on
  a debounced timer hooked to `WM_DWMCOLORIZATIONCOLORCHANGED` (fires when the owner's wallpaper
  slideshow rotates, on UAW's machine every 10 minutes). This app's window uses `titleBarStyle:
  'hidden'` + `titleBarOverlay` instead of `frame: false` — a deliberate choice (§ original work
  order: this frontend has no window-control buttons of its own, and adding them was out of this
  lane's territory) — and `titleBarOverlay`'s color is set directly through Electron's own supported
  API, not independently repainted by DWM the way a bare `frame: false` caption is. No accent-colored
  border/caption artifact showed in either screenshot. Porting ~300 lines of spawned-PowerShell +
  embedded-C# + raw Win32 message hooking to guard against a problem that (a) very likely doesn't
  apply to this window style and (b) would show for well under a second every several minutes even
  if it did, was judged disproportionate. Flagged rather than silently skipped; not reversed by the
  supervisor as of this writing.
- Packaging structure: `scripts/package-workbench-windows.ts` confirmed to use `@electron/packager`,
  not electron-builder (matches what `package.json` already showed before this instruction — no new
  information there). Its "stage build output into a scratch directory, then point the packager at
  it" structure is exactly what `prepare-resources.js` + `build-resources/` already do; kept
  electron-builder itself per the original work order's explicit nsis+portable requirement.

Both installer and portable were produced by the same `npm run dist`; only the **portable** exe was

its `electron-builder` log inspected, but not run — installing modifies `Program Files`, the Start
Menu and the registry on a machine other lanes and the owner share, which felt like more than this
verification needed given the portable exe already proves the same underlying `win-unpacked` bundle
launches correctly. Flagging this as a gap rather than claiming it's covered.

**Not signed**, confirmed with `Get-AuthenticodeSignature` on both output files
(`Status: NotSigned`) — electron-builder's build log prints `signing with signtool.exe` for several
files regardless of whether a certificate is configured, which reads alarmingly like it signed
something; it didn't, checked rather than assumed. SmartScreen will warn on first run of either
artifact; documented in `desktop/README.md` for the owner.
