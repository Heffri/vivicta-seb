## What the scripts do

`scripts/run.py` (296 lines, stdlib only, no new dependency) holds all the logic; `run.bat` (28
lines) and `run.sh` (15 lines) are thin wrappers that only locate a Python interpreter and hand off —
matches the work order's "one Python implementation, bat/sh are just wrappers". Order of operations:
check Python ≥3.11 (`sys.version_info`, so the version *message itself* still prints correctly even
under an older interpreter — the whole module parses under old Pythons too: `from __future__ import
annotations` defers every modern type hint, no `match` statements) → check Node ≥18 / npm on PATH,
pointing at nodejs.org if missing (no auto-download, per the work order) → `backend/.venv` +
`pip install` if missing, else skip → `frontend/node_modules` (`npm ci`) if missing, else skip →
`frontend/dist` rebuilt if missing or older than `frontend/src`/config files, else skip →
`find_open_port(8000, tries=20)` (sequential bind test, real port, not desktop's random one — this
script wants a stable, tellable default) → spawns `<venv>/python -m uvicorn app:app --host 127.0.0.1
--port <port>` with `FRONTEND_DIST=<abs path to frontend/dist>` in its env, `cwd=backend/` → polls
`GET /api/config` for health → prints the resolved provider (fixture or real, straight from the
backend's own answer, never re-derived) → `webbrowser.open()` → foreground `proc.wait()` → Ctrl+C ->
`kill_process_tree()` in a `finally`, so it also runs on a health-check failure, not just on the happy
path. `--reinstall` (documented, not separately timed live — see "Not done") removes `.venv`,
`node_modules` and `dist` first, then falls through to the same create/skip logic.

**Borrowed from `desktop/main.js` (both cited in the work order's reading list and its own "先抄
UAW" house rule), adapted from Node/Electron to Python:**
- `startBackendFromVenv`'s exact invocation shape — venv python path (`Scripts/python.exe` vs.
  `bin/python`), `-m uvicorn app:app --port <port>`, `cwd=backend/`, env merged over `os.environ` —
  ported near-verbatim into `venv_python()` / `start_backend()`.
- `httpGetOk`/`waitForHealth` (status `<500` = healthy, stop early if the child already exited) →
  `wait_for_health()`.
- `killProcessTree` (Windows: `taskkill /pid <pid> /t /f`; POSIX: `process.kill(-pid)`) →
  `kill_process_tree()` (POSIX side uses `os.killpg` + a `SIGKILL` fallback after a 10s grace period,
  one step more than the JS original since Python doesn't need to match it 1:1).
- The `npm.cmd` shim problem: `desktop/main.js`'s own comment (its `startViteDevServer`) explains that
  Windows `CreateProcess` cannot run a `.cmd` shim directly and Node's `spawn()` needs `shell: true` to
  route it through `cmd.exe`, while the backend's own `python.exe` spawns need no such thing (a real
  PE, no shim). `run_step()` mirrors that exact split: `use_shell=True` only for the two `npm`
  invocations on Windows, never for `venv`/`pip`.

Not borrowed: desktop's random free port (`findFreePort`, bind to `:0`) — this script wants the
*default* 8000 when free and to *say* when it had to move, so `find_open_port` does a sequential bind
test from 8000 instead; and desktop's "reuse an already-listening backend on that port" check — a
one-click launcher that finds *something* on 8000 should not guess whether it is safe to reuse, it
should just move to 8001 (the work order's own spec).

## Model config: root `.env`, no new plumbing needed

The work order asked the script to read a repo-root `.env`. It turns out `backend/app.py`'s own
`load_dotenv()` (called with no arguments) already does this for free: python-dotenv's default search
walks upward from `app.py`'s own file location — `backend/.env` first, then `backend/../.env` (the
repo root) if that's absent — regardless of the *process*'s current working directory, since the
search is keyed off `app.py`'s own `__file__`, not `os.getcwd()`. Since `run.py` spawns the backend
with `cwd=backend/` and an inherited environment, a repo-root `.env` is picked up **without run.py
parsing or forwarding it itself** — confirmed by reading `python-dotenv`'s `find_dotenv()` and by this
lane's own runs (always fixture mode here, since no `.env` was ever created, but `/api/config` is the
live proof the backend resolves its own config independent of anything this script injects).
`run.py`'s own contribution is just user-facing: `note_env_status()` says up front whether a
repo-root `.env` exists (fixture vs. "here's how"), and after the backend answers healthy,
`print_mode_banner()` reprints the backend's *own* `/api/config` answer — so the script's message and
the backend's real behavior can never drift apart. README's "Run it" section and `.env.example`'s
existing text are otherwise untouched; one new sentence says a repo-root `.env` also works and that
`backend/.env` wins if both exist (true per the search order above).

## Stopping it — what was actually tested, and the one thing that stayed unproven here

**Directly, in isolation:** `kill_process_tree()` called on a `start_backend()`-spawned process —
before: PID alive, `GET /api/config` → `200`; after: PID gone, `GET /api/config` → `URLError`
(connection refused), synchronously, no polling needed.

**End to end, real backend, real signal, real cleanup:** `cmd /c run.bat` on the clean clone (the run
timed above) was sent a real Windows console-control event from an external harness
(`CREATE_NEW_PROCESS_GROUP` + `Popen.send_signal`). `CTRL_C_EVENT` — the one a literal Ctrl+C keypress
generates — never reached the child tree in this sandboxed, non-interactive console (no real attached
console for `GenerateConsoleCtrlEvent` to target; confirmed the same way twice, once against `run.py`
directly and once against `run.bat`). `CTRL_BREAK_EVENT` did land: `cmd.exe` printed its own standard
`Terminate batch job (Y/N)?` (this is `cmd.exe`'s prompt for *any* batch file running a long foreground
command, not something `run.bat` opts into or can fully suppress — now called out in the README so a
real user isn't surprised by it), `run.bat`'s own error branch also fired (`--reinstall`... no,
unrelated — the nonzero exit branch, printing "exited with code ..." + its own `pause`), and — the
part that matters — **uvicorn received the same broadcast and shut down gracefully on its own**
(`INFO: Shutting down` / `Application shutdown complete` / `Finished server process`, not a hard
kill). Post-check by PID: all 5 tracked processes in the tree (`cmd.exe` + 4 descendants, including
the backend) confirmed dead, port 8000 confirmed closed (`URLError`). Result: **clean, no residual
processes**, matching the work order's "Ctrl+C 后无残留进程(按 PID 核)" bar, even though the exact
keystroke could not be simulated from this harness.

**What stayed unproven:** a literal, physical Ctrl+C keypress in a real interactive console window —
this sandbox has none to attach to. That specific gap is judged low-risk rather than left silent: a
real Ctrl+C reliably raises `KeyboardInterrupt` in a Windows Python process (Python installs its own
`CTRL_C_EVENT` → `SIGINT` translation at interpreter start, standard behavior every Python CLI on
Windows already depends on, not something this script adds), which enters `run.py`'s own
`except KeyboardInterrupt: ... finally: kill_process_tree(proc)` — the same function just proven
above to correctly kill the backend and free the port. Reported per reporting.md's "premise" framing:
not a defect, a boundary of what this sandbox can simulate, with the adjacent code path proven
correct by two independent, more direct routes instead.

## `run.sh` (Git Bash, this machine)

Reached a fully healthy, working app — further than the work order's minimum bar ("至少跑到检测 +
venv + npm 步骤"): `./run.sh` → found `python3` → `exec`'d into `scripts/run.py` (confirmed no
leftover wrapper process — `exec` replaces the shell image, verified by checking the parent PID
chain) → detected the already-set-up `.venv`/`node_modules`/`dist` from the `run.bat` run above and
skipped straight to starting the backend → `GET /api/config` → `200` fixture → browser opened and
loaded the full app (same asset + API request pattern as the `run.bat` run). Stopping it via a signal
sent *from Git Bash* did not work — MSYS's `kill` cannot target a native (non-MSYS) `python.exe` PID
(`kill: (25256) - No such process`, even though `Get-Process` on Windows sees it fine) — so it was
stopped via `taskkill /t /f` on the confirmed PID instead, same as the `run.bat` case. This is a
Windows/Git-Bash cross-runtime testing artifact, not evidence about `run.sh` itself: on a real
macOS/Linux box (`run.sh`'s actual target), `./run.sh`'s `exec python3 scripts/run.py` is a normal
POSIX foreground process and Ctrl+C there is unremarkable, standard `SIGINT` delivery — not
independently re-proven here beyond `kill_process_tree()`'s POSIX branch (`os.killpg`, `SIGTERM` then
`SIGKILL` after a 10s grace period) already having been code-reviewed against `desktop/main.js`'s
equivalent.

## Other checks

- **Port-busy fallback**: bound `127.0.0.1:8000` from a separate socket, then called
  `find_open_port(8000, 20)` directly → returned `8001`. (Never hit "for real" in any live run above
  since 8000 was always free at the time; this isolates and confirms the fallback logic itself.)
- **`python -m pipeline.test_paths`**: `paths self-check ok`, run against the clean clone's own venv —
  `FRONTEND_DIST` semantics untouched by this lane (`run.py` only ever sets it to an absolute path,
  `str(DIST_DIR)` where `DIST_DIR = (repo root).resolve() / "frontend" / "dist"` — never a relative
  one, which would have resolved wrong against the backend's `cwd=backend/`).
- **`npm run lint` / backend's five `test_*` suites**: not run — out of scope per the work order
  ("没改代码"), since nothing in `backend/pipeline` or `frontend/src` changed.
- A Chinese-locale Windows console (this machine) decodes piped subprocess text as `GBK`/`cp936` by
  default, which crashed an early version of this lane's *own throwaway test harness* (not
  `run.py`) when it piped `npm run build`'s UTF-8 output through Python's `text=True` with no explicit
  encoding. Checked `run.py` itself for the same risk: it never captures backend/npm/vite output as
  text (everything is inherited straight to the real console, matching how a real double-click session
  behaves) except one `node --version` call, which now explicitly decodes as
  `encoding="utf-8", errors="replace"` rather than relying on the locale default. `run.py` also
  contains zero non-ASCII bytes (checked directly), so it cannot itself hit a console-codepage
  `UnicodeEncodeError` on `print()`.
