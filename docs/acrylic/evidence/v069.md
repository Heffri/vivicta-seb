## The bug, precisely (v068's own "downstream" section, read-only diagnosis — this lane implements)

v068 rebuilt Ework p.70 and XANO p.84's matrix-transposed two-line headers into one correct line each
(`PARSER_VERSION` 6). Read mechanically now instead of by eye, both tables' `_bucket_header` hit counts
came out wrong for the **same root cause**: two schema synonyms (or a bare Total/Summa word and a
synonym) can each match a *piece* of the same one printed phrase, and nothing before this lane
collapsed that into one column:

- **XANO** (`PER 2025-12-31 –30 dgr 31–90 dgr 91–360 dgr Summa inom 1 år Mellan 1 och 3 år Mellan 3 och 5
  år Efter 5 år Totalt`): the header hit list came out **10**, not 8. `due_within_1_year`'s own plain
  synonym `"inom 1 år"` is a literal substring of the subtotal phrase `"summa inom 1 år"` (already
  matched whole, tagged `:subtotal`) — a second, spurious hit for the same one column. Independently,
  `_BARE_TOTAL`'s bare-word regex (`\bsumma\b`) matches the leading "Summa" of that same phrase a second
  time, on top of the real, separate bare "Totalt" at the row's own end. Confirmed directly (not just
  reasoned): `_bucket_header` on the real row returned
  `['_excluded','_excluded','_excluded','due_within_1_year','total','due_within_1_year','due_1_to_5_years','due_1_to_5_years','due_after_5_years','total']`
  (10) against the row's own 8 amounts — declined, matching v068's own finding exactly.
- **Ework** (`kSEK Due < 1 month 1-3 months 3-12 months 1-5 years > 5 years Total undiscounted value
  Carrying amount`): the header hit list came out **7**, with a spurious duplicate hiding a genuine gap.
  The schema's own `due_within_1_year` header_synonym `"3 months"` is a literal substring of its own
  `"1-3 months"` — a second hit for that one column — which happened to roughly cancel out, in raw count
  only, the header's *other*, separate problem: nothing in the schema recognises "Due" (v068's own
  finding: a real, sometimes-nonzero column, the Accounts payable row's own Due figure is 91,284) or
  "Carrying amount" at all. Confirmed directly: `_bucket_header` returned
  `['due_within_1_year']*4 + ['due_1_to_5_years','due_after_5_years','total']` (7, with the `<1 month`/
  `1-3 months`/`3 months`[dup]/`3-12 months` cluster) against the row's own 8 amounts — declined.

## The fix: `_drop_nested_hits` (new, `extract.py`)

General, not per-company: `_bucket_synonym_hits` now returns `(start, end, key)` spans instead of
`(start, key)`, and `_bucket_header` runs the combined per-row hit list (synonym hits + the bare-total
scan) through a new `_drop_nested_hits` before counting — a hit whose span sits entirely inside another,
*strictly wider* hit's own span in the same row is dropped; ties (identical span, two different keys)
are left alone, a real ambiguity this function does not resolve. One printed phrase is one column, no
matter how many schema entries happen to match pieces of it — the same principle the file's own
subtotal-override logic already applies one level up (a subtotal overrides its own finer columns to its
left), generalised to substring-level overlap regardless of position.

With this alone, XANO's 10 hits become the correct 8
(`['_excluded']*3 + ['due_within_1_year','due_1_to_5_years','due_1_to_5_years','due_after_5_years','total']`)
and Ework's 7 spurious-but-coincidentally-7 hits become 7 *correct* hits (the "3 months" duplicate
removed) — still 7, since the underlying "Due"/"Carrying amount" gap is untouched by a dedup alone.

## "Due": red, green, then a real problem found and fixed before delivery

The work order's own instruction: add `"due"` to `due_within_1_year`'s `header_synonyms`. Implemented
first exactly as written, confirmed green in isolation (Ework's own two-line header + row, `_bucket_header`
correctly adds the `Due` hit, `_drop_nested_hits` correctly removes the `3 months` duplicate) — **then
verified end to end against the real page in full**, not just the isolated header+row snippet, per this
project's own standing lesson (LESSONS.md #10: a fix that looks right in isolation still needs the real
page). That surfaced a real defect: `header_synonyms` is matched case-insensitively, with no word
boundary, over the *whole* 25-row window `_bucket_header` searches above a candidate row — not just the
header line itself — and Ework's own p.70/71 carries a dozen+ ordinary-prose "due"s in that window
("...risk **due** to assets...", "Past **due** accounts receivable...", "...not yet **due**...", an
accounts-receivable ageing table two tables down). A direct check against the full page (`_bucket_total_row`
+ every candidate row it finds, not just the one row this lane cares about) showed the effect concretely:
two *new* warnings appeared that were never there before —

```
total_debt: column reading of 'Total 103,815 1,869,039 1,243,796 59,303 7,518 19,973 3,303,445 3,300,679'
  rejected -- due_1_to_5_years 3303445, due_after_5_years 3300679 exceed its own total 1869039
total_debt: column reading of 'Short-term interest-bearing liabilities* ... 156,410 156,410'
  rejected -- due_1_to_5_years 156410, due_after_5_years 156410 exceed its own total 153761
```

— a bare "due" match against the prose sentence pushed an *unrelated* candidate row's own hit count to
coincidentally equal its own amount count, reaching `_fill_bucket_columns`'s `over` safety valve instead
of the column-count valve above it. Caught here because `over` happened to reject both; not guaranteed
caught the same way on another company's own surrounding prose, where a coincidental match could write a
wrong value instead of only tripping a warning.

**Deviation from the work order's literal instruction**: rather than ship `"due"` as a plain
`header_synonyms` string, it now lives in `extract.py`'s existing `_BUCKET_BOUNDARY` dict (the mechanism
this file already uses for exactly this class of problem — the `< 1 year`/`> 5 years` English-symbol
patches are regex, not literal substrings, for the same reason) as
`r"(?i:<\s*1\s*years?\b)|\bDue\b(?!\s+to\b)"` — the new alternative is **case-sensitive** (real column
headers print "Due" capitalised; all dozen+ prose collisions found on Ework's own pages are lowercase)
and excludes the one capitalised false positive a scan like this would still invite, a sentence opening
"Due to ...". This is squarely inside this lane's territory (`_BUCKET_BOUNDARY` is part of `extract.py`'s
bucket-column header-hit logic) and inside the work order's own "主管的观察可被推翻" allowance — reported
here with full before/after evidence per `reporting.md`'s "premise overturned" guidance, not silently
substituted. `backend/schemas/debt_maturity.json` ends this lane with **zero net diff** (added `"due"`,
then reverted it once the `_BUCKET_BOUNDARY` fix replaced it — confirmed via `git status`/`git diff`,
both empty for that file).

Re-verified after the fix: the same full-page check now shows **zero new warnings**, Ework's outcome
byte-identical to before this lane (see "Ework: why it still declines" below), and none of the four
bare-Total/debt-row candidate rows on Ework's own page 70 are spuriously reached anymore.
