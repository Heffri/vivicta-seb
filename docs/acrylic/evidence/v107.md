# v107 — desktop: merge bundled `data/` into userData on every launch (never overwrite user files)

Lane `v107`, branch `ao/vivicta-glm-47/v107-desktop-kb-sync`, baseline `origin/acrylic@45e7dc1`
(fetched again before delivery — nothing new ahead; no merge needed). Territory held: `desktop/main.js`
(only the `ensureUserData` block + the one startup log line; the two helper functions it owned moved
out with the logic they implemented), new `desktop/data-sync.js` + `desktop/data-sync.test.js`,
one clause + citation in the `docs/acrylic/README.md` desktop section, this file. Nothing in
`backend/`, `frontend/`, `schemas/`, `data/` touched; zero model calls.

## The defect

`ensureUserData` copied the bundled `data/` (companies.json, reports/index.json, kb/) into
`<userData>/data` only when that directory did not exist, then returned early forever after. Any
KB entry or index row bundled with a **new** app version therefore never reached an install created
by an **older** version. Observed live, pre-fix: an install seeded at 186 KB entries, bundled data
at 196 — ten `kb/<stem>/` trees (attendo, bhg, byggmastare_a_j_ahlstrom_h, fagerhult, humble,
lime_technologies, powercell_sweden, rejlers, rvrc_holding, svedbergs — the Swedish finer-split
batch) unreachable by that install.

## What changed

`desktop/data-sync.js` owns the merge; `main.js`'s `ensureUserData` is now a one-line call into it,
and `main()` writes one log line with the run's counts:

- `planDataSync(bundled, dest)` walks the bundled tree and plans only what the destination lacks.
  A `kb/<stem>` directory the user lacks is copied whole (still skip-filtered); a stem they have
  gets only its *missing files* backfilled (e.g. a newly shipped `extractions/debt_maturity.json`
  never lands if the user's own copy exists). Any destination file that exists is never opened for
  comparison — existing means untouchable, whatever its contents.
- `reports/index.json` merges by the entries' `file` key: user entries keep their order and win
  collisions, bundled-only entries append. Nothing is rewritten when the merge would add zero
  entries (byte-stable idempotency). When a merge does write, it is tmp+rename (same crash safety
  as `kb.save_extraction`) and uses the same indent-2/no-ASCII-escape/trailing-newline shape the
  backend's fetch writes (the tags-on-one-line cosmetic pass is not replicated — parser-irrelevant).
- `shouldSkipDataEntry` moved here verbatim from `main.js` (reports/*.pdf, kb embeddings.jsonl,
  kb *.tmp, `kb/up-*`) so the old first-launch copy and the new merge share one rule set; the
  now-dead `copyDataDir` moved out with it. Skip semantics are otherwise unchanged.
- Counting semantics for the log line (`syncLogLine`): `kb entries` = new whole `kb/<stem>` dirs;
  `files` = individually backfilled/new files outside those stems; `reports/index.json` additions
  are counted separately (`indexEntries`) and do not appear in the two-counter line.
- A fresh install (no `<userData>/data`) goes through the same plan/execute path — the plan is
  simply "everything" — so there is exactly one code path, the one the tests exercise.

## Unit tests — red, then green (`node --test desktop/data-sync.test.js`, runtime-derived temp dirs)

Fixture = the work-order scenario: user `data/` holds a reviewed `kb/a_2025/extractions/debt_maturity.json`
(content X) and `kb/up-1/`; bundled ships the same extraction path with content Y, a new `kb/b_2025/`,
and a report index; the user side also carries an index row for the same `file` key (so "user wins"
is actually exercised).

- **Red** (implementation still replicating the old once-copy semantics): `1 fail / 1 pass / 4 fail`
  across the suite — the core test dies on `kbEntries 0 !== 1` (the new stem never reaches the old
  install), fresh-install and index-branch tests fail on counts/merge; only the idempotency test
  passes, trivially (a no-op is idempotent). Recorded before the real implementation was written.
- **Green**: 4/4 pass, covering the five required points — (1) `kb/b_2025` appears; (2) the reviewed
  file still says X; (3) `kb/up-1` untouched; (4) index merged by `file`, user entry wins, bundled-only
  appended; (5) second run returns all-zero counts and the whole-tree content hash is unchanged —
  plus skip-rule assertions (bundled `kb/up-9`, `embeddings.jsonl`, `reports/*.pdf` never copied) and
  the exact log string: `data sync: +1 kb entries, +0 files`.

`node --test desktop/updates.test.js` still green (2/2) — run together: `6 pass / 0 fail`.
