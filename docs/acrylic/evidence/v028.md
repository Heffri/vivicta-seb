Rationale per assumption (owner's decision, 2026-09-16 — see work order for full text):

1. **Carrying amounts, not contractual undiscounted cash flows.** HANDOFF's open question #1; v008
   found the locator alone can't split the two tables (an exclude-keyword attempt on liquidity-risk
   pages flipped 21 companies' top-1: 2 better, 16 worse). Per HANDOFF and v008's own recommendation,
   the fix belongs in what the model is told to read and what the arithmetic checks against — not the
   locator — so it's written into the top-level `description` (which table to prefer) and `total_debt`
   (what its total must reconcile to).
2. **Leases follow the report's own convention.** HANDOFF's open question #2. No experiment behind this
   one — it's the simplest rule that doesn't require the pipeline to itself decide something Kristian
   hasn't stated: never add or remove lease liabilities, and preserve the printed row's wording in
   `raw_label` so a reviewer can see which convention a given report used.
3. **A missing bucket is null, and counts as 0 in the sum check.** HANDOFF's "null buckets are normal";
   v011 already implemented the check-side mechanism (`null_as_zero`, untouched here). This lane adds
   the extraction-side half of the same assumption: the field description telling the model not to
   invent a 0, plus a doc-only `description` on the check explaining why a null bucket still counts as
   0 once it's genuinely absent.

Full generated prompt (after) — `Section:` and `Fields to extract:` blocks show all 5 model-facing edits

```
You extract figures from a corporate annual report (Swedish or English) into JSON.

Section: Debt maturity structure
Total interest-bearing debt and when it falls due, as printed in the borrowings note (often 'Note 20' but the number varies by issuer). Amounts only — no interest rates, no covenants. Some reports print two maturity tables on nearby pages: the borrowings note's carrying amounts, and a liquidity-risk note's contractual undiscounted cash flows (includes future interest, a higher total). Read the carrying-amount table — the one whose total ties to interest-bearing borrowings on the balance sheet.

Value convention: Numbers exactly as printed in the maturity table. Unit = the unit stated in the table header (MSEK, SEK m, MEUR, USD m ...). Bucket boundaries follow the report's own columns; a report with finer splits (e.g. 1-2y, 2-5y) should have its 1-5y bucket taken as the sum of those columns.
Ignore statements/pages about: five-year summary, femårsöversikt, moderbolaget, parent company, quarterly, kvartal. Use the consolidated (group / koncernen) statement.

Fields to extract (key | label | description | unit hint):
- total_debt | Total borrowings | Total interest-bearing debt / borrowings, the row the maturity table sums to (or the note's own total if the maturity table has no total row). Must be a carrying amount that reconciles to interest-bearing borrowings on the balance sheet, not an undiscounted contractual cash-flow total. Include lease liabilities (IFRS 16) only if the report's own note includes them in this total — do not add or remove leases yourself; keep the row's own wording in raw_label so the choice is traceable. | currency_millions
- due_within_1_year | Due within 1 year | Amount falling due within one year of the balance sheet date (current portion of borrowings). null if the table has no such row — do not enter 0 for a bucket the report doesn't print. | currency_millions
- due_1_to_5_years | Due 1–5 years | Amount falling due between one and five years from the balance sheet date. If the report splits this further (e.g. 1-2y, 2-5y), sum those columns. null if the table has no such row — do not enter 0 for a bucket the report doesn't print. | currency_millions
- due_after_5_years | Due after 5 years | Amount falling due more than five years from the balance sheet date. null if the table has no such row — do not enter 0 for a bucket the report doesn't print. | currency_millions

Rules:
- Return ONE JSON object {"fields": [...]} with exactly one entry per key above, in that order.
- Entry: key, label, value (number, or null if not found), unit (from the table header, e.g. "MSEK"),
  period ("YYYY"), raw_label (the row label as printed), source, confidence (0..1).
- source = {"page": <n from the "=== PAGE n ===" marker>, "quote": "<text copied verbatim from that page,
  containing the row label and the number>"}. Copy character for character, do not reformat numbers.
  If value is null, source must be null and confidence 0.
- Report the column of the fiscal year named in the user message. Read the table's year header to find it:
  most reports print the current year first ("2025 2024"), some print it last ("2024 2025").
- value: drop thousands separators (152 340 -> 152340), "." as decimal separator, sign as printed (costs negative).
- Only rows that are printed. Never compute a value (no revenue minus costs, no EBITDA as gross profit):
  if the row is not in the statement, value is null.
- Never invent numbers. Prefer null over a guess.
- Compact JSON: no indentation, no line breaks.
```

## Findings

- Premise held: schema `description` (top-level and per-field) is exactly what
  `extract.system_prompt()` puts in front of the model — verified by printing the real generated prompt
  above, not by reading the template and assuming.
- One boundary worth flagging for whoever reads the schema next: `checks[].description` is inert as far
  as the model is concerned (checks run in Python only). Added it anyway for the null-bucket assumption
  since the work order allowed it "if necessary" and it's the one place that explains why the *check*
  treats a null bucket as 0, distinct from the field description explaining why the *extraction* returns
  null in the first place — but it's schema documentation, not prompt content, and should not be
  mistaken for the latter.
- The lease-liabilities assumption (#2) has no prior experiment behind it (unlike #1/#3, which build on
  v008/v011) — it's a fresh decision this lane formalizes into the schema text, flagged as such in both
  the schema and the README so it doesn't read as more validated than it is.
