# v191 — bounded OCR for scanned reports (page budget, ocr=full opt-in, on-demand pages)

## Scope

Consult item 12 / the work order's problem statement: a scanned annual report registered
synchronously OCR's every qualifying page (`backend/pipeline/parse.py`'s `page_text`, pre-v191
unconditional once a page has no text layer and is image/drawing-heavy) — a 150-page scan costs
ten-minute-class requests the frontend has no way to wait out. Saab's own 231-page scan measured

packaging for `data/tessdata`. Touched only `backend/pipeline/parse.py`, `kb.py`, `app.py`, their
tests, `frontend/src/{api.ts,types.ts,hooks/useBatch.ts,components/upload/BatchProgress.tsx}`,
one e2e spec, `docs/API.md`, `docs/DEMO.md`. **Not touched:** `extract.py`, any schema file,
`data/` (checked with `git status` throughout — clean). No model call anywhere in this lane.

`frontend/src/components/UploadView.tsx` was also touched (not in the work order's file list):

through to the actual HTTP request requires them to forward an `opts` parameter they previously
ignored. Three one-line closures plus the `onRetry` prop wiring; no other behavior changed.

## (a) Bounded registration OCR

`parse.page_texts(pdf_path, metadata, ocr="bounded")` (new default) first classifies every page
as scanned or not (`_looks_scanned`, the same no-text-layer + image/drawing-heavy test `page_text`
already used) without OCR'ing anything, then computes `_locator_bound_pages(doc)`: the report's own
front matter (`FRONT_PAGES = 8`, mirrors `locate.TOC_PAGES`) plus any PDF outline/bookmark entry
whose title hits the `debt_maturity` schema's own `toc_keywords` (reused via
`paths.schemas_dir()`, not a new list — the same words `locate.toc_targets` already trusts for
this kind of match), ±1 page. Outline titles are PDF metadata, readable with no text layer at all,
which is what makes computing the bound set possible before any OCR has run. Only
scanned-pages-within-the-bound-set get OCR'd; the rest come back `""`, flagged in
`metadata["ocr_pending"]`. If the bounded set alone needs more than `OCR_PAGE_BUDGET` pages (env,
default 40), `OCRBudgetExceeded(pages_needed)` is raised instead of running it — `pages_needed` is
every scanned page in the whole document (what a full pass would actually cost), not just the
bounded subset, so the message tells the truth about what "Run OCR anyway" commits to.
`app.py`'s new `ocr_budget_exceeded` handler turns that into
`422 {"detail": "scanned PDF: OCR would take ~N min for P pages", "ocr_pages_needed": P}`
(`OCR_SECONDS_PER_PAGE = 2.2`, from Saab's measured 506 s / 231 pages).

`kb.load_texts(stem, path, digest, ocr="bounded")` threads the mode into the three registration
call sites (`upload_report`, `register_library` — used by both `/from-library` and `/fetch`); the
default case still calls `parse.page_texts(path, parsing)` with the exact pre-v191 two-positional-
arg signature (only passes `ocr=` when it differs from bounded), so `test_runtime.py`'s existing
`test_ocr_cache_settings_and_reopen_keep_provenance`, which mocks `parse.page_texts` with a plain
`(path, metadata)` function, is untouched.

`fill_texts()` (the `/fill` endpoint's own text reader for a report whose `pages.jsonl` isn't
saved yet) explicitly passes `ocr="full"`: a human already picked those 1-2 exact pages, and
bounding by generic debt keywords could leave the one they asked for blank. Preserves this
fallback path's exact pre-v191 behavior.

## (b) `ocr=full` opt-in and on-demand top-up before `/extract`

`ocr=full` (query param on `POST /api/reports`; a JSON field on `/api/reports/from-library` and
`/api/reports/fetch`) skips the bounded-set computation entirely and OCRs every scanned page, no
budget check — the explicit-opt-in branch inside `page_texts` itself.

`_run_extract` computes `locate.candidate_pages(texts, schema, ...)` as before; if any of those
pages are still `ocr_pending` for this report, `fill_pending_ocr` OCRs exactly those pages (via a
bare `parse.page_text(doc[n-1])`, no budget gate — a top-up of a handful of pages, not a fresh
registration), persists them with `kb.fill_ocr_pages` (which always rewrites `pages.jsonl`, since
`save_report`'s own sha256/parser/ocr_settings cache guard would otherwise skip a page-content-only
change), and recomputes candidates against the now-real text. Guarded on the PDF still being on
disk (`pdf_path(report_id).is_file()`) — a text-only KB-restored report has no PDF to re-OCR from
and is left exactly as before. No-op in the common case (`ocr_pending` empty, or none of it
overlaps the section actually being extracted).

## (c) Frontend: 422 → "Run OCR anyway" → resend with `ocr=full`

`useBatch.ts`'s `classify()` now reads the 422 body (`ApiError.ocrPagesNeeded`, threaded through
`api.ts`'s `request()`) to tell an OCR-budget 422 apart from the pre-existing "no candidate pages"
422 (`'ocr-budget'` vs `'needs-ocr'`, registration-stage only). `BatchSpec.getReport` and
`Batch.retry` gained an optional `{ ocr?: 'full' }` passthrough; `BatchProgress` renders a "Run OCR
anyway (~N min)" button for `'ocr-budget'` in place of the generic retry button — the minutes are
read back out of the backend's own error string (`/~(\d+) min/`) rather than recomputed, so the
number shown can never drift from what the retry will actually do. A registration response's
`ocr_pages` (new field, `Report.ocr_pages`) renders as an "OCR: k pages" badge next to the batch
row's filename once known. The pre-existing per-field "From OCR" badge (`FieldsTable`/
`SourcePanel`, v179) and the extraction-level warning are untouched in code; the warning text
itself now names the page count (`app.py`: "This report contains OCR text (N pages)."), read
through the existing generic warnings list in `StatusCards` — no new Results-view component needed.

## Not settled

- The bounded window is a generic "debt/maturity/borrowings" heuristic (the schema this whole
  project centers on), computed once at registration, before any section is chosen. A section far
  from both the front matter and any outline hit for those keywords (a scanned company whose
  income statement sits on page 80 of a report with no PDF outline at all) stays `ocr_pending`
  until/unless `locate.candidate_pages` itself names it a candidate for the section actually being
  extracted — which needs some real page text to score against in the first place. The on-demand
  top-up in (b) closes the one gap that is reachable without solving that chicken-and-egg problem
  (a candidate page named without relying on this page's own text, e.g. the "page after the best
  one" companion mechanic landing just past the registration pass's own cutoff); it is not a
  general guarantee that every extraction eventually reads every relevant page of a heavily bounded
  scan. Out of scope per the work order's own S-M sizing.
