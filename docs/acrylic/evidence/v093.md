only extraction work is the stored-fields replay through the worktree's own `extract()` with

## Why

`data/kb` held 102 Large Cap entries of which only Ericsson had a `debt_maturity` extraction, while
the eight hardening rounds (v035…v084 era) had produced results for 72 distinct Mid Cap stems that
lived only in the shared seed directories. Published into `data/kb`, they light up everywhere at
once: the KB view and its sections list, Compare, PPT export, Ask (BM25 walks `pages.jsonl`), the
desktop build's bundled data, and `python eval/run.py --stored-kb data/kb` — which now scores the
Mid Cap `debt_maturity` labels (90 rows, 27 companies, v057) against one committed best-of-seeds KB
instead of four per-seed snapshots.

## `scripts/publish_kb.py` — what it does

    python scripts/publish_kb.py --kb <seed1-kb> ... --kb <seed8-kb> [--section debt_maturity] [--dry-run]

- Best run per stem: the `--kb` dirs are walked in the order given, a later dir overrides an earlier
  one — `seed1…seed8` therefore naturally selects the highest seed that has the stem. 12 stems exist
  in several seeds (apotea 1,2 · cloetta 1,3,4 · ework 1,5 · flat_capital 1,3 · knowit 1,3 · ncab
  1,2 · acast 2,4 · boozt 2,5 · ependion 3,5 · medcap 3,5 · svolder 3,4 · vef 3,5); the other 60 in
  exactly one.
- Per stem: `data/kb/<stem>` missing → `meta.json` + `pages.jsonl` are copied **byte for byte**
  (the seeds were written by Windows-Python and carry CRLF line endings; `.gitattributes` is
  `* text=auto eol=lf`, so the committed blob is LF, checkout stays LF, `git status` stays clean —
  `git check-attr -a data/kb/<stem>/pages.jsonl` → `text: auto`, `eol: lf`). An existing
  `data/kb/<stem>` with the same `meta.json` `sha256` → only the extraction is written; a different
  sha256 → the stem is skipped and listed (never overwritten). None of the 72 existed, so all 72
  were fresh copies. `meta.json`'s `parser` (3–6 across the seeds) is published as stored, exactly
  like the seeds wrote it.
- The extraction is replay-gated: the stored fields are fed back as the model's own answer (the
  replay_check `MODEL_KEYS` shape — stored `confidence`/`evidence` stripped, `extract()` derives
  both itself) through the **current** `extract()`, with page texts from the same seed's
  `pages.jsonl`. The replay window is the `two_pass: page [..] selected` pages recorded in the
  stored warnings (what the original run's window actually was) **union** the pages the stored
  fields cite — selected pages first, so `extract()`'s `pages[:2]` is the original window; not the
  candidates' first two, which would lose it.
- Per field, replayed vs stored: a value lost (non-null → null) or a confidence drop publishes the
  **stored** extraction and the reason is listed; anything else (null → value, a confidence gain, or
  both fields reading different values) publishes the **replayed** output and is listed. Both cases
  keep the original warnings and append exactly one line: `published: seed<N> run replayed with
  extract.py @ <8-hex>` (sha256 of `extract.py`'s bytes, not HEAD — a re-run from a moved HEAD with
  unchanged code still writes byte-identical files) or `published: seed<N> run as stored`.
- **Idempotent**: run twice, all 216 published files hash-identical — `git status` shows nothing
  new. Seed 9/10 can be appended to the same command later and re-run safely.
- 5 stems (academedia, better_collective, bico, flat_capital, oresund) are all-null runs with empty
  warnings: no candidate pages are derivable, so no replay is possible and they publish as stored
  (the same "not replayable" rule `replay_check.py` uses). 5 more (bonava, duni, meko, net_insight,
  traction) replayed **worse** and publish as stored too; reasons in the table.

## For the team — where these entries come from, and how to regenerate them

These 72 entries are the accumulated results of the eight debt-maturity hardening rounds (each
seed = one full pass of the Mid Cap universe with the pipeline as of that round's code; 85 seed
extraction files existed, 12 companies ran in more than one seed). Publishing took, per company,
the **highest-seed run available** — later rounds ran later, more-hardened code — and then
re-checked it against the code that ships with this branch: the stored fields were replayed through
`extract()` as if the model had just answered (no model call; the stored answer is the answer), and
the replayed result replaced the stored one **only where it was no worse** — never a lost value,
never a lower confidence. 55 replays reproduced the stored run exactly, 7 improved on it, 10 kept
the stored version (5 of them because an all-null run's pages cannot even be reconstructed — the
raw model answer behind a null is not stored, so a null stays null).

To regenerate after seeds 9/10 land (nothing else needed — the script is idempotent, and a stem
already in `data/kb` is only re-written when its source `sha256` says the PDF is the same):

    python scripts/publish_kb.py --kb <shared>/seed1-kb ... --kb <shared>/seed10-kb

To re-check the published data against any past or future code state:

    python scripts/replay_check.py --kb data/kb --section debt_maturity --baseline <git-ref>

One caveat for anyone reading `warnings` in the published files: they are the **original run's**
warnings (the work order keeps them) plus the one `published:` line — the replay's own warnings are
deliberately not mixed in. One exception to "as stored": Stillfront's seed-7 run stored a provider
timeout warning quoting the whole failed command line, machine paths included; the user segment of
any `X:\Users\…` path in a published warning is masked generically by the script (`…\Users\<user>\…`)
so the published KB carries no machine-identifying paths, and the rest of the error text survives.
