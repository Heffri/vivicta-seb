## 2. Switch mechanics (why a new IPC, not the Save path)

`applySettings` (`arp:settings:set`) kills and respawns the backend — right for provider/model,
wrong for a visual change. So `arp:theme:set` → `applyTheme(theme)`:

1. persists `theme` by **merging over the stored config** (`{ ...loadConfig(), theme }` then
   `saveConfig`) — an API key survives, and a later Save writes the same value because
   `ThemeSelect` also syncs the form's `theme` field through `onThemeChange`;
2. if the live window has `setBackgroundMaterial` (Win11 22H2+), switches the material and the
   native background colour in place → `appliedNow: true`, and the renderer flips
   `<html data-material>` to match (`main.tsx`'s startup rule, mirrored in `ThemeSelect`);
3. otherwise returns `appliedNow: false` and Settings shows "Restart the app to apply the window
   material." — the restart still works because the config was already written in (1).

Known edge, accepted: after a *runtime* switch, a manual reload (dev Ctrl+R) before a restart reads
the stale `--arp-material` process arg, so the renderer paints the wallpaper glass instead of the
OS material until the app restarts (window material and `data-theme` stay correct; only the
"transparent ground over OS blur" CSS branch lags). Restart makes everything consistent; the
normal switch path (no reload) is correct immediately, verified below.
