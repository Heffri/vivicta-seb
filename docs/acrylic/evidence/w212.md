## Two premise checks against the tree (both reported in the delivery message)

- The work order described `EXTRACT_SCAN_ALL` as "并进了 SettingsView". It is not and never was:
  neither `SettingsView.tsx` nor any frontend file mentions `scan_all`/`SCAN_ALL`, and w207's own
  evidence says the same. This lane therefore adds **no** scan-all toggle — DEMO.md still frames
  the full-report scan as an offline diagnostic (77–110 model calls per report/section, m02), and
  the work order's own "要做的" list only asks for its `/api/config` echo.
- The work order placed "Settings 保存把 `EXTRACT_SECOND_PASS` 传下去" under `backend/app.py`,
  but the backend has no settings-write route: the save path is the desktop shell's
  `desktop/settings.js` `envForConfig()` translation table (the file v140's recipe also edited).
  Without it the toggle would write `config.json` and reach nothing — a dead switch, and the
  work order's own round-trip requirement would be unmeetable. `desktop/settings.js` is therefore
  edited as the save path, flagged here and in the delivery message as the one file beyond the
  listed territory; no parallel lane (w208/w209/w210b/w211, backend/docs) touches it.

## What landed

- **`desktop/settings.js`** — `DEFAULTS.secondPass: false` (comment: default off per w197's
  measurement, the same call as two-pass and merge-runs; no hosted-only caveat, since the retry
  rides the same `fixed_pages` seam as the analyst fill); `sanitize` accepts exactly a boolean —
  a typo or an older config falls back to off; every **non-fixture** provider branch (ollama,
  openai, codex, claude) adds `EXTRACT_SECOND_PASS: clean.secondPass ? '1' : '0'` —
  model-independent like `DEBT_BASIS`/`EXTRACT_MERGE_RUNS`, so Ollama passes it through too,
  unlike `EXTRACT_TWO_PASS`. Fixture stays `{}` (demo mode makes no model call either way).
  `desktop/main.js` untouched: the env flows through its existing generic
  `{ ...backendBaseEnv, ...envForConfig(clean) }` spread (v140's arrangement).
- **`backend/app.py`** — `/api/config` echoes the two switches that w207 found had no API
  surface: `"second_pass": os.getenv("EXTRACT_SECOND_PASS", "0") == "1"` (the same reading
  `apply_second_pass` makes) and `"scan_all": os.getenv("EXTRACT_SCAN_ALL", "0") == "1"` (echo
  for confirmation only — the scan stays env-only by design). Echo-only route, like v140's.
- **`frontend/src/main.tsx`** — `DesktopConfig` gains the required `secondPass: boolean`
  (one flagged line, the one place `window.arp`'s shape exists).
- **`frontend/src/api.ts`** — `Config` gains optional `second_pass` / `scan_all` booleans,
  optional exactly like `maturity_basis`/`merge_runs`, so older backends and the suite's
  `/api/config` route mocks stay valid.
- **`frontend/src/components/SettingsView.tsx`** — `DEFAULT_CONFIG.secondPass: false`; a
  `DeepSearchControl` rendered once on the **Extraction** page directly under
  `MergeRunsControl` (same card + `Segmented` primitive, options On/Off, the work order's fixed
  explanation line under it); the status strip gains `deep search <on|off>` and
  `scan all <on|off>` segments sourced from `/api/config` — the basis/merge treatment (v089/
  v140): the echo is the backend's live env value, so the segments render in the plain-browser
  mirror too. Both segments use `!== undefined` guards, not truthiness — a plain `false` is the
  normal off state and must still render.
- **`backend/pipeline/test_runtime.py`** — `RuntimeChecks.test_config_echoes_extraction_switches`:
  default off for both keys; `EXTRACT_SECOND_PASS=1`/`EXTRACT_SCAN_ALL=1` flip both to true;
  explicit `=0` back to false — the same env reading the pipeline makes.
- **`frontend/e2e/tests/settings-deep-search.spec.ts`** — one spec, the work order's round trip:
  flip On → Save → "Saved — backend restarted." → the strip's echo flips (the save's own

- **`docs/API.md`** — the `GET /api/config` row gains `merge_runs` (v140 left it undocumented),
