## 2. The ceiling statistic (the work order's zero-model measure)

Method: on the page `locate.balance_sheet_page` (v139) returns, take the lines containing a
`total_debt.row_synonyms` hit; from each, take the leading bare 1–2-digit tokens after the label
(the note-reference read `extract._row_amounts` already uses: refs sit between label and amounts;
3-digit tokens stop the run, so Swedish-grouped amounts never become refs). Resolve each number to
a page: **note-index entries first** (`NOTE_ENTRY` rows, printed page folio-validated exactly like
`toc_targets`), else **line-start note headings** (`^(?:note|not)\.?\s+\d{1,2}` on any stripped
line — a superset of the page-head scan: acast's "NOTE 29. LEASES" prints mid-page, outside any
150-char head).

| step | companies (of 105) |
|---|---|
| BS page found by the v139 detector | 78 |
| … with ≥1 `row_synonyms` borrowings row | 58 |
| … whose rows carry ≥1 note ref | 49 |
| … with ≥1 ref resolving to a page | 41 |
| … where a resolved page **is a label page** | 16 |
| … where a resolved page is a label page **not already a candidate** (the actual gain) | **1 — acast** |

Two structural facts fell out of the same run:

- **The note-index path is dead weight: zero companies resolve through it.** Every live resolution
  in the corpus goes through line-start note headings. The 105 reports' BS rows carry note numbers,
  but no report's note index (where one exists) is what makes them resolvable — the heading scan
  alone is, and the index machinery (`NOTE_ENTRY` + folio validation) never fires first.
- **If shipped, the mechanism would append 32 new candidate pages across 21 companies, 28 of them
  not label pages** (kabe's BS rows alone carry seven refs; modern_times' torn lease row reads
  amounts 55/61/88 as refs). One class gain, 28 new pass-1 snippets of noise into the page-select
  step v146/v150 identified as the binding constraint — which works *against* the next lane.

## 3. Why the other four adjacent are structurally out of reach (page-level diagnosis)

- **acast 67 — the one hit.** BS p.42 row `Lease liabilities 4, 28, 29 103,330 117,709`; note 29's
  heading line `NOTE 29. LEASES` prints mid-page on p.67 → resolves to the label page. Refs 4/28
  also resolve (p.32, p.63), harmless.
- **inwido 166**: the detector finds **no balance sheet at all** — scanned all 186 pages for BS
  titles anywhere in the text: the group statement's page carries no balance-sheet title in any
  position (only parent-company/prose mentions elsewhere). No BS page → no rows → no refs. A
  locator fix here is a detector-shape change (anchor-only detection), not note numbers.
- **rvrc 95**: BS not found because `CONSOLIDATED BALANCE SHEET` prints **mid-page** (between the
  assets and equity halves), outside the first-150-chars heading window v139 reads. And the label
  page *is* the BS: note refs point away from it (`Lease liabilities 18 7 8` → note 18's page), so
  note resolution can never add p.95 — only a detector fix (companion append) could.
- **smartcraft 58**: BS found (p.68), but it is the assets half and **the report prints no
  borrowings row on either BS half** (p.69's liabilities block has none — the company's only debt
  is leases, whose balances print inside Note 24). No row → no ref. Note 24's heading page is 57
  and the label page 58 is the note's continuation, so even a working resolution leaves 58 only
  adjacent (it already is, via 59).
- **tangen 62**: BS found (p.36, assets half); the borrowings rows (`Skulder till kreditinstitut
  22 …`, `Leasingskulder 21 …`) sit on the continuation p.37, whose BS title line lands at the
  page bottom in PDF text order so the detector skips it. Reading p.37 anyway would not help:
  note 22's heading page is 61 (already a candidate) and the label page 62 — the maturity-table
  continuation — carries **no "Not 22" text anywhere**, so no text-based resolver can map 22→62.

The pattern: the four misses need (a) BS-continuation reading (tangen), (b) mid-page BS titles
(rvrc), (c) anchor-only BS detection (inwido), or (d) selection-level work on note continuation
pages (smartcraft, tangen) — each a separate mechanism with its own crowding risks, all measurable
with `locate_reach` before anyone writes code.

## 5. For the group

1. **The locator's reachability is saturated and its residual is structural.** All five remaining
   non-candidate label pages miss for page-shape reasons, not keyword reasons — the next locator
   work item with real expected value is `balance_sheet_page`'s heading window (rvrc's mid-page
   title, tangen's bottom-of-page title on the continuation), which v139's own docstring already
   scopes ("the same first-150-chars window scored_pages' heading bonus reads"). Measure first:
   title-anywhere + totals-anchor has a known false-positive family (notes *mentioning* the
   balance sheet) that the totals anchor only partly excludes.
2. **Note numbers on BS rows are real signal but not a locator lever**: 49/105 reports print them,
   41/105 resolve, but only 1/105 resolves to a page the window lacks. Where they *do* help is
   provenance (which note owns which BS row) — potential input to a v166-style tie or a review
   hint, not to `candidate_pages`.
3. The two continuation-page label pages (smartcraft 58, tangen 62) are a **selection** problem:
   their notes' title pages resolve fine (57, 61); the label tables sit on the following page. A
   pass-1 that treats a selected note page's +1 as first-class (it already forces pages[0]+1 for
   the top-1 only) would reach both without any new locator machinery.
