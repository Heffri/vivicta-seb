3. **`kb.spec.ts`** (a) — filter "atlas" → exactly 1 row, contains "Atlas Copco" → Open → Results

4. **`kb.spec.ts`** (b) — a KB row with no cached PDF (any of the other ~101 companies — this

   regardless of whether the shared PDF was copied in.
5. **`ask.spec.ts`** — upload one runtime-generated 70-page PDF → lands on Results directly (not

## PDF generator vs fixed fixtures (the work order's choice)

Took the "hand-rolled generator" option, not "two fixed 5 KB PDFs committed to `e2e/fixtures/`".
`make-pdf.ts` builds a minimal valid multi-page PDF (catalog, pages, N page objects with no
`/Contents` — legal per the spec, MuPDF renders it blank) with a byte-exact xref table, entirely
from string concatenation — no `pdf-lib`, no binary blobs in the repo. Page content doesn't matter:
`backend/app.py`'s fixture-mode `run_extract`/`ask` return the canned
`fixtures/sample_extraction.json` / a canned answer regardless of what PDF was uploaded (confirmed
live, see "How it was verified" below); only the page **count** matters, so a citation's page image
(`GET /api/reports/{id}/pages/64.png`) doesn't 404 on a report with fewer than 64 pages. Playwright
takes the generated `Buffer` straight into `setInputFiles` as an in-memory
`{name, mimeType, buffer}` payload — no temp files written to disk, nothing to clean up. The two
multi-upload PDFs use different page counts (2 and 3, not both 2) so their bytes/sizes differ and
the backend's own content-hash-keyed report registration doesn't collapse them into the same
`report_id` — mirrors v021's evidence, which built its two PyMuPDF fixtures the same way for the
same reason.

## Serial, not parallel

`fullyParallel: false` / `workers: 1`. All ten tests share one long-lived dev backend (in-memory
`reports` dict, `data/kb` on disk); `extract-cached.spec.ts` and `kb.spec.ts`'s "filter atlas"
case both register the same cached PDF (`register_library` in `backend/app.py`), which writes
`data/kb/atlas_copco_2025/{meta.json,pages.jsonl}` on its **first** call for that stem per process
(LESSONS.md #27) — two nearly-simultaneous first calls from parallel workers would race on that
write. Ten fast tests don't need the parallelism enough to risk it; serial cost is ~15s per run
(see the four full-suite runs below).

## The merge changed Rail's ARIA role (caught by re-running gates post-merge, not assumed safe)

v027 turns the Rail into a WAI-ARIA Tabs pattern: each tab button is now `role="tab"` inside a
`role="tablist"` (previously plain `role="button"`); disabled tabs switch from the native
`disabled` attribute to `aria-disabled`. `e2e/support/nav.ts`'s `railTab()` helper (used by
`kb.spec.ts` and `ask.spec.ts` to reach the Knowledge base / Ask tabs) queried
`getByRole('navigation').getByRole('button', …)` — that stopped matching anything after the merge.
Fixed by querying `getByRole('tab', …)` instead (still scoped to `<nav>`, still matched by visible
label — no other change needed, since `title`/text stayed the same). Caught this **because** the
work order's baseline note ("基线不一样就以基线为准") and `LESSONS.md` #29 ("验收按合并后状态跑门")
say to re-verify against the merged state rather than trust the pre-merge green — the two
Rail-navigating tests would have been silently broken for the next lane to touch this otherwise.
Confirmed fixed: full suite green twice post-merge (below). The KB "disabled Open button" test is
unaffected either way — that's a plain shadcn `<Button disabled>` inside `KbView.tsx`, not a Rail
tab, so it never used the native/`aria-disabled` distinction this merge introduced.
