## 1. Where the state lives now

`frontend/src/hooks/useBatch.ts` (new) owns the queue: one `BatchItem` per report with a
`stage` (`queued → registering → candidates → extracting → done|failed`, or `skipped` once
"Stop after current" empties the rest), a `result` once it settles, and a `retrying` flag. The
hook is called once in `App.tsx` — not inside `UploadView` — so the state and the async loop
survive `UploadView` unmounting when the user leaves the Extract tab. The loop itself reads/writes
through `itemsRef` (a plain ref mirror of the React state), because a `retry()` invoked mid-loop
needs the *current* item synchronously, and `setState` updates don't apply until the next render.
`UploadView` is now a submission entry only: it gathers picks/library selections/uploads into a
`BatchSpec[]` and hands it to `App`'s `submitBatch`, which resets `results` and calls `batch.start`.

`frontend/src/components/upload/BatchProgress.tsx` (new) renders the list — one row per report,
icon + label + elapsed seconds + stage line, "saved result" badge on `extraction.cached`, and for
failed rows the raw error plus a classified next step (§3) and a per-row Retry. A small "Batch n/m"
pill was also added to `StatusBar.tsx` (always mounted) so a batch running while the user is on a
different tab is still visible, with a click back to Extract.

## 2. A finding that changed the plan: ending a batch never force-navigates, full stop

The work order's own wording ("全批结束不强制切页,给一个查看结果按钮") reads as unconditional, but
the safer-looking reading — auto-advance only if the user never left Extract, otherwise don't yank
them back — is what a first pass implemented, since it's the minimal diff from the old `onDone`
behaviour and doesn't touch any of the six pre-existing specs that assert on Results/Compare content
right after clicking Extract.

That first pass is wrong, demonstrated rather than assumed: `extract-batch-progress.spec.ts`'s own
Stop-after-current and retry tests **failed** under it, because the conditional still fires the
instant the (partial) batch settles *while the user is still on Extract* — which is exactly the
moment a user reading a failed item's next step, or having just clicked "Stop after current", is
sitting there. The screenshot in the failed run showed the app already on Results, mid-`git status`
of the bug this ticket exists to fix. Ending a batch now never switches tabs, unconditionally;
`onQueueDone` was removed from the hook entirely. §5 below lists the six pre-existing specs this
made stale (all in this lane's own Extract-flow territory) and how they were fixed — one added step,
`click View results`, before the assertions that used to fire automatically.

## 3. Error triage (work order §3)

Two different endpoints can both return 409, so the classification is keyed on *which step failed*,
not the status code alone (`useBatch.ts::classify`):

| Failed at | Status | Shown as | Actions |
|---|---|---|---|
| `getReport()` (fetch/register/upload) | 409 | "No saved text or local PDF for this one without a download. Check "Allow PDF download" above, then retry." | Retry this one |
| `extractSection()` | 409 | "This report already has a human-reviewed result, which was kept as-is." | Open Knowledge base (no retry — retrying would just 409 again by design) |
| `extractSection()` | 422 | "No text found on the candidate pages — this file may need OCR, or try a different one." | Open Settings, Retry this one |
| `extractSection()` | 502 | "The model provider failed. Check Settings › Test connection, then retry just this one." | Open Settings, Retry this one |
| anything else | 400/404/network/… | raw message only, no canned copy | Retry this one |

Retry re-runs exactly one item through the same registering → candidates → extracting pipeline
(`useBatch.ts::runItem`, shared by the first attempt and by retry — not a special-cased second code
path). For directory/web picks, the closure reads `year`/`downloadPdf` off a ref synced from the
live checkbox state, not a snapshot from whenever the batch was submitted — otherwise checking
"Allow PDF download" *after* a download-needed failure and clicking Retry would silently redo the
same failing request. No automatic re-POST anywhere (v072's lesson): every retry is one explicit click.

## 4. Stop after current

"Stop after current" sets a flag checked once per loop iteration, *before* starting the next item —
the in-flight item always finishes normally. Everything still `queued` at that point becomes
`skipped` ("Stopped after current — not started"); nothing already running is aborted mid-flight
(there is no client-side cancellation of the server-side call, matching v072's finding that the
backend keeps working and billing regardless of what the client does).

## 5. Six pre-existing specs updated for §2

All within this lane's own Extract-flow territory (none touch ResultsView/CompareView/KbView code,
only the test steps that walk through Extract to reach them) — each gained one line, clicking
"View results" where it used to arrive there automatically:

- `ask.spec.ts`, `extract-cached.spec.ts`, `extract-candidates.spec.ts` (2 of its 3 tests — the
  saved-sample test bypasses the batch entirely and needed no change), `verification.spec.ts` (5 of

- `extract-multi-upload.spec.ts` needed one more fix beyond that: the button appears as soon as the

  Fixed by waiting for the button's own label, `View results (2)`, before clicking.

## 7. Red → green (the three new scenarios)

Observed by temporarily reverting `App.tsx`/`UploadView.tsx`/`StatusBar.tsx` to the dispatch
baseline (`git stash push -u` on just those three files, applied — not popped — and dropped after,
per the shared-stash-stack rule) and running only `extract-batch-progress.spec.ts` against it:

- **Red** (baseline, no `BatchProgress`): all three tests fail — `getByRole('list', { name: 'Batch
  progress' })` never resolves, since the list doesn't exist yet. Not a copy of the fix's own
  expectations: the assertions describe the *absence* the work order names (no per-report stage
  list, nothing to switch tabs and come back to).
- **Green** (restored): same three tests, `3 passed` — tab-switch-and-back keeps both rows and
  their final state; the 502'd report's Retry button re-runs only that one (three `/extract` calls
  total: the initial 502, the other report's own success, then just the retry — never a fourth call
  for the report that already succeeded); Stop after current finishes the in-flight report and marks
  the rest `skipped` without a second `/extract` call ever firing.
- Full suite red→green isn't reported for the six adjusted pre-existing specs — they encode the
  *old* forced-navigation behaviour by construction, so reverting to baseline would make them pass
  again (that's not a meaningful red for §2's fix). Their own assertions besides the navigation step
  are unchanged from before this lane.
