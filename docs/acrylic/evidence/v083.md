## Step 1 — migration, verbatim, zero behavior change (commit `dd2b34a`)

`_DEBT_ROW_SYNONYMS` (11 words, `extract.py`'s own private module constant, the sole read site being
`_bucket_total_row`'s `debt_sf = {"synonyms": _DEBT_ROW_SYNONYMS}`) moved to
`backend/schemas/debt_maturity.json`'s `total_debt.row_synonyms`, content unchanged byte for byte. The
private constant is **deleted**, not kept as a code-level default for a missing schema key — chosen over
"keep it as a fallback default" (the work order's own either/or) because `_fill_bucket_columns`/
`_bucket_total_row` is schema-generic by design (`_identity_parts`'s own docstring: "generic, not a
debt_maturity-only hook... any schema whose check has the same shape... qualifies") while the word list
itself is debt-specific vocabulary ("borrowing", "upplåning", ...) — a blind code-level default would
silently inject debt wording into any future schema whose own identity check has the same `null_as_zero`
shape but is not about debt. The read site is now `debt_sf = {"synonyms": total_sf.get("row_synonyms", [])}`
— `total_sf` is already the schema's own `total_debt` field dict at that call site (`_fill_bucket_columns`
passes `total_sf = next(sf for sf in sfs if sf["key"] == total_key)`), so this is a pure "read the schema
key that's already in hand" change, matching every other optional-schema-list read in the file
(`sf.get("synonyms", [])`, `total_sf.get("header_synonyms", [])`, `schema.get("ignore_header_synonyms", [])`).

### Direction safety of the two `row_synonyms` additions

v060 Finding 2 is the reason bare `"loan"`/`"loans"` is *not* in this list: a bank's own asset-side
"Loans to credit institutions"/"Loans to the public" (money it lent out) prefix-matched bare `"loan"` and
out-competed the real debt row (Norion Bank, seed4-kb). Both new words are the **exact phrase actually
printed**, not a bare root word, and neither one is a prefix of the dangerous asset-side wording:
`"lån kreditinstitut"` (no "till"/"to") does not prefix-match a lending-direction row like
`"Lån till kreditinstitut"` (the intervening "till" breaks the prefix); `"liabilities to credit
institutions"` is directionally unambiguous on its own terms — "liabilities" is always the reporting
company's own obligation, regardless of which way the counterparty phrase points. Confirmed, not just
argued: the full replay below re-runs every stored `debt_maturity` extraction in `data/kb` +
seed1-kb..seed8-kb (179 companies, including seed4-kb's Norion Bank) and finds **zero** changed — if
either new word had swept in a wrong row anywhere in the corpus the same way bare `loan` did in v060, it
would show up there as a CHANGED entry, the same mechanism that caught the original bug.

### Tången (v082 Finding 1) — row-label gap fixed; a *separate*, pre-existing gap still blocks the real page

`_bucket_total_row`'s own candidacy gate now recognises `"Lån Kreditinstitut"` (confirmed via direct
`_bucket_total_row`/`_label_known` calls on the real row). Proven closing **end to end** on an isolated
single-year replay of the real p.62 text (2024's duplicate block removed, to separate this fix from the
unrelated issue below) — new `test_confidence.py` case, model answer all-null in, real page text:

```
before (v082, pass1, page 62 in the two-pass window): total_debt=null due_within_1_year=null due_1_to_5_years=null due_after_5_years=57486@0.5
after (isolated single-year replay):                  total_debt=588199@0.9 due_within_1_year=141734@0.9 due_1_to_5_years=388979@1.0 due_after_5_years=57486@0.9
check maturity_sums_to_total: passed (141734 + (137898+251081) + 57486 == 588199, exactly)
```

**But the real p.62 page prints the same row label twice** (once under "31 december 2025", once under
"31 december 2024", each with its own 4-bucket-column amounts) — `_bucket_total_row` finds both as
candidates and, since neither this round nor the model's own pass1 answer independently supplies a
trustworthy `known_total` to narrow by (pass1's own `total_debt` was null; even seeding it with the
*correct* 588199 does not help — traced below), it correctly declines rather than guess:

```
replay of v082's real pass1 JSON through extract() with the fix applied, pages=[62,63], real page text:
  (all four fields unchanged from before: total_debt=null, due_within_1_year=null, due_1_to_5_years=null, due_after_5_years=57486@0.5 — no regression)
  + new warning: "total_debt: 2 candidate debt rows for the bucket table ('Lån Kreditinstitut', 'Lån Kreditinstitut') -- ambiguous, none used"
```

Traced one level further (not assumed): `_bucket_total_row`'s own `known_total` narrowing calls
`_row_amounts(rows[i])` **without** an `ncols` hint to test whether a candidate row prints the known
total among its own amounts. Without that hint, this table's tightly Swedish-space-grouped thousands
("57 486 588 199") merge into one unrecognisable blob, so **even seeding `known_total=588199` (the
correct figure) does not narrow the two candidates** — confirmed by direct `_bucket_total_row` call, not
inferred. That narrowing behaviour lives inside `_bucket_total_row` itself, one of the six functions this
round's territory does not extend to (word-list content only, no mechanism change) — flagged here, the
same way v082 flagged the `_row_amounts` "37" drop, as a concrete future lever: teach the `known_total`
narrowing step to re-read a candidate with the header's own column count before comparing, not the
unhinted parse. `test_confidence.py`'s new second case asserts this exact decline (`_bucket_total_row(...)
== []` with that exact warning) on the real two-year page text, so a future fix to the narrowing step is
the one that should flip it, not a regression in this lane's own mechanism.

### Instalco (v082 Finding 2) — row-label gap fixed; zero end-to-end change, matches v082 exactly

Replayed both stored passes (`instalco_2025.pass1.debt_maturity.json`, `.pass2...json`) through
`extract()` with the fix applied, pages=[127,128], real page text — **byte-identical to before both
times**: `total_debt=3122@0.9` (unchanged), `due_within_1_year`/`due_1_to_5_years`/`due_after_5_years`
all stay null, check still `missing: due_within_1_year`. Not a regression — traced why, directly:

- `"Liabilities to credit institutions"` **is** now a recognised row_synonym and **is** tested as a
  candidate (confirmed via instrumented `_bucket_header`/`_bucket_total_row` calls), but its own header
  window reads as only 5 column keys (`total, due_within_1_year, due_within_1_year, due_1_to_5_years,
  due_after_5_years`) against the row's own 6 printed amounts (`–, –, 3209, –, 3209, 3122`) — a pre-existing
  `_bucket_header` limitation, not this round's own new word: the header's carrying-amount phrase
  ("31/12/2025 Carrying amount receivables/ payables") sits on its own line with no bucket word on that
  same line, so `_bucket_header`'s `has_carry` gate (which only keeps a `total:carrying` hit on a line that
  *also* names a bucket, v076's own "dropped from lines that name no bucket" rule) never fires, and the
  bare "Total" from a *different*, unrelated line ("Total contractual cash flows") fills the total slot
  instead — one column short of the row's real 6. Length mismatch (6 ≠ 5) → declined, same as before.
- The table's own bare-Total row (`"Total 1,151 160 3,583 37 4,931 4,802"`) is tried too (pre-existing,
  unrelated to `row_synonyms`) and rejected by the existing `over` safety valve — this is v082 Finding 2's
  own already-documented `_row_amounts` "37 silently dropped" shape, `parse.py`/`extract.py` territory this
  round does not touch either.

Both blockers are `_bucket_header`/`_row_amounts` mechanism-layer, confirmed identical to v082's own
conclusion ("adding the missing fourth word... changes nothing — confirmed empirically"); this round adds
one more confirmation (`row_synonyms` itself is not the remaining blocker either) rather than a new gap.
