## Quote-highlight matching rules (and what they miss)

`highlightQuote` builds one regex from the value's digits and marks the **first** match inside
`source.quote`:

- thousands groups joined by an *optional* separator class: regular/NBSP/thin-narrow space, `.`, `,`,
  `'` — so `168343` matches `168 343`, `168,343`, `168343`, `168'343`;
- decimal `.` or `,` (Swedish), plus trailing zeros so a stored `4.8` still matches printed `4,80`;
- negatives: en dash `–` (U+2013, what Atlas Copco actually prints), real minus `−`, hyphen, accounting
  parentheses `(96 131)`, or bare digits;
- digit boundaries `(?<!\d)` / `(?![.,]?\d)` so a stored `5` never lights up inside `5.43`, and `68343`
  doesn't match inside `1168343`.

Verified against the real data: all 15 sourced fields of Atlas Copco p.106 + the fixture extraction
match, including `–96 131` (en dash), `34 114` behind footnote digits (`Operating profit 3, 4, 5, 15 34 114`),
and `5.43`/`4,81` decimals. Checker script output (lane temp dir, not committed): 34/34 cases ok.

**Known misses / accepted limitations:**

- a value whose digits are a *suffix group of a bigger number printed in its quote* still lights up the
  fragment — value `343` in quote `Revenues 3 168 343 176 771` highlights `343` inside `168 343`.
  Blocking that shape would also block the real footnote-prefixed matches above (`3 168 343` is
  indistinguishable from a 7-digit number by text alone), and each field only ever highlights inside
  its own verified quote, so the fragment case was judged rarer than the footnote case.
- values printed with unit-scaled text the backend didn't store (e.g. stored `209` for printed `20.9%`)
  or inside table columns the quote doesn't contain verbatim → no match → plain quote, by design
  ("匹配不到就整段引用照常显示、不报错").
- `String(value)` exponents (≥1e21) would not match; no report number is that large.

## Notes for the merger

- Registering `atlas_copco_2025.pdf` (real PDF, matching sha) rewrote `data/kb/atlas_copco_2025/
  {meta.json,pages.jsonl}` in the working tree — the backend appends `"parser": 2` to meta.json and
  re-serializes pages.jsonl on every first registration per process. Harmless (same sha/content), but
  **not committed here**; anyone running the backend against a real PDF in `data/reports/` will see the
  same two-file diff and should drop it from their commit too.
- Opening a KB row whose PDF is absent fails the whole open with 409 ("no longer cached") — not just the
  page images. common.md's "没有 PDF 的只能看字段" understates it; only Atlas Copco is openable offline.
