# v023 — `_clean_label` strips magnitude-prefixed currency units (MSEK / TSEK / KSEK / MEUR / kSEK …) — evidence

Branch `ao/vivicta-seb-18/v023-unit-labels`, off `origin/acrylic`.
Work order: the v018 Findings item — `_clean_label`'s currency strip only lists bare unit words
(`\b(?:SEK|EUR|...)\b`), so a magnitude prefix glued directly ahead of the code (`MSEK`, `TSEK`, `KSEK`,
`MEUR`, `kSEK`, `(MSEK)`) breaks the required word boundary and the whole token survives uncleaned —
independent of any footnote, a different gap than v018's own footnote-marker fix. Offline work: no
services started, no model calls, `data/` untouched.

## The gap

`_clean_label`'s currency strip before this lane:

```python
label = re.sub(r",?\s*\(?\b(?:SEK|EUR|USD|NOK|DKK|ISK|GBP|CHF|kr)\b\)?", "", label, flags=re.I)
```

`\bSEK\b` requires a word-boundary transition immediately before the "S". In `"MSEK"`, the character
before "S" is "M" — both are `\w`, so there is no boundary there and the regex never matches, even though
the whole token is only two extra letters away from the same currency word. `"Revenue, MSEK"` therefore
kept `", msek"` in its cleaned form while `"Revenue"` alone had nothing to strip — the two would only
compare equal by coincidence, if some other string also carried the literal `", msek"` tail (v018 checked:
no schema synonym does today, so this hadn't surfaced as a `label_known`/`own_row_exact` mismatch yet, only
as a latent asymmetry).

## What changed (`_clean_label`'s currency-strip line only, 1 line touched)

```python
label = re.sub(r",?\s*\(?\b(?:[kmbt]?(?:SEK|EUR|USD|NOK|DKK|ISK|GBP)|CHF|kr)\b\)?", "", label, flags=re.I)
```

One optional magnitude letter (`k`/`m`/`b`/`t`, case-insensitive via the existing `flags=re.I` — `t` also
covers the Swedish "tusen" convention for thousand) is now allowed immediately before the seven currency
codes the work order names (`SEK`/`EUR`/`USD`/`NOK`/`DKK`/`GBP`/`ISK`); `CHF` and the bare word `kr` are
left exactly as before (out of the work order's scope — no magnitude-prefix form of either is in the
corpus or the ticket). The `\b` anchors move with the group: for `"MSEK"` the boundary now sits before the
"M" (transition from whatever precedes it — comma, space, `(`, or start of label — into a word character),
and the closing `\b` still sits right after the code's last letter, same as before. A bare code with no
prefix (`"SEK"`) still matches exactly as it did (the prefix class matches zero characters), so
`"EPS, SEK"` → `"eps"` is unchanged. The pattern mirrors the one the file already uses for the unrelated
`_UNIT` constant a few lines down (`[MKT](?:SEK|EUR|USD|NOK|DKK|GBP)`, used for page-header unit
detection) — same "one magnitude letter glued to a currency code" shape, applied here to label cleaning
instead.

Because the match still requires a boundary on *both* sides of the whole prefix+code token, a real word
that merely contains one of these letters followed by a currency-like substring is not at risk: the
regex only starts consuming at a boundary, so a preceding word's own last letter is never mistaken for the
prefix (there is always a space/comma/paren between two label words in the extracted text, never a glued
join) — the "don't touch a word in the middle of the label" requirement falls out of the existing
boundary anchoring, not a new positional restriction. `_row_label`, `_label_known`, `_statement_row`, the
sum-repair call site and every other `_clean_label` caller inherit the fix automatically, same as v018.

`_ccy` (the separate function that turns a `unit` field like `"MSEK"` into the base currency `"SEK"` for
value-scale purposes) and the `_UNIT` constant are untouched — different function, different job (scale
extraction from the `unit` field, not label text cleaning); confirmed unrelated by reading both before
editing.

## Test cases (4 new assertions, +11/−1 in `test_confidence.py`)

1. The work order's own pair: `_clean_label("Revenue, MSEK") == _clean_label("Revenue") == "revenue"`.
2. Case-insensitivity across the three prefix letters the ticket names besides M:
   `_clean_label("Revenue, TSEK") == _clean_label("Revenue, KSEK") == _clean_label("Revenue, kSEK") == "revenue"`
   (uppercase T, uppercase K, lowercase k — one assertion, three input shapes).
3. A different currency code: `_clean_label("Net sales, MEUR") == _clean_label("Net sales") == "net sales"`.
4. The parenthesised shape: `_clean_label("Net sales (MSEK)") == _clean_label("Net sales")`.

Plus the two non-regressions the work order calls out by name, both already covered by existing asserts
and reconfirmed unchanged: `_clean_label("1-5 years") == _clean_label("1–5 years") == "1-5years"` /
`_clean_label("Within 1 year") == "within1year"` (digits that are the label's own meaning), and
`_clean_label("EPS, SEK1)") == _clean_label("EPS, SEK") == "eps"` (bare code, no magnitude prefix). The
pre-existing `"Earnings per share, MSEK2)"` assertion (v018) still passes but its inline comment was
updated — before this lane both sides were equal by coincidence (both kept `", msek"` uncleaned); after
this lane both sides are equal because both now fully strip the unit.
