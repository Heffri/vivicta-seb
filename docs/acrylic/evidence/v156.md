## The rule (`backend/pipeline/extract.py`, additions only)

- **`_window_rows_derive(...)`** — v126's window family, deriving on a NULL bucket answer (v096's
  adoption) instead of only keeping a sum the model itself answered. Same family and column gates
  as `_window_row_sum`, reused verbatim: rows of one page whose window (`_row_bucket_span` →
  `_span_bucket`) falls entirely inside the bucket's range, at least two of them, summed in the
  one column where the note's own total row ties to the already-verified `total_debt` — which is
  what makes "the table's total row" and "the verified total_debt" the same number here. In its
  place stands the **closure gate** (v096-style, through `maturity_sums_to_total`): family sum +
  the other buckets' already-read values (a bucket still null contributes 0 — its rows would sit
  inside the total too, so a partial family cannot close) must reach that total. Write:
  `value_derived`, v126's quote convention (joined rows when verbatim, else the first row),
  raw_label = wordings joined " + ", warning
  `"{key}: derived as the sum of {n} rows inside its window on page {p} ({first!r} … {last!r}); closes on {total}"`.
  Every decline is silent (v110's convention) — the write is the only warning the walk emits. One
  call site, right after `_subtotal_pair_fill`.
- **`_window_subtotal_row(row, key)`** — the printed-subtotal guard: a total-labelled row carrying
  the bucket's own window wording at its figure edge ("Total Repayment within 2–5 yr. 200 190")
  stands the walk down for that bucket — the printed row is the bucket's read, and a family
  disagreeing with it is the report's inconsistency, not a sum to redo. This guard is what keeps
  v126's existing counter-example page null (see Red → green): without it the new on-null rule
  would derive 1–5y = 150 over that page's printed 200 and break v126's cases.
- **`_wording_window(w)`** — the window half of the v126 wording grammar, split out of
  `_row_bucket_span` (which delegates, behavior byte-identical) so the guard can ask which window
  a TOTAL-labelled row names — a thing `_row_bucket_span` itself refuses.
- **`_subtotal_pair_fill._closes`** (the sdiptech fix) — see below.
- `_window_row_sum`, `_finer_split_rows`, `_bucket_span`, `_span_bucket`, `_row_amounts`,
  `_table_scope`, `_page_rows`, `_row_label`, the schema word lists: untouched. v126's rescue
  path: untouched.

v131's method, gate by gate: title gate passes (t=1), pair (3, 9, 10, 15) found, scope
"unknown", both Summas resolve year header `(0, 2)`, quote span verifies — **the only failing
gate is `_closes`**, and it fails three ways at once: the bare `*` between label and figures

of the closure (B then misses its 10: 437 ≠ 446). The fix: inside `_closes` only, a row that
looks like furniture (or a star row that reads short) is arbitrated by **the section's own ncols
read of the star-stripped row** — ncols real (non-year) figures make it a data row; anything else
stays furniture. The per-column closures still decide everything: A = 2309+800+342+597+2 = 4050 ≈
4049 / 1910+811+393+910+4 = 4028 ≈ 4027; B = 10+119+317+1 = 447 ≈ 446 / 537 = 537. Red (pristine
`033bf64` + merged baseline module both observed): total null; green: **4495 @1.0
`value_derived`**, w1y untouched where stored (446), written from Summa B where null.
