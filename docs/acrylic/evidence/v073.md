## Shape definition

A third way a maturity note prints (beside bucket-rows, `_between_rows`, and bucket-columns,
`_fill_bucket_columns`): **one row per loan/lease**, each naming its own due date, year, or year-range,
then its own carrying amount — no bucket label anywhere, no single row with all three buckets as
columns. Proact's own p.103 (`docs/acrylic/evidence/v063.md` gap 2):

```
Bank loan, Svensk Exportkredit ... 16 Jul 2026 216,360
Lease liability ... 2026 96,098
Lease liability ... 2027-2030 166,153
Total interest-bearing liabilities 478,611
```

216,360 + 96,098 = 312,458 (due within 1 year); 166,153 (due 1–5 years); 312,458 + 166,153 = 478,611
to the cent — the model's earlier read of this exact shape (v063) was arithmetically correct and was
only lost to an unrelated, pre-existing bug (the segment-column re-read, `_identity_closes`'s own
territory, out of scope here).

## Rule and gates

New function `_date_bucket_derive` (`backend/pipeline/extract.py`), hooked into the derivation chain at
the same "missing operand" trigger point as `_between_rows` (an `elif` tried only when `_between_rows`
finds fewer than two other real operands to sit between — a date-shaped note proves every null bucket
at once, so it is tried independently of which single key `missing` happened to name).

- **Scope**: anchored on `total_debt`'s own verified row on its own page — a bounded window (15 rows)
  looked *upward* only, never a page-wide search. Reusing `_operand_table_rows` (v058) directly does not
  fit: its year-header boundary test (`_year_run`) fires on a bare year-**range** value ("2027-2030") as
  if it were a 2-column table header, cutting the window down to one row before it ever reaches the
  instruments above.
- **Row shape**: `<label> … <date|year|year-range> … <amount>`. A day-month-year date buckets directly;
  a year-range or bare year buckets by comparing its *start* and *end* against the balance-sheet date
  (`fye.replace(year=fye.year+1)` / `+5`, exact calendar arithmetic, not a fixed day-count — see Findings
  2) — when the two ends land in **different** buckets, the row "straddles" and the **whole derivation**
  is abandoned (not just that row), per the work order's own "don't guess" instruction.
- **Balance sheet date**: 31 Dec of `fiscal_year` by default, or the day/month a caption in the same
  window states for that year — but only when nothing `_row_amounts` would call an amount follows the
  date on that row, so an instrument's own due-date row (nil "-" included) is never mistaken for the
  table's caption.
- **Guard against running headers/watermarks**: a row naming its own maturity three times or more is
  never a candidate. Proact's own page literally carries a repeated-watermark artifact
  (`_page_rows` glues a 3x-repeated footer into one line, "...Report Report Report 2025 2025 2025") and
  a 4-column "31 Dec 2025 31 Dec 2024 31 Dec 2025 31 Dec 2024" caption — both would otherwise inject a
  bogus addend and were caught empirically (Findings 4), not just by review.
- **Amount**: each row's own last printed number (`_row_amounts(r)[-1]`) — a single-column list like
  this has no year header for `_row_year_column` to key a column off.
- **Adoption gate**: only when the newly-proposed bucket(s) make `maturity_sums_to_total` pass exactly
  (`_check`'s own ±2 tolerance) against whatever the model already filled — buckets the model already
  answered are never overwritten (v066's closure guard runs first structurally, since this only ever
  proposes values for fields that are still null).
- Evidence: `quote_on_page` + `value_derived` — except when a bucket's own value happens to be a single
  row's literal printed number, in which case only `quote_on_page` (+ `value_in_quote`, added later by
  `score_field` itself) applies, never both (`WEIGHTS`'s own "never both" invariant — see Findings 4).
  `quote` = the contiguous span of rows from the first contributing row through to (not including)
  the total row, verified verbatim via `quote_on_page`.

## Findings (ranked for the group)

1. **Proact's date-per-instrument note now closes exactly** (312,458 + 166,153 = 478,611): the round's
   named gap-2 miss (v063) is mechanically fixed. The *stored* v063 extraction still won't replay fixed,
   since a different, pre-existing bug (segment-column) already zeroed `due_within_1_year` before this
   mechanism's trigger point — worth a fresh live re-extraction in a future round to see the two
   mechanisms interact for real, not just replay the old corrupted value.
2. **Nederman is a fourth variant worth naming**: a genuine date-per-instrument table exists on the
   page, but (a) `total_debt`'s own citation sits on a sentence structurally distant from it (several
   unrelated sub-tables between), so this lane's "total's own row, look upward" scope never reaches it —
   by design, the same conservatism `_operand_table_rows` (v058) already applies elsewhere; and (b) even
   a reachable read wouldn't close: the note's lease line ("Lease liabilities 538.7") carries no
   individual due date, so a per-instrument sum tops out at 1,936.6 of the 2,358.0 needed for the
   non-current bucket. Two independent, honest reasons to decline — not a bug, but a real boundary of
   "exact closure only."
3. **HANZA and Stillfront confirm the shape boundary holds**: neither carries a maturity date/year
   anywhere near its total row (HANZA is bucket-column, Stillfront is duration-labelled component rows),
   and the mechanism correctly finds nothing rather than reaching for an unrelated number.
4. **Two implementation bugs caught only by running the code against the real pages, not by review**:
   (a) an initial fixed 366-day cutoff mis-classified a year-range's own start when it landed exactly on
   the boundary (Proact's own "2027" is *exactly* 366 days after a 2025-12-31 balance date), manufacturing
   a false "straddle" that would have silently killed the one real win this lane exists for — fixed by
   switching to exact calendar-date comparison (`fye.replace(year=fye.year+1)`); (b) naively tagging
   every derived bucket `value_derived` double-counted with `score_field`'s own `value_in_quote` for a
   bucket whose value is a single row's literal printed number, pushing confidence past 1.0 — fixed by
   only tagging `value_derived` when the value is not itself literally in the quote, matching
   `_fill_bucket_columns`'s existing pattern. Both were only visible once the real Proact page text was
   run through the function, not from reading the regex.
