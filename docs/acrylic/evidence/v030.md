## `paths.py` — the single resolution point

Two roots (module docstring has the full contract):
- `resource_dir()` — read-only, bundled: `schemas/`, `fixtures/`. `backend/` in dev, `sys._MEIPASS` when frozen.
- `data_dir()` — read-write: `ARP_DATA_DIR` if set, else `resource_dir().parent / "data"` (`<repo>/data` in dev;
  next to `backend.exe` when frozen, since `_MEIPASS`'s parent is the onedir folder containing the exe).

`kb_dir()` keeps its **pre-existing** semantics on purpose: `KB_DIR` (if set) resolves against `resource_dir()`,
not `data_dir()`, and wins over `ARP_DATA_DIR` — matching the old `(HERE / os.getenv("KB_DIR", "../data/kb"))`
exactly, because `KB_DIR` is a documented `.env` override independent of the new desktop-packaging env. All of
`paths.py`'s functions are called live (no module-level constant snapshots paths.py itself), same discipline
`kb.py`'s own `kb_dir()` already used and documents ("function, not constant: app.py calls load_dotenv() after
importing us") — `fetch.py`'s old `REPORTS`/`INDEX` module-level constants broke that discipline (computed at
`import fetch` time, before app.py's `load_dotenv()` runs), so `fetch_report()`'s `dest_dir` default became a
lazy `paths.reports_dir()` call instead, and `_load_index()`/the manifest write now derive `index.json` from the
actual `dest_dir` parameter rather than a separately-computed global (a latent inconsistency if a caller ever
passed a non-default `dest_dir` — nobody currently does, `app.py` always passes its own `LIBRARY` explicitly, so
this is a pure path-resolution fix, not a behavior change for any existing caller).

**Byte-identical dev default, verified two ways**: (1) `python -m pipeline.test_confidence` / `test_parse` /
`test_kb` — none of which touch `app.py`'s paths — ran green *before* touching any file and stayed green after;
(2) new `test_paths.py` asserts the unset-env dev values equal the exact pre-v030 hardcoded paths
(`backend/`, `backend/schemas`, `backend/fixtures/sample_extraction.json`, `<repo>/data{,/reports,/kb,
/companies.json}`), plus `ARP_DATA_DIR`, `KB_DIR`-relative, `KB_DIR`-absolute, and a simulated-frozen
(`sys.frozen`/`sys._MEIPASS` monkeypatched) case for `resource_dir()`/`data_dir()`. `import app` in dev mode
(no env set) resolves every constant to the old location except one deliberate change below.

**One intentional dev-mode behavior change**: `uploads_dir()` is `data_dir()/uploads` per the brief (auto-mkdir),
so uploads now land in `<repo>/data/uploads/` instead of the old `backend/uploads/` — both gitignored (`.gitignore`
updated: `backend/uploads/` → `data/uploads/`), and no existing test or script referenced the old location (grepped
the repo first). Flagging this explicitly since it's the one default-path change that isn't "byte-identical."

## Static frontend hosting — a real bug found and fixed, not just written

First cut mounted `SPAStaticFiles(StaticFiles)` and checked `response.status_code == 404` after calling
`super().get_response()` to decide whether to fall back to `index.html`. That never fires: Starlette's
`StaticFiles.get_response` signals a miss by **raising** `HTTPException(404)`, not by returning a 404 response —
confirmed by testing (`/reports/some-client-route` came back as FastAPI's default `{"detail":"Not Found"}` JSON,
not `index.html`). Fixed with a `try/except StarletteHTTPException`. Second bug, found the same way: the `api/`
prefix guard (so an `/api/*` typo that matched no real route still 404s instead of silently returning HTML) used
`path.startswith("api/")`, but `StaticFiles.get_path()` builds `path` with `os.path.join`/`os.path.normpath`,
which use **backslash** on Windows — so `path` was actually `"api\\does-not-exist"` and the guard silently never
matched (confirmed: `/api/does-not-exist` returned **200** with `index.html`, not 404, until fixed). Now compares
via `Path(path).parts[:1] != ("api",)`, which parses both separators correctly on Windows. Re-verified after the
fix (see table below) — both bugs would have shipped invisibly against a "looks reasonable" read of the code;
neither showed up until actually hitting the running exe.

## PyInstaller build

`pip install -r requirements-build.txt` (adds `pyinstaller==6.22.3` on top of `requirements.txt`, all already
present in the shared venv) then `python build_exe.py` → `pyinstaller backend.spec --noconfirm`, onedir:

```
dist/backend/backend.exe        12,595,467 bytes (~12 MB)
dist/backend/  (whole onedir)   ~102 MB, 214 files
```

Hidden imports needed beyond PyInstaller's automatic analysis: `uvicorn.loops.asyncio` / `protocols.http.h11_impl`
/ `lifespan.on` (`app.py`'s `main()` passes `loop="asyncio", http="h11", ws="none"` explicitly to `uvicorn.run()`
so only these concrete implementations need declaring — uvicorn resolves them by dotted-string import at runtime,
invisible to static analysis regardless of which loop/protocol you pick), `multipart`, `dotenv`, `pptx`, `openai`.
`collect_data_files` for `pymupdf` and `pptx` (both ship non-code package data — font/ICC resources and the
`default.pptx` template — that PyInstaller's import-graph analysis can't see). One build-time warning, expected
and harmless: `Hidden import "tzdata" not found` (a hook-contrib suggestion for `zoneinfo`; nothing in this
codebase does named-timezone conversion, only `datetime.date.today()`). Built clean on the **first real attempt**
— no missing-DLL or import errors from `pymupdf`/`openai`/`pptx` at runtime, so the "known PyInstaller pitfalls"
the brief warned about did not materialize here (Windows, Python 3.12.10, PyInstaller 6.22.3, current package
versions — recorded in case a different combination hits them later).

`console=True` (kept, not switched to windowed): the desktop shell manages/hides the process itself; a
`console=False` build would make `sys.stdout`/`sys.stderr` `None` inside the frozen exe, which the new logging
tee (below) writes to directly.
