## Verdict

**Not a product bug. All 5 failures were stale tests** — three test locations still assumed the
Knowledge base tab defaults to the curated Wallenberg roster (11 companies) and shares its
collection choice with the rest of the app. Both assumptions were deliberately retired by
`4c94188` ("fix: recover historical reports and browser-only downloads", merged via `m03` /
`d652d10`, 2026-09-22 15:39), which gave `KbView.tsx` its own collection preference
(`arp-kb-view-collection`, default `all`) specifically so a newly discovered or downloaded report
outside the curated roster is never hidden. That intent is spelled out in
`docs/historical-report-discovery-handoff.md`: *"Knowledge base: … keep its collection filter
independent of Extract with a clear way to show all saved reports"* — and it ships with its own
UI banner ("This collection hides reports from other companies…" + "Show all saved reports") and
its own passing regression, `kb-new-reports.spec.ts:30` *"Knowledge base defaults to all reports
independently of the Extract collection"*. Nobody had run the full browser suite against that
change before now (`m03`'s own evidence says so explicitly), so the 3 stale locations went red
and stayed red through `w215`'s later audit, which correctly found them pre-existing and
unrelated to its refactor.

The underlying filter/scope computation itself is correct and untouched — confirmed against the
running backend, not inferred from source:

```
GET /api/kb?collection_name=wallenberg           -> 11 companies  (ABB, Atlas Copco, Electrolux
                                                      Professional, Ericsson, Husqvarna Group,
                                                      Investor AB, Saab, Saab (svenska), SEB, SKF,
                                                      Stora Enso)
GET /api/kb?collection_name=midcap                -> 104 companies
GET /api/kb?collection_name=all  (= no param)      -> 206 companies
GET /api/kb/maturity-wall?collection=wallenberg    -> 1 row  (Ericsson, Telecommunications,
                                                      complete=false, share=0.1082)
GET /api/kb/maturity-wall?collection=all           -> 105 rows across 10 sectors
```

"Wallenberg = 11" is still exactly right today; the tests were never wrong about the backend, only
about which collection the KB tab shows by default and whether it echoes the Extract tab's choice.

## What changed and why it's the minimal diff

No product code touched — `git diff --stat` against baseline shows exactly two files, both under
`frontend/e2e/tests/`. The 3-tab-vs-1 (KB defaults independently to All) split is a deliberate,
documented, already-tested design decision (`kb-new-reports.spec.ts`), not an accident, so per the
work order's own branching rule this is the "stale test" path, not the "fix product" path.

- **`kb.spec.ts:89`** rewritten to mock its own 5-company roster (2 Wallenberg-scoped, 3 outside)
  instead of asserting on the live `data/kb` company count, which only grows as other lanes save
  reports into it (the old test's own comment already conceded this: *"it keeps growing as other
  tests upload, so no exact number here"* — that's the smell that made it fragile in the first
  place). It now asserts, in order: the fresh-session default is All (5 rows, matching the real
  default), switching to Wallenberg narrows to the 2 built-in members by name, the choice survives
  a reload (still `localStorage['arp-kb-view-collection']`), and switching back to All restores 5.
  Same round-trip shape as the original test, updated for the real default.
- **`kb.spec.ts:137`** rewritten to mock one fictional debt_maturity company ("Fjord Metals",
  sector "Materials", incomplete buckets) instead of requiring the real
  `data/kb/ericsson_2025/extractions/debt_maturity.json` to exist and be the sole Wallenberg debt
  report — the `existsSync`/`test.skip` real-file dependency is gone. Every original assertion
  (one sector group, "0 of N companies with complete buckets", the grey "buckets incomplete" SVG
  label, row click opens the company) is kept, now proven against a fixture this test owns instead
  of the shared library's current contents.
- **`team-workflow.spec.ts:46`** keeps its existing 2-company mock (`abb`/`acast`) untouched and
  keeps testing that the KB tab's own Collection picker correctly scopes to SEB Mid Cap (still
  asserts `kbScopes` contains `'midcap'` and the row counts). What's removed is only the false
  premise that picking a collection on the Extract tab reaches the KB tab without also picking it
  there; the test is renamed to `"Knowledge base scopes to SEB Mid Cap independently of the Extract
  collection"` and now asserts that independence directly (KB opens showing both companies first,
  *then* scoping to SEB Mid Cap from its own picker narrows to one) — same coverage, corrected
  premise, matching the sibling assertion already living in `kb-new-reports.spec.ts:30`.

No assertion was loosened (no `toBeGreaterThan`, no widened regex) and nothing was skipped.

## kb.spec.ts:68 ("filter atlas") flakiness — not reproduced, cause not pinned down

Ran the full suite **twice before** the fix (red baseline) and **twice after** (green), all real,
serial, against the live `data/kb`: this test passed clean in all 4 runs, both tones each time.
Not flaky in 8 observed executions here.

What was checked: this test relies on exactly one real KB entry matching the substring "atlas"
(`GET /api/kb?collection_name=all` confirmed exactly one match: `atlas_copco_2025` — no
"Atlas Antibodies" or similar collides, and the free-text filter also matches on `stem`, so a
company-name rewrite alone wouldn't make it miss). The suite runs `fullyParallel: false,
workers: 1` — one shared backend and on-disk `data/kb`, tests strictly sequential, so the failure
mode w215 flagged ("HEAD passed, baseline didn't, suspected `KB_DIR` state residue") can't be a
worker race; `KB_DIR` itself is a backend-test-only override, never set for the e2e run, so both
sides use the same live `data/kb`. The nearest real (unmocked) interaction with the same
`atlas_copco_2025` entry is `extract-cached.spec.ts` (2 files earlier, alphabetically, in the same
serial run), which re-runs a real Extract against the cached Atlas Copco PDF and — per the known
`data/kb` re-registration side effect (rewrites `meta.json`/`pages.jsonl` on open) — is the most
plausible source of the transient state w215 saw, but it completes and settles well before
`kb.spec.ts` starts, so a repeat here found nothing wrong. Left as-is per the work order's own
fallback: root cause not confirmed, no fix applied, repro conditions written here for whoever
looks next.
