## The gap (recap of v035's finding)

v035 found 4/10 companies in a seed of 10 hit the same wall: a debt-maturity note that prints one row
(often literally "Total") with the maturity buckets as **columns**, instead of the income-statement shape
every other repair in `extract.py` assumes (one row per line item, N *year* columns). `_year_column` finds
no year in a bucket header ("< 1 year / 1-2 years / 2-5 years / > 5 years"), so it returns `None`, and
every repair built on it (`_column_values`, `_derived_value`, `_between_rows`) bails out before it can even
try.

## The fix: a general column-bucket reader, gated off the schema's own check shape

New in `extract.py`. Schema-driven, not company-driven — no company name, and (deliberately) no literal
`"debt_maturity"` string anywhere in the new code:

- `_identity_parts(schema)` — reads which field is "the total" and which are "the parts" from the schema's
  own identity check (`null_as_zero` + `expr`), the same technique `_between_rows` already uses elsewhere
  to find which fields participate in an identity. Any schema whose check has this shape qualifies, not
  only this one.
- `_bucket_total_row(rows, total_sf)` — candidate grand-total rows: the total field's own synonym ("Summa
  räntebärande skulder"), or a bare Total/Totalt/Summa. A schema's total-field synonyms are themselves
  phrased as row labels ("total borrowings"), but plenty of reports print just the bare word on the total
  row of a note that is already, by construction, about borrowings — the page only got here as a
  `debt_maturity` candidate in the first place.
- `_bucket_header(rows, idx, bucket_sfs, fiscal_year)` — the ordered column keys above a candidate total
  row: every bucket-field synonym hit, in print order (dash-normalised, so "1–2 years" matches the
  schema's own "1-2 years"; one small patch for the plain English "< 1 year" / "> 5 years" symbol form,
  which the schema only states in Swedish — "< 1 år" / "> 5 år" — even though reports print it in English
  too, e.g. Cloetta), plus a bare Total/Summa marker wherever one is seen. Searched over a generous window
  above the total row, not just the one row directly above it, because pymupdf sometimes wraps a two-line
  column header ("Summa" / "inom 1 år") into two separate `_page_rows` rows. Falls back to a literal
  calendar-year header ("2026 2027 2028 Later") folded to <1y / 1-5y / >5y off the report's own fiscal
  year, per HANDOFF's own anticipated case. Returns `None` without ≥2 distinct bucket keys — a page that
  merely mentions one bucket word in passing prose is not a bucket-column table.
- `_bucket_assign(amounts, col_keys)` — zips the row's own numbers to the header; a bucket spanning more
  than one column (a finer split, e.g. "1-2 years" + "2-5 years" both feeding `due_1_to_5_years`) is their
  sum; a column printed as `-`/`—` is `None`, not a fabricated 0 (this needed a `nil=` parameter added to
  `_row_amounts` — default unchanged, so every one of its existing call sites is untouched).
- `_fill_bucket_columns(...)` — the entry point, run once near the end of `extract()`: finds a qualifying
  page (the statement spread, or wherever any of the total/part fields already cite), and for each field
  either fills a null or — if the model's own answer disagrees with the column reading by more than the
  check's own rounding tolerance — lets the page win. Same merge rule as every other repair already in
  this file (Pandox, Getinge, …): warn, then override.

**The safety valve is structural, not an exception list**: the row's own column count must exactly equal
the number of header hits found, or the mechanism declines rather than guess. That's what keeps XANO and
Ework (below) honestly unfixed instead of wrongly "fixed".

## Why the other three stay unfixed, and why that's the honest answer, not a shortfall

- **XANO Industri**: the real header wraps across two of `_page_rows`' lines (pymupdf prints "Summa" on
  one physical PDF line and "inom 1 år" on the next), which scrambles hit order out of print order
  (`_bucket_header` would find "efter 5 år" before "inom 1 år" — backwards, verified by hand). The header
  also uses day/month sub-splits ("–30 dgr", "31–90 dgr", "Mellan 1 [och 3 år]") that never literally say
  "year" anywhere, and the row has an 8th numeric column this lane could not attribute to any header
  phrase even reading the real PDF text by hand (see the git history around this file for the arithmetic).
  The safety valve — header-hit count must equal the row's own column count — correctly declines rather
  than guess across a scrambled, incompletely-understood header.
- **Ework Group**: the same day/month-vs-year gap (the table's own finer split is "< 1 month / 1-3 months
  / 3-12 months", never "year"), plus an unexplained 6th numeric column in the row (verified by hand: 6
  columns of amounts before the two trailing "Total undiscounted value" / "Carrying amount" columns, but
  the visible header text, spread across two physical PDF lines, only names 5 buckets). Declined for the
  same structural reason: the column count the safety valve checks never matches what the header can
  explain.
- **Bergman & Beving**: worse than a parsing gap — verified by hand against the real page text that this
  company's own bucket breakdown ("within 3 months" / "after 3 months within 1 year" / "after 1 year
  within 5 years" / "after 5 years") sums to the note's **undiscounted "Future payment amount"** column
  (2,334), not the **carrying "Total interest-bearing liabilities"** total (2,062) that `total_debt` is
  defined against and that the model already correctly answered, from a different page. No column-order
  reading of this table can ever pass the identity check, because the two totals are genuinely on
  different bases — this is HANDOFF's own "two tables" problem, one level down (within one table's
  columns, instead of between two whole tables), not the bucket-as-columns problem this lane's territory
  covers. `_bucket_total_row` correctly finds no candidate here regardless: the only "total"-shaped row in
  the block is "Total financial liabilities", which is neither a `total_debt` synonym (missing
  "interest-bearing"/"borrowings") nor a bare Total/Summa/Totalt — and would be wrong to treat as one even
  if it matched syntactically, since it includes non-interest-bearing accounts payable. Flagging for the
  group rather than guessing at scope, same as v035 did for the bucket-as-columns gap itself.
