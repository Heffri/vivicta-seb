# v052 — row-anchored year header for row derivations (multi-table pages, Group | Parent)

Lane: `ao/vivicta-glm-14/v052-repeated-year-header` (work order `v052-repeated-year-header`, 2026-09-17).
Territory: `backend/pipeline/extract.py` (year-header selection and its call sites on the derivation paths only),
`backend/pipeline/test_confidence.py`, this file. Zero model calls everywhere; offline only.

## The two mechanisms

A note page can stack more than one table, and the header of the second one can repeat the fiscal year across
Group | Parent column pairs. Both together defeated every row-derivation repair on MedCap p.101 (seed 3,
`Förfallotidpunkt för upplåning`):

1. **Multi-table pages took the page's FIRST year header.** `_year_run(text[:4000])` returns the first
   >=2-year run on the page. On MedCap p.101 that is the receivables-ageing table's
   `MSEK 2025-12-31 2024-12-31` above the note — `_year_column` returned `(0, 2)` while the maturity rows
   print 4 amounts (Koncernen 2025/2024 + Moderbolaget 2025/2024), so every window in `_derived_value` /
   `_between_rows` failed its `len(amounts) == ncols` gate and bailed.
   Fix: `_row_year_column(rows, i, fiscal_year)` — the NEAREST year run above the quoted row (`_year_run`
   over the `rows[j:i]` window, `j` walked upward; the nearest complete run wins, and the walk never climbs
   past a found run, so it can never cross into the table above). Fiscal year once in that run -> `(pos, n)`.
2. **A repeated year (Koncernen | Moderbolaget) had no usable column.** `_year_column` returns None when the
   fiscal year repeats (Volvo's segment pairs — correct there, they are unknowable). But when the run's own
   row, or the one directly above it, names Group before Parent (`Koncernen Moderbolaget`,
   `Group Parent Company`), the Group side IS knowable: take the first pair; Parent named first -> the last
   pair. Neither word, or no order -> None, exactly as before. `locate.GROUP` / `locate.ENTITY` are reused
   unchanged; `_segment_column`'s voting logic is untouched.

New mechanism needed for the green (flagged as a deviation below): `_between_rows` only read rows *strictly
between* the other operands' rows. MedCap's first-year split rows sit directly ABOVE its uppermost operand
row (`1 – 5 år`), so nothing is between them. When the strictly-between window comes up empty (or fails to
close the identity), `_between_rows` now also tries the k = 2..8 full rows printed directly above the
uppermost operand row — same label gate (no other field's label), same every-column `_check` gate.

## Call sites of `_year_column` — what changed and why

| site | function | change |
|---|---|---|
| `_column_values` (field's own header) | `_column_values` | **row-anchored** to the field's quoted row (`anchor` param stands in for a quoteless caller); falls back to the page header when the quote is not a printed row |
| `_column_values` (other fields' admission compare, ex-line 468) | `_column_values` | **row-anchored on BOTH sides** (deviation, below): each other field is admitted by the header of its OWN quoted row, so same-page rows of the other stacked table are not mixed in |
| `_derived_value` | `_derived_value` | **row-anchored** to the quoted row (reordered: rows -> index -> header) |
| `_between_rows` | `_between_rows` | **row-anchored** at the uppermost operand row (the rows this derivation reads sit at or directly above it) |
| identity_all_columns block (ex-line 1103) | `extract()` | **row-anchored**, consistent with the `_column_values(f, ...)` call beside it (both must name the field's own table) |
| null-fill in the field loop (ex-line 828) | `extract()` | **kept page-level**: statement-spread read, no quote exists yet to anchor to |
| field-verification header (ex-line 873) | `extract()` | **kept page-level**: verifies the model's own read of the page's main statement; does not derive across tables |
| statement-spread fill (ex-line 986) | `extract()` | **kept page-level**: statement-spread fill, no quote to anchor to |

Untouched by design: `_segment_column` (v041 voting), `_bucket_year_hits` / `_fill_bucket_columns`
(v036/v040 bucket-column mechanism), `_check` null_as_zero (v044), the end-segment provenance gate (v050),
schemas, locate.py, parse.py.

### Deviations from the work order's letter (each verified, listed for the supervisor)

1. **The 468 "two pages agree" compare anchors both sides, not just the left one.** Keeping the left side
   page-level would compare the wrong-table `(0, 2)` against the anchored `(0, 4)` and exclude the very
   fields (`total_debt`, `due_1_to_5_years`) the MedCap derivation needs from `_column_values`' columns.
   On single-table pages both sides still reduce to the page header, so the compare is unchanged there.
2. **The identity check ends `missing: due_after_5_years`, not passed.** The work order expected
   "恒等式 passed". It cannot pass without relaxing v044's own rule: `>5år` (due_after_5_years' header) is
   printed on the *contractual* table one page over (a candidate page), so `_check`'s v044 refinement
   refuses to zero-fill it, and the carrying table genuinely prints no >5y row. The identity itself IS
   closed in every column by the derivation (54.3+48.0+616.5 = 718.8 vs 718.7; 41.8+19.0+316.7 = 377.5 vs
   377.6; Moderbolaget columns nil). Making the reported check read `passed` would mean zero-filling a
   bucket whose label is present on a candidate page — the exact false-0 v044 removed, and `_check` is
   outside this lane's territory. Reported instead of forced.
3. **The v044 MedCap test's expected detail was updated** (`missing: due_within_1_year` ->
   `missing: due_after_5_years`): the same derivation now also fills the model-null `due_within_1_year` in
   that case (102.3 @ 1.0, value_derived). Strictly better on the same fixture; comment updated in place.

## Findings

- The work order's premise about the mechanism was confirmed on the current baseline: `_year_column` returns
  `(0, 2)` (the page-first run) and `_segment_column` None on p.101 — v041's "returns None because the year
  repeats" was indeed not the live path. The general gaps are exactly the two fixed here.
- `_between_rows`' strictly-between window could never have served MedCap even with a correct header (its
  bucket rows are above, not between, the operands). The above-window extension is what makes the general
  mechanism land; it reuses the same gates, so Addnode's between case is untouched and green.
- Multi-table note pages are common (MedCap here; the ageing/currency tables on the same page), but the
  135-company replay shows the anchored header changes nothing anywhere else — the nearest-run-above rule is
  conservative exactly because it declines (None) whenever the nearest run cannot name a usable column.
