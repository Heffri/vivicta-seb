## 1. Rail — WAI-ARIA Tabs pattern (vertical, manual activation)

`aria-current="page"` → `aria-selected` on `role="tab"` buttons inside a `role="tablist"` (`<ul>`; the `<li>`
wrappers get `role="presentation"` so they don't inject a stray "listitem" between tablist and tab). The
tablist gets `aria-label="Sections"` per the pattern's naming requirement. Each tab gets `aria-controls="content"`
(the single `<main>` all five views swap inside).

Native `disabled` → `aria-disabled` on the three tabs that aren't ready yet (Results/Compare/Ask before any
report). Reason: a natively-`disabled` button drops out of the accessibility tree entirely, so a screen-reader
user arrowing through the tablist would only ever discover 2 of the 5 tabs; `aria-disabled` keeps it
discoverable ("Results, dimmed") while JS still makes it inert — `pointer-events-none` blocks the mouse,
`tabIndex={-1}` keeps it out of both the normal Tab order and the roving pointer, and the click handler no-ops
if the target is disabled (defense in depth, since `aria-disabled` alone doesn't stop a click the way the
native attribute did).

Roving tabindex: exactly one tab (the one the user last moved keyboard/mouse focus to) has `tabIndex=0`, the
rest `-1`. Up/Down **and** Left/Right (work order asked for both, not just the vertical pair) move the roving
pointer among the *enabled* tabs only, wrapping; Home/End jump to the first/last enabled tab. This is
"manual activation" — moving focus doesn't select the tab; Enter/Space does, for free, since these stay real
`<button>` elements (native keyup/keydown activation), which the verification script confirmed explicitly
(`aria-selected="false"` right after 3×ArrowDown, before Enter). The roving pointer resyncs to the active tab
whenever `active` changes for any reason (click, keyboard activation, or a switch triggered elsewhere in the
app, e.g. after an upload) — done by comparing `active` against a stored previous value **during render**
(React's documented "adjust state while rendering" pattern) rather than in a `useEffect`, which is what oxlint's
`react(set-state-in-effect)` rule flagged on the first pass (see §4).

New `shell/focusRing.ts` exports the v006/v010 ring recipe (`outline-none focus-visible:outline-2
focus-visible:outline-solid focus-visible:outline-offset-2 focus-visible:outline-ring`) as one constant, used
by the rail buttons (previously inlined twice), the skip link, and the h1 focus styling below — one source of
truth instead of three copies of the same literal string.

## 2. Skip link

`shell/SkipLink.tsx`, mounted as the very first child in `App.tsx` (before `Titlebar`) so it's the page's first
focusable element. `sr-only` until focused, then `focus:not-sr-only focus:fixed focus:top-3 focus:left-3
focus:z-50` plus the existing `glass` utility + `ring-1 ring-foreground/10` — the same "floating surface outside
the one shell pane" treatment `DESIGN.md` already carves out for `SelectContent`, reused rather than inventing
a new visual, per the work order's "用现有 token 类". Target: `<a href="#content">`, which browsers natively
focus on activation since `<main id="content" tabIndex={-1}>` is focusable — plus an explicit `onClick`
`.focus()` call, because the native fragment-focus step is a documented no-op on a *second* activation when
`location.hash` is already `#content` (no hash-change event to hang the behaviour off). `App.tsx` itself only
gained the `<SkipLink />` mount and `main`'s `id="content" tabIndex={-1}` — no other lines touched, per the
work order's territory line.

## 3. h1 focus after a rail navigation

`shell/useHeadingFocus.ts`, called once from `App.tsx` as `useHeadingFocus(tab)` (the one non-JSX addition to
`App.tsx`, needed because the tab-change signal only exists there). On every `tab` change it finds `#content`'s
`h1` (every view renders exactly one — checked all five view files), sets `tabIndex=-1` if not already present,
adds the shared focus-ring classes, and calls `.focus({ preventScroll: true })`. Skipped on mount so page load
doesn't steal focus from the skip link.

Whether a screen reader sees the ring is handled by `:focus-visible` itself, not extra code: browsers decide
`:focus-visible` by the *modality of the interaction that caused the focus*, including for a programmatic
`.focus()` called from inside an event handler — keyboard activation (Enter/Space on a rail tab) keeps it
visible, a mouse click doesn't. Verified directly (§5) rather than assumed.

## 4. A real bug caught by the "red before green" step, not by inspection

First implementation of `useHeadingFocus` used a `mounted = useRef(false)` flag ("if not mounted yet, mark
mounted and return") to skip the initial run. That's wrong under React's dev-mode Strict Mode, which
double-invokes a fresh mount's effect (mount → cleanup → mount again) *without* resetting refs in between: the
first invocation flips the flag and returns (correct skip), but the second invocation sees the flag already
`true` and proceeds — so on every fresh page load the Extract view's h1 silently stole focus from the skip
link, and Tab #1 landed on a directory-search `<input>` instead of "Skip to content". Caught by the
verification script's *first* real run (§5) — before that, the flag looked obviously correct on inspection.
Fixed by comparing `tab` against a `useRef(tab)`-seeded previous value instead of a boolean: idempotent, so a
second invocation with unchanged inputs reaches the same (correct) answer instead of flipping it. Confirmed
with a standalone DOM dump (`document.activeElement` was `H1` before any key press; after the fix, `BODY`).
Flagging this because the pattern (`useRef(false)` "have I mounted yet" flag inside an effect) is easy to reach
for again elsewhere in this codebase or others — the fix is the general one (compare against the previous
value of the thing the effect depends on, not a fired-once flag).

## 5. Verification

lives in the lane's own temp dir per `common.md`, resolves the shared Playwright install in

cross sideways between sibling directories). Same 12 assertions run in both tones, all pass:

1. First Tab stop is the skip link (`<a href="#content">`, text "Skip to content").
2. It's visible once focused (non-zero bounding box — `sr-only` → `not-sr-only` toggle confirmed live, not
   just by reading the CSS).
3. Enter on it moves focus to `<main id="content">`.
4. Fresh load, Tab past the skip link → 2nd stop is `#rail-tab-extract` (roving tabindex's initial `0` sits on
   the active tab).
5. 3×ArrowDown lands on `#rail-tab-kb` — the two-item cycle (`extract ↔ kb`, since Results/Compare/Ask are all
   disabled with no report loaded) matches the work order's expected outcome exactly, which is itself a check
   that the wraparound math is right, not just the "disabled tabs are skipped" part.

7. `aria-selected="false"` on it — moving focus hasn't activated it yet (manual activation, not automatic).
8. Enter activates it; focus lands on an `H1` whose text matches `/102 reports/` (the real KB count, not a
   fixture).
9. That h1 has `tabindex="-1"`.
10. A mouse click on a different tab (`Extract`) does **not** leave the new h1 matching `:focus-visible` —
