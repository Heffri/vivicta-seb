## 1. The change

v107's merge copied only files the user does not have, so a v107-era install kept its first-generation
bundle content forever (v137 Finding 2: the 09-16 `enea_2025` extraction, `total_debt` null, pinned
against the current bundle's 305,555). `desktop/data-sync.js` now syncs three-way:

- `<userData>/data/.bundle-manifest.json` records the sha256 of every file the bundle installed
  (rel path → hash; tmp+rename write, sorted keys, skipped when unchanged). On every later launch,
  for each bundled file: user lacks it → copied (v107 behavior); user's copy hashes equal to the
  manifest's recorded bundle version → the user never modified it, so the new bundle overwrites it
  and the manifest entry moves to the new hash; hash differs from the manifest (or the manifest has
  no entry) → kept, counted as `kept (user-modified)`. `reports/index.json` stays merge-only and is
  never manifest-tracked; `kb/up-*`, PDFs, embeddings/tmp stay under `shouldSkipDataEntry`.
- Reviews are an absolute keep: an extraction whose JSON carries the backend's review markers is
  never overwritten. The work order pointed at `backend/pipeline/kb.py`'s `has_reviews`, but that
  function actually lives in `backend/app.py` (`result.get("basis_history")` non-empty, or any field
  with `review_history`); the review endpoint also stores a `human_review` object on the field. The
  JS port (`resultHasReviews`) treats a non-empty top-level `basis_history`/`reviews` or any field
  with a non-empty `human_review`/`review_history` as reviewed. Verified: `data/kb` in the repo
  contains zero `review_history` occurrences — bundled extractions are all machine-generated, so
  any file carrying markers is user-reviewed.
- **One-time rule for installs created before the manifest existed** (the owner's machine, v137
  Finding 2): when no manifest file is present, "user file == some older bundle" is unknowable, so
  for `kb/<stem>/` only: a file that differs from the new bundle, in a stem that is not `up-*`, in
  an extraction without review markers, is treated as stale bundle data and overwritten once; the
  log line itemizes the refreshed stems. Non-kb user files (`companies.json`) are kept. From the
  second launch on, everything is three-way.
- Log line: `data sync: +X kb entries, +Y files` unchanged, extended by `N updated`,
  `M kept (user-modified)` and the stale-stem list — each part printed only when non-zero, so the
  settled second-launch line stays `data sync: +0 kb entries, +0 files`.
- `desktop/main.js`: `--user-data-dir <dir>` / `--user-data-dir=<dir>` is read from `process.argv`
  before `requestSingleInstanceLock()` (the lock is keyed on `app.getPath('userData')`, which is
  exactly why v137's packaged run ignored the switch) and `app.setPath('userData', …)` applied.
  Works for the packaged exe and `electron .` alike. `desktop/README.md` "Packaged mode" paragraph
  now describes the v138 sync and the switch (v107 had left the old "first launch copies" sentence
  stale; corrected in the same paragraph, which is this lane's README allowance).
