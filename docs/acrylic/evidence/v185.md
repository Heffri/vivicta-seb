# v185 — sprint: less review, faster runs, a company search that names the company, the PDF always

## Ask

Product direction (2026-09-21): too many things need reviewing after parsing; the whole point is
minimising the human in the loop. Runs are too slow. The AI search should say exactly which company
it found and let the user confirm it or look for another — "intel" is not a company, Intel
Corporation is. The "allow PDF download" option made no sense: the PDF is always wanted. Model
choice was left open ("a smaller local model instead of the big terra model?").

## What changed

**Review burden** (`backend/pipeline/workbench.py`, `extract.py`, schemas)

- The basis form no longer blocks `ready`: its entries live in `basis_issues` beside the queue with a
  prefill (`basis_suggested`); `issues` holds field and check tasks only.
- One stand-in resolves a row: `value_in_quote` or exactly one of `value_derived` / `stated_zero` /
  `printed_nil`, plus the other five codes and a source.
- Optional income rows (`cost_of_sales`, `gross_profit`, `profit_discontinued`) that are null go to
  `not_reported` — unless an optional peer in the same identity (cost of sales present, gross
  profit null) has a value, which is a miss. A null optional with a schema `default` counts as that
  default in the workbench checks, as in extraction, so `net_profit_arith` evaluates.
- A buckets-as-columns row whose bare "Total" closes on its own arithmetic earns
  `identity_all_columns` → `label_known` only when the row or its own table names the borrowing
  scope (title "Note 21 Borrowings", a "Lease liabilities" row) and no all-liabilities row (trade
  payables, earn-outs) sits in the table. Karnell's markerless "Total 72.2 454.4 - 526.6" closes too
  and earns nothing: closing alone is self-referential (v088/v095).
- `label_known` for scoring is the field's synonyms + row synonyms + label ("Borrowings",
  "Interest-bearing liabilities", "Liabilities to credit institutions" are known debt rows; never
  `header_synonyms`, whose "Total" would identify any row). Decorate re-derives it with the same
  vocabulary, so saved extractions scored before the change resolve without re-extraction.
- Checks are a task only when `failed`; `unavailable` is a missing operand, already a field task.
- PPT footer and CSV `unresolved` list field, check and basis issues together.

Measured over the 209 saved extractions in `data/kb` (decorate only, no model call):

| | ready | blocking tasks | of which field / check / basis |
|---|---|---|---|
| before the sprint | **0 / 209** | 2,642 | 623 / 235 / 1,784 |
| after lane R (5e7c855) | 79 / 209 | 426 | 424 / 2 / 0 (basis beside the queue) |
| after this note | **78 / 209** | **410** | 405 / 5 / 0 |

The step from 79 to 78 ready and 2 to 5 check tasks is the peer rule and the default-aware
`net_profit_arith` finding real problems (three income statements whose net profit identity fails
once discontinued operations count as 0; one gross-profit pair with one side missing). The
re-derived `label_known` released 24 field tasks. What remains: 249 of the 405 field tasks are
nulls (mostly debt buckets the report does not print or the extraction could not read); 26 are bare
"Total"/"Summa"/"Totalt" rows from extractions that predate the closing-row marker and would earn it
on re-extraction if they close.

**Speed** (`backend/pipeline/llm.py`, `app.py`, `frontend/src/components/UploadView.tsx`)

- Hosted-model calls run three at a time (`LLM_CONCURRENCY`, default 3; the openai-compatible
  provider stays at 1) instead of behind a global lock; timeout 300 s; the extraction cache key is
  `EXTRACT_VERSION`, so a code change invalidates the cache without touching the settings string.
- The frontend runs the queue three wide (mocked e2e: five uploads, the fourth `/extract` waits for
  one of the first three).
- `EXTRACT_TWO_PASS` stays on by default: v045's evidence was net positive and nothing here
  re-measured it.

**Company search** (`backend/pipeline/fetch.py`, `app.py`, `frontend/src/components/upload/CompanySearch.tsx`)

- `POST /api/reports/discover` resolves the typed text to concrete legal entities: saved reports
  first (prefix match on the identity words), then the connected model's web search returns
  `legal_name`, ticker/exchange, country, org number or LEI, fiscal year end, the document it found
  and a one-line reason. "intel" → Intel Corporation (NASDAQ: INTC), Form 10-K.
- Cards; **Use this company** fetches that candidate's URL first (`url` on `/fetch`) and extracts;
  **None of these** re-runs discovery with a hint. Query and year are frozen while discovery runs.
- The report index is written atomically (`index.json.tmp` + `os.replace`) under a lock and
  re-read before each upsert: three parallel fetches no longer race on it.

**The PDF, always** (`backend/app.py`, `frontend`)

- `download_pdf` defaults to true. A cached PDF is reused, otherwise downloaded; if the download
  fails while page text is saved, the saved report is returned instead of a 404 (the Source panel
  says the PDF is missing). `download_pdf: false` remains for API callers as the text-only path
  (409 when nothing is saved). The checkbox is gone; the UI sends one request per pick, never the
  old false-then-409-retry pair.

## Model decision

Kept Codex `gpt-5.6-terra`. Evidence: v148 measured `sol` worse on the same corpus; the Claude CLI
on this machine is installed but not logged in (`claude login` is the user's to run — no Claude
model could be benchmarked); Ollama is not running, so no local model was available. A benchmark
run that fell through to the deterministic fallback (no model) produced 7/9 correct income fields
on SEB 2025 in 3–5 s — the mechanisms carry a lot of the recall on well-formed statements
(consistent with v158), but v158 also showed the model supplying the recall on 86 % of debt stems,
so terra stays. To test a Claude model: `claude login`, then `LLM_PROVIDER=claude LLM_MODEL=…` and
re-run `scripts/eval_breakdown.py`; the parallel semaphore already applies to it.
