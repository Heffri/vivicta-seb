## What changed

1. **`frontend/src/components/SettingsView.tsx`**: a `TwoPassToggle` checkbox ("Two-pass page
   selection (recommended for hosted models)") on the Codex, Claude (via the shared
   `SubscriptionCliFields`), and API-endpoint cards — not on Local (Ollama), which has no evidence
   behind running it. `DEFAULT_CONFIG.extractTwoPass = true`. A new `effectiveTwoPass(cfg)` helper
   (`ollama` → `false`, `fixture` → `undefined`, else the stored value) drives both the toggle's
   effective value and a new `StatusRow` segment, `two-pass on/off`, sourced from the desktop's own
   last-saved config (`api.get()` on load, then whatever `api.set()` just persisted) — never the
   in-progress form, same "confirmed, not edited" contract the existing provider/model/embed fields
   already keep. `StatusRow`'s `twoPass` prop is left `undefined` by `ReadOnlySettings` (the plain-
   browser mirror): `GET /api/config` never carries this field (backend untouched, per territory), so
   that view has no source of truth for it and shows nothing rather than guess.
2. **`frontend/src/main.tsx`**: `DesktopConfig` gains `extractTwoPass: boolean`. Not in the work
   order's own territory list, but unavoidable — this is the one place the shared `window.arp`
   contract type lives (per its own existing comment), and `SettingsView.tsx` cannot compile against
   a field that isn't on the type. Three lines, additive, no logic.
3. **`desktop/settings.js`**: `DEFAULTS.extractTwoPass = true`; `sanitize()` gains the field (falls
   back to the default for anything not literally `true`/`false`, same pattern as every other field);
   `envForConfig()` now sets `EXTRACT_TWO_PASS` for every non-fixture provider — `'1'`/`'0'` from
   `clean.extractTwoPass` for `codex`/`claude`/`openai`, hardcoded `'0'` for `ollama` regardless of
   what's stored (that card has no toggle and v045's evidence never validated two-pass against a local
   model — see docs/acrylic/README.md's "Model providers"). `fixture` unchanged (`{}`, no env at all).
4. **`desktop/main.js`**: the two existing `backendLogStream.write(...)` lines (startup, and settings-
   save restart) now also print `two-pass: <value or 'unset'>`. `GET /api/config` was never going to
   carry this field (backend is out of territory), so `backend.log` is the only place a settings save's
   actual env is provable from this repo alone — see "Env passthrough" below for why that mattered
   here specifically. Two lines changed, no new logic, no new IPC surface.
5. **`docs/acrylic/README.md`**: a paragraph under "Model providers" (what two-pass is, v045's
   30-company numbers, why the default stays off, how to turn it on) + two new hardening-table rows
   for v045 and v046 (debt_maturity two-pass v2, and the bucket-label synonym batch) — both already
   shipped and evidenced but missing from that table until now.
6. **`backend/README.md`**: one new section, "Two-pass page selection (`EXTRACT_TWO_PASS`)", between
   the Claude CLI provider section and Checks — same env var, same default-off rationale, pointing at
   `pipeline/extract.py`'s own docstring and the v043/v045 evidence. No backend code touched.

Not touched: `backend/pipeline/*`, `backend/schemas/*`, `data/`, any file outside the above.

## Env passthrough: proven directly against the real `desktop/settings.js`, not through Electron

**Electron dev mode would not come up in this worker environment.** `desktop\npm run dev`'s own
`electron .` (and a direct `electron.exe <path> --remote-debugging-port=9222 --user-data-dir=<isolated
dir>` invocation, matching v033's own CDP-driven testing method) left `app.whenReady()` hung
indefinitely both times: zero child processes ever appeared under the electron.exe PID (no GPU
process, no renderer, no backend `uvicorn`, no vite) for 90+ seconds, `<userData>/logs/backend.log`
was never created (meaning `main()` in `desktop/main.js` never even started), and no crash event
landed in the Windows Application event log (a hang, not a crash). A second attempt added
`--disable-gpu --disable-gpu-compositing --disable-software-rasterizer --no-sandbox` (the standard
fix for Electron hanging in a restricted/virtual-display environment) — same result, zero children,
90+ seconds. This looks like a constraint of this specific AO worker's environment (it reports as the
real interactive console session, `query session` shows `>console ... Active`, not a detached Session
0), not something fixable from inside this lane's territory, and not something worth spending this
small lane's whole budget chasing further.

**What actually verifies the passthrough instead**: a standalone script (`env-proof.cjs`, kept in
`uaw-lanes/v047/`, not a deliverable — see common.md's owner-identifier rule, path masked here) that
`require()`s this repo's real, unmodified `desktop/settings.js` directly, calls its real
`saveConfig()`/`envForConfig()`, and `spawn()`s a real `python.exe` from `backend/.venv` **the exact
same way `desktop/main.js` does** (`spawn(exe, args, { env: { ...process.env, ...env } })`) — except
the spawned command is `python -c "import os; print('EXTRACT_TWO_PASS=' + repr(os.environ.get(...)))"`
instead of `uvicorn`, so the *real child process itself* reports its *own real environment* back,
which is stronger evidence than anything `Get-CimInstance` can show (Windows doesn't expose another
process's environment block through WMI/CIM at all — command-line args only). Five cases, each its
own real spawned PID:

| Case | `envForConfig()` output | real child process's own `os.environ.get("EXTRACT_TWO_PASS")` |
|---|---|---|
| codex, toggle on (default) | `{"LLM_PROVIDER":"codex","LLM_MODEL":"gpt-5.6-terra","EXTRACT_TWO_PASS":"1"}` | `'1'` |
| codex, toggle off | `{"LLM_PROVIDER":"codex","LLM_MODEL":"gpt-5.6-terra","EXTRACT_TWO_PASS":"0"}` | `'0'` |
| claude, toggle on (default) | `{"LLM_PROVIDER":"claude","LLM_MODEL":"claude-sonnet-5","EXTRACT_TWO_PASS":"1"}` | `'1'` |
| openai (API endpoint), toggle on (default) | `{"EXTRACT_TWO_PASS":"1","LLM_BASE_URL":"https://api.openai.com/v1","LLM_MODEL":"gpt-4o-mini"}` | `'1'` |
| ollama, `extractTwoPass: true` **stored** (simulating a stale value left over from a prior hosted-provider save) | `{"LLM_BASE_URL":"http://127.0.0.1:11434/v1","LLM_MODEL":"qwen3:8b","EMBED_MODEL":"bge-m3","EXTRACT_TWO_PASS":"0"}` | `'0'` |

The last row is the one that actually mattered to get right: `sanitize()` still stores whatever
`extractTwoPass` a hosted-provider save last wrote even after switching to Ollama (same "shared field
across providers" shape `baseUrl`/`apiKey`/etc. already have), and `envForConfig`'s `'ollama'` case
correctly ignores it and forces `'0'` regardless — confirmed above, not just read off the source.

A `Get-CimInstance Win32_Process` snapshot taken while this script ran did catch a live `python.exe`
child mid-flight, but not one of *this* script's own five (a sibling lane's own unrelated backend
process on this shared machine won the race instead, harmless, ignored, not touched) — the table
above is the load-bearing evidence, not that snapshot; re-run instructions below can reproduce a CIM
capture if wanted.
