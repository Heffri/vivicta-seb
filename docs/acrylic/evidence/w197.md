# w197 — bounded required-null second pass

Branch `ao/vivicta-seb-114/w197-missing-field-second-pass`, based on the current
`origin/acrylic` as directed at delivery. The parallel w196 branch was not merged here; its
integration is reserved for the supervising lane.

## Change

After ordinary extraction and any configured merge, the route may run a narrowly scoped follow-up
for each still-null, non-optional schema field (at most three fields per report). The follow-up:

- reuses `extract(..., fixed_pages=True)` with only the target field and the locator's first up to
  three valid candidate pages, including their complete extracted page text;
- puts that field's complete schema synonym list and a US GAAP / IFRS flexible-name instruction in
  the prompt;
- preserves the first answer unless the normal quote-on-page, value-in-quote, known-label, and
  table-scope checks all succeed again at the write-back seam;
- never changes a null to zero, rechecks the full schema checks after an accepted write-back, and
  marks an accepted field with `second_pass` evidence;
- adds second-pass model/validation time, attempts, `second_pass_calls`, and `second_pass` seconds
  to normal extraction timing. The setting is part of the extraction cache identity.

`EXTRACT_SECOND_PASS=1` explicitly enables it; the default is now **off** (the measurement below
was not sufficient to justify an always-on cost). `=0` or an unset setting makes no follow-up calls.

I examined UAW's bounded single-field extraction/verification flow in
`run-extraction-attempt.ts`, `run-verified-extraction.ts`, and `extraction-prompt.ts`. It has no
reusable Python/FastAPI fixed-page retry seam, so this adapts the local v177 `fixed_pages` seam
rather than copying UAW code.

2. an off-page quote is rejected and remains null;
3. an optional null issues no call;

   calls, while explicit `=1` records timing/accounting.

## Live validation and default verdict

The corrected live harness used Codex `gpt-5.6-terra`, `LLM_STRICT_SCHEMA=0`, no few-shot data,
carrying debt basis, merge off, and a hard 20-call wrapper. It reads report text only and does not
save KB or report data. The corrected run completed all seven reports at **20 actual Codex calls**.

| report | second-pass accounting calls / seconds | actual follow-up calls | result |
| --- | ---: | ---: | --- |
| AMD income statement | 3 / 20.934 s | 3 | accepted `net_profit=4335` from the cited page; 3 required fields still null |
| Nvidia income statement | 0 / 0.000 s | 0 | no required null after pass one |
| Intel income statement | 3 / 21.376 s | 3 | no accepted follow-up; 6 required fields still null |
| Annehem debt maturity | 3 / 19.653 s | 3 | target within-one-year value remained null |
| INQ debt maturity | 2 / 17.172 s | 2 | target one-to-five-years value remained null |
| Keo debt maturity | 3 / 0.237 s | 0 | hard call cap was already reached; 3 logical retries were rejected before a model call |
| Xspray debt maturity | 3 / 0.217 s | 0 | hard call cap was already reached; 3 logical retries were rejected before a model call |

The US set therefore added **1** accepted field and ended with **9** required nulls. The current
base's debt first passes exposed seven expected-value null targets across the four selected reports:
**0 filled / 0 wrong / 7 still null**. The first five actual debt follow-ups did not fill a target;
the final two reports could not consume a model call after the shared hard cap. The call-cap path
left every value null rather than inventing a value.

The one AMD correction is useful, but it does not demonstrate a default-on net gain: it required
11 actual follow-up calls and about 78.2 seconds of model time across the reports that reached the
follow-up, while the debt target score was 0 improvements and 0 wrong values. The default is
therefore **off**; the bounded, guarded facility remains available by explicit opt-in.

The initial live harness reached its hard cap but failed only while printing its final JSON through
the Windows GBK console because report text contained an unencodable character. Per supervisory
ruling it was rerun once with `PYTHONIOENCODING=utf-8`; the corrected harness checkpoints UTF-8 JSON
after every report before printing. This is a collection-output lesson, not a pipeline or model
result.
