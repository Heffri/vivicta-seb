# v064 — `_row_amounts`: split a space-glued pair when the header's column count says so

Lane `ao/vivicta-seb-55/v064-row-amounts-split`, off `origin/acrylic` (`adcd0d6` at dispatch, unchanged
through delivery — no rebase needed). Territory: `backend/pipeline/extract.py` (`_row_amounts` only, no
call sites needed a change — the two bucket callers already pass `ncols`/`nil=None`), `backend/pipeline/
test_confidence.py`, this file. `_fill_bucket_columns`/`_bucket_total_row` and the other four of v060's
six bucket functions: untouched. No model calls.

## Why (v060's own finding)

v060 got Boozt's row and header both reading correctly (6-column header, "Lease liabilities" picked as
the debt row) but left `due_within_1_year` null: `_row_amounts(row, 6, nil=None)` on `"Lease liabilities
441 26 78 273 63 -"` returned 5 values, not 6 — the file's own Swedish-thousands-grouping regex
(`_SPACE_GROUPS`) can't tell two adjacent small bucket columns ("78", "273") from one space-grouped
number (78273), and column count then never matched the header's, so the safety valve declined rather
than guess. Named in `docs/acrylic/evidence/v060.md` ("3. Boozt's row and header are now read correctly")
as a separate, pre-existing limit outside that lane's six-function scope.

## The rule (verbatim from `_row_amounts`'s docstring)

> The same space-grouping can over-merge two adjacent bucket columns that happen to look like one Swedish-
> grouped number: Boozt's "Lease liabilities 441 26 78 273 63 -" (ncols=6) reads "78 273" as one 78273, a
> column short. Undone only on the narrowest evidence ncols gives: the ordinary reading is exactly one
> column short, that reading already has a nil in it (a bare "-" printed elsewhere in the same row -- one
> instrument's own row, sparse by nature; a table's own whole-table Total row sums every instrument and is
> almost never nil anywhere, so this must not start reading a coincidentally same-shaped Total row too, e.g.
> Boozt's own "Total 2,358 1,928 92 273 63 0"), and exactly one "NN NNN" token in the row could be the glue
> (two or more is a guess between candidates, so none is split) -- and even then only kept if splitting that
> one token lands on exactly ncols amounts; landing anywhere else is not trusted either, and the ordinary
> (short) reading stands.

Implementation: the existing collapse-and-parse logic was pulled into a nested `_amounts(qc)` helper (used
unchanged for the ordinary reading) so it can be re-run a second time on a string built by collapsing every
`_SPACE_GROUPS` match *except* the one candidate token, via `_SPACE_GROUPS.sub` with a replacement function
that leaves that one match's span untouched. No new parameter on `_row_amounts` was needed — every existing
caller keeps its exact current behaviour unless it already happens to satisfy all three conditions above.
Full diff: saved to this lane's scratch directory under `uaw-lanes\v064\extract.diff` (not committed).

## Discovered mid-lane: the general fix alone corrupts Boozt a different way — narrowed inside `_row_amounts`

The first version of this fix split whenever (a) ncols known, (b) reading is exactly one column short, (c)
exactly one glueable "NN NNN" token, (d) the split lands on exactly ncols — no nil-in-result condition.
That version passed the direct `_row_amounts` assertion, passed 0/0 on both replays' *other* 160 companies,
but **failed** `test_confidence.py`'s own end-to-end Boozt case: `total_debt` came back **2358**, not 441.

Root cause: Boozt's own bare `"Total 2,358 1,928 92 273 63 0"` row (the note's whole-table sum — credit
institutions + lease liabilities + accounts payables + other liabilities, the wrong scope for `total_debt`)
has the exact same "one column short, one glueable NN NNN token, splits to exactly 6" shape as the correct
"Lease liabilities" row — `92 273` splits exactly as cleanly as `78 273` does. Once `_row_amounts` can read
*both* rows' 6 columns, `_fill_bucket_columns`'s own row order (`_bucket_total_row` returns bare-Total-
labelled `hits` before debt-synonym-labelled `candidates`; both survive its `matched` filter for the 2025
table) tries the Total row first, its own internal columns sum to itself (2358 ≈ 1928+92+273+63+0, so
`_fill_bucket_columns`'s own `over` guard sees nothing wrong) and it wins, overwriting the model's already-
correct `total_debt=441` and filling `due_within_1_year=2020` instead of 104. `_fill_bucket_columns` and
`_bucket_total_row` are both out of this lane's territory (v060's six-function scope; `_fill_bucket_columns`'s
guard logic specifically is named as v066's) — not touched, on purpose. Before this lane, this row-order
issue never surfaced because the *same* `_row_amounts` bug blocked both rows at once; fixing `_row_amounts`
without narrowing it would have swapped one bug for a worse one on the exact company this lane targets.

Fix: the `nil in result` condition in the rule above. A bucket table's individual-instrument rows print a
bare "-" for buckets that instrument has nothing in (sparse by nature — Boozt's own "Lease liabilities" row
ends in one); the table's own whole-table Total row sums every instrument and is essentially never nil
anywhere it doesn't have to be (Boozt's prints an actual "0", not "-", even though it happens to be zero) —
requiring the *ordinary* (pre-split) reading to already contain a nil before attempting the split uses a
signal `_row_amounts` already has on hand (no new parameter, no row-label access) to tell the two rows
apart. Re-verified after adding it: `_row_amounts("Total 2,358 1,928 92 273 63 0", 6, nil=None)` still
returns 5 values (declines, as before this lane); `test_confidence.py` green end to end; both replays
re-run clean (tables below).

## Not done

No call site changed (`_bucket_total_row`'s and `_fill_bucket_columns`'s own `_row_amounts(..., ncols,
nil=None)` calls already passed both arguments; the rule activates automatically wherever its three
conditions hold, nothing to wire up). No new parameter added to `_row_amounts` — considered one (an
explicit opt-in flag scoped to the bucket call sites, the work order's own suggested fallback if income
replay showed diffs) but it turned out unnecessary: income replay was clean without it, and an opt-in flag
would not have solved the Total-row collision anyway, since both the correct row and the Total row reach
`_fill_bucket_columns`'s derivation call through the exact same call site — the `nil in result` condition
was the fix either way, so the extra parameter would have been pure ceremony. `_fill_bucket_columns`'s and
`_bucket_total_row`'s own row-preference order (`hits` i.e. bare-Total-labelled rows before `candidates`
i.e. debt-synonym rows) is untouched and, on its own, still not a general guarantee for some future company
where a bare Total row's `_row_amounts` reading happens to match `ncols` *without* going through this
lane's split path at all (e.g. a Total row with no glued pair to begin with) — out of scope here (v060's
six-function territory), flagged for whoever next touches `_fill_bucket_columns`'s row ordering. `ncols`
unknown behaviour: byte-for-byte unchanged (the new code path is gated on `ncols and ...`, same as the
pre-existing first branch). No Boozt-specific special-casing (the rule is shape-based: exact one-short
count, exactly one glueable token, a nil already present, split lands on exactly ncols — any company's
report that matches this shape benefits, not a stem-keyed branch).
