## Method and sample boundary

The 24 PDFs were copied from the shared library into this tree's `data/reports/`; every
copy's sha256 was verified **identical to the committed `data/kb/<stem>/meta.json`** of
the stored extraction it replaces (24/24 match), so before/after differs by pipeline
only, never by document. Registered with `POST /api/reports/from-library` and extracted
twice each (`pass1`/`pass2`). Full responses in [`v119/`](v119/).

One disclosure, zero extract cost: the **committed `data/reports/index.json` (114
entries) did not contain these 24 stems**, so the first driver launch died on the
from-library 404 for stem #1 **before any `/extract` call** (backend log had 0
`[extract]` lines). The 24 library entries were appended offline from each stem's own
committed `meta.json` (file/company/fiscal_year/language/source_url), the PDF shas
re-verified, and the driver relaunched — `library_index()` re-reads the file per call,
no backend restart. The final log shows exactly **48 `[extract]` lines = 24 × 2, one
route per (stem, pass), no resend, no fallback** (every response carries `two_pass:
page [...] selected from candidates [...]`; 0 "fell back"). Cap 60.

## Per-company notes worth keeping

- **ework — a label↔mechanism contradiction, newly surfaced.** The rerun *fixed*
  w1y (null → 156409, the v068-corrected column-order read) and *broke* 1-5y against
  the label: the row prints a dash in its 1-5y column, the pipeline's dash-to-0 (whose
  arithmetic gate closes: 156409 + 0 + 0 == 156410) wrote `printed_nil` 0 — while the
  v068 label ruling says that dash means **null**, not a fabricated zero. Both passes
  identical; check passes. One of the two positions must move (the label, or the
  mechanism's dash semantics when the row's own arithmetic closes); this round changes
  neither, it only records the collision. Company stays 2/3 either way.
- **flerie — the one regression.** Stored: total 2.1 (✓). Rerun: pass1 declines
  everything; pass2 reads total 0.4 @ 0.9 from `Leasingskuld 0,8 -0,5 0,1 1,4 0,4`
  (p.86) — a lease roll-forward row, wrong scope and wrong column. The stored 2.1 was a
  real read the current two passes never reproduced. Model-side instability on a small
  (SEK m) lease-only borrower.
- **kabe — right note, wrong line.** Label w1y 30 = the balance sheet's two current
  lines (kreditinstitut 22 + current leases 8, p.79). Pass1 read 22 from the note's own
  `Kortfristiga räntebärande` row (the leases line never enters the window); pass2
  declined. Total 50 ✓ both passes.
- **svolder — ✓ both, but pass2 dropped the total** (0 → null; pass1 holds the printed
  unused-credit 0). The only ✓ company with a pass instability.
- **linc / enea — the computed-not-read family, unchanged from their stored rounds.**
  linc: the model answers 0, the guard verifies no 0 is printed on the NAV
  reconciliation's pages and drops it (the printed-nil cap — v090/v097/v108's standing
  gap: a dash-to-0 conversion can stamp `printed_nil` on a repair, never on a model
  answer). enea: both buckets read exactly (136,403 / 169,152 — the label's own
  figures), but the total is the **sum of the note's two printed section subtotals**
  and no row prints 305,555, so total_debt stays honestly null and the check fails on
  the missing value (v108's Arctic Paper note 4, second instance).
- **meren_energy / fm_mattsson — locator misses.** Both labels live on balance-sheet /
  reconciliation pages outside the two-pass window (meren: label p.73 Note 15, window

## For the group (what a future lane should pick up)

1. **The ework collision is a decision, not a bug**: v078's dash-to-0 (with the
   arithmetic-closes gate and `printed_nil` stamped) and the v068 label ruling ("a
   dash-marked bucket column is unprinted, not a fabricated zero") now disagree on the
   same printed row. Whoever owns the semantics should pick one; the current state
   scores the same company ✗ under either repair direction.
2. **enea is the second clean instance of v108's "join the note's own two printed
   subtotals" ruling** (Arctic Paper was the first). Two instances with page-verified
   sums is enough to justify the one-line schema-description ruling that lets
   `total_debt` be derived from a note's own section subtotals when their buckets are
   the ones read.
3. **Locator gap has a concrete shape**: in all three locator misses the label cites a
   balance-sheet page while the two-pass window sat on the notes the debt vocabulary
   prefers. A candidate generator that always includes the balance sheet's current
   liabilities block (fm_mattsson p.110, kabe p.79) for w1y, and the financing-note
   page range for totals, is the cheap first fix.
4. **The rerun's value is confirmed but bounded**: +4 fields net, all from mechanisms
   already landed (v068 column-order, v101 signs, v090 bank ruling applied at extract
   time) — none from the nine newest columns, which these companies never exercise.
   flerie shows the reverse risk: a stored ✓ can decay under pass instability when no
   mechanism anchors the read.
