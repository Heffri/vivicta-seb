## What changed

- **Tokens** (`frontend/src/index.css`): full rewrite of the shadcn CSS-variable block to the acrylic
  glass ladder (`--bg-0..4`, `--line-0..2`, `--fg-0..3`, `--glass-hi/shadow`, `--blur`) ported from UAW's
  `theme-acrylic.css`, mapped onto the existing shadcn semantic names. `:root` is dark glass by default,
  `[data-tone="light"]` overrides the same variables — no `.dark` class, and the generated-but-unused
  `.dark { ... }` block is gone. Added `body`'s wallpaper gradient and the `@utility glass` (translucent
  ground + `backdrop-filter` + specular top edge + contact shadow). Dropped `--color-sidebar-*` /
  `--color-chart-*` from `@theme inline` — grepped first, confirmed unused by any component. Full token
  table + rationale: [`DESIGN.md`](../DESIGN.md).
- **Shell** (`frontend/src/App.tsx` + new `frontend/src/components/shell/{tabs,useTone,Titlebar,Rail,StatusBar}`):
  titlebar (product name + the README's first sentence), left rail (5 tabs as icon+label rail items,
  `aria-current`, disabled state preserved, folds to an icon-only column at ≤900px per `min-[901px]:`/`max-[900px]:`
  breakpoints), tone toggle in the rail footer (persists to `localStorage`, sets `<html data-tone>`), status
  bar (`/api/config` model · embed_model, moved out of the old nav). The five view components
  (`UploadView`/`ResultsView`/`CompareView`/`AskPanel`/`KbView`) are mounted with the exact same props/logic
  as before — only the chrome around them changed. No router, no state library.
- **Five primitives** (`components/ui/{button,card,badge,select,table}.tsx`): re-pointed at the new tokens
  (automatic for anything already using semantic classes — most of the app). Concretely:
  - Stripped every `dark:` Tailwind variant from `button`/`badge`/`select` — the app never adds a `.dark`
    class (tone is `data-tone`, not `.dark`), so those classes were dead code that would only have activated
    on `prefers-color-scheme: dark`, a second, uncontrolled tone axis we don't want. One of them was a real
    gap: `SelectTrigger`'s only hover fill was `dark:hover:bg-input/50`, i.e. it never actually had a hover
    state in this app before — replaced with a plain `hover:bg-muted` (token-driven, works in both tones).
  - `Card` and `Badge` get the `--glass-hi` inset top edge (UAW's "chips/cards are small glass tiles" cue);
    `Table` needed no changes, it was already 100% semantic-token-driven.
  - `SelectContent` (the one floating/portaled element among the five) gets the `.glass` utility instead of
    `shadow-md` — UAW's own stated exception to "one material": popovers keep their own thin glass since they
    render outside the window pane. It now reads `--bg-0` instead of `--popover` for that reason (`--popover`
    stays defined for later components; nothing else in v001 renders it).
  - Did **not** touch props or exports on any of the five.

## Screenshots — blocked, not shipped

Backend fixture mode came up fine (`GET /api/config` → `{"model":"fixture","llm":false,...}`), the frontend
loaded through it, and `ao browser snapshot` confirms the Extract tab renders correctly on first load: banner
with the product name and the exact README first sentence as subtitle, all 5 rail tabs present with the right
`disabled`/`aria-current` state (Results/Compare/Ask disabled until there's a report), the tone-toggle button
present and correctly labelled `"Switch to light glass"` for the dark default. A live end-to-end check also
passed: typing "Volvo" into the company search correctly round-tripped through the Vite proxy to the fixture
backend and filtered the list to the 2 matches — so the app itself, tokens included, is working.

What didn't work: every **state-changing** browser-automation call — `browser click`, `browser act`,
keyboard `Enter`/`Space` on a focused button — reported success but produced **no observable effect** on
repeat, on multiple different buttons (the tone toggle, the rail tabs, a pre-existing company-picker button
in `UploadView` that I did not touch), across a fresh page reload. `browser fill` (setting an input's value)
worked correctly and did trigger real re-renders and API calls, which is what isolated this to
click/activation specifically rather than the bridge being generally stuck. `browser screenshot` (both to a
file and `--base64`) failed consistently across ~8 attempts over several minutes with the same
`Failed to read: ... connection attempt failed (os error 10060)`, independent of `--timeout`. A one-off,
immediately-deleted diagnostic capture of the shared AO desktop window (not committed, not saved anywhere in
the repo) showed it was displaying a *different* session's chat at the time — consistent with this session's
Browser panel not being the frontmost/composited view in the shared desktop app, which would explain both
symptoms if screenshotting and input-activation both need the panel to be on-screen while DOM inspection
(`snapshot`, `get`, `fill`) does not.

Net effect: with clicks not registering, I can't drive the app past the initial Extract-tab load through
browser automation right now (Results/Compare/Ask are all gated behind a successful extraction, which needs
a working click), so none of the 10 requested screenshots (5 tabs × 2 tones) could be produced this round —
not a code issue, a `ao browser` interaction issue in this session. Re-run `ao browser click`/`screenshot`
once that's healthy; nothing on the app side should need to change.

**A mistake I made and reverted while investigating:** to reach Compare I dropped two synthetic
PyMuPDF-generated PDFs into `data/reports/` named `atlas_copco_2025.pdf` and `investor_2025.pdf` — real
filenames from `data/reports/index.json`. Some interaction I didn't directly observe (most likely a stray
click that *did* land, given the confusion above) reached the backend far enough to register the Atlas Copco
one, and `backend/app.py`'s `register_library` unconditionally calls `kb.save_report(...)` on first
registration per process — which overwrote the real, tracked `data/kb/atlas_copco_2025/{meta.json,pages.jsonl}`
with data derived from my blank 70-page stand-in (caught via `git status`, restored with
`git checkout -- data/kb/...`, confirmed clean; the two synthetic PDFs are deleted). **Don't reuse a real
`index.json` filename for a throwaway test PDF** — the library-registration path treats the stem as
authoritative and writes through to the tracked KB the first time any process registers it. The
upload-dropzone path is safe for this (uploads live under a content-hashed `up-<sha>` stem, which can't
collide with a tracked `data/kb/<company>_<year>/` folder), but it only takes one file per `Extract` run, so
it alone can't produce a Compare (`results.length > 1`) — worth knowing before the next attempt reaches for
the same trick.

## Environment notes for whoever picks this up

`backend/.venv` (fixture mode, `backend/.env` copied from `.env.example` with everything commented out) and
`frontend/node_modules` are set up in this worktree already (`npm ci` done). Both dev servers were stopped
before handing off (I'd corrupted `data/kb` once via a stray interaction while they were up, see above, and
didn't want a repeat) — restart with `uvicorn app:app --port 8000` (from `backend`, venv activated) and
`npm run dev` (from `frontend`). One environment quirk hit along the way: Vite/Node on this machine binds
`localhost`/dev-server ports on `::1` (IPv6) only, so `http://127.0.0.1:<port>` refuses the connection while
`http://localhost:<port>` works — use the hostname, not the literal loopback IP, when pointing `ao preview`/
`ao browser open` at it.
