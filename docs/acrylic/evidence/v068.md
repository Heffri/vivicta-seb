## The bug (v060's finding, now closed)

Ework p.70 and XANO p.84 each print a table's column headers as two physical PDF lines that are **matrix-transposed**:
line 1 holds every column's *first* fragment, line 2 holds every column's *second* fragment (plus every column that
only needs one line) — because a two-line column and its one-line neighbor both set their first/only line at the
same height. Reading order glues these into two lines whose word sequence matches no real left-to-right column
order, and neither existing mechanism can fix it: it isn't a stacked cell (`_stack_cells`/`_group_blocks` chain
*vertically adjacent* fragments within one column, and these fragments across columns are on the same two
baselines site-wide, not one column's own two lines touching), and it isn't two side-by-side tables (`_cut_regions`
refuses a cut when the sides share a row grid, and here every "column" shares the row's own baseline).

## The fix: `_rebuild_transposed_headers` (new, `backend/pipeline/parse.py`)

A new, self-contained step, not a change to `_stack_cells`/`_group_blocks` (v049/v049b's calibration is untouched):

1. **Trigger**: a line with ≥3 bare value-shaped phrases (`_is_amount`: no letters at all — a figure, a lone
   `-`/`–` nil marker) is a table's own data row. Its phrases' own x1 (right edge) are the column positions —
   both companies' printers right-align a column's figures to a shared right edge, and (this lane's finding) a
   wrapped header phrase's *last word* is right-aligned to that same edge, measured exact to <0.2pt on every real
   match found.
2. **Header lines**: walk upward from that row, collecting up to 3 lines (`_HEADER_MAX_LINES`, v060: neither
   company wraps deeper) that have zero value-shaped phrases and at least one phrase reaching past the row's own
   label boundary (the first amount's x0). One bare 1-2 word line confined entirely to the label column (a lone
   fiscal year, Ework's "2025") is skipped over rather than treated as a header line or as a wall — it isn't part
   of the transposed header, but its presence between the header and the row must not block the search reaching
   the real header lines above it.
3. **Column assignment** (`_assign_columns`): each header line's words are first grouped into phrases by gap size
   (`_phrases`, `_PHRASE_GAP=4.0` — real intra-phrase gaps measured ≤1.9pt, e.g. Ework's "< 1 month", XANO's
   space-grouped "51"+"075"; the tightest real inter-column gap measured is 5.5pt), then each phrase is matched to
   the nearest column by right-edge distance (`_HEADER_TOL=2.0`, real matches measured exact to <0.2pt). Declines
   (keeps the original text untouched) the instant any word is not clearly closest to one column: too far from
   every column, tied between two, or repeating a column its own line already claimed. Same-column phrases from
   different header lines stitch top-to-bottom; a trailing hyphen glues directly instead of spacing, so a
   line-wrapped word reassembles ("Total undis-" + "counted value" → "Total undiscounted value").
4. Wired into both places a page's lines get built: `_words_to_lines` (the word-level rebuild XANO's page uses)
   and `_merge_baselines` (the block rebuild Ework's page uses, restructured to collect all groups' rows with
   their bboxes *before* stringifying, so the new step can see across group boundaries — same final row order as
   before when it finds nothing to fix). `PARSER_VERSION` 5 → 6.

**A real regression found and fixed mid-lane, not shipped**: extending each line's stored word tuples from
`(x0, text)` to `(x0, x1, text)` (needed so the new step can read a phrase's own right edge) changed how Python's
tuple comparison breaks a tie when two lines land on the *exact* same y-center — a real scenario on multi-column
pages (two columns' lines set on a shared baseline grid). First full-corpus `--dump-all` diff surfaced this as
word-order swaps on decorative/infographic pages that were never near a table (Academedia p.11, Cloetta p.17,
Viva Wine p.22 — see "the mistake" below). Fixed by sorting with an explicit key that reconstructs the old
`(x0, text)` tuple for comparison everywhere a line or word list is sorted, so `x1` is available to the new
function's own logic without changing any existing tie-break. Confirmed by rerunning the full corpus dump: those
three pages (and every other page the mistake touched) came back byte-identical to the pre-v068 baseline.

## It generalizes: the same fix, unprompted, on other companies' tables

Work order territory was these two pages; the rule is geometric (no company name, no page number anywhere in it),
and the full-corpus `--dump-all` diff shows it firing correctly well beyond them — the same "1-3 wrapped/short
header lines above a numeric row" shape recurs across the corpus (financial-instrument tables, statements of
changes in equity, HR/gender-split notes, associate-holdings tables...). A random sample of 15 of the 285 pages
`--dump-all` shows changed on pymupdf 1.27 (seed 42, reviewed by hand) is 15/15 correct reconstructions, e.g.:
- Cloetta p.33 (shareholder table): `No. of % of` / `Country shareholders votes % of share capital ...` →
  `Country No. of shareholders % of votes % of share capital ...` — reconciles against the row's own 5 amounts.
- Cloetta p.148 (statement of changes in equity, a **3-line** transposed header): `Other ­currency` / `Share
  paid-in Treasury ­translation Retained Total` / `SEKm capital capital shares reserve earnings equity` →

  Total equity`.
- Catella p.101: `Non-` / `controlling interests * Total equity` → `...Noncontrolling interests * Total equity`
  (the same hyphen-rejoin mechanism as Ework's "undiscounted", on an unrelated word).
- Arjo p.114, Storytel p.89, Boozt p.129, Fasadgruppen p.116/127, Hansa Biopharma p.72, Atlas Copco p.138,

`_DEBT_ROW_SYNONYMS` fallback (`_label_known` → True). `_bucket_header` now reads the rebuilt single-line header
and returns **7** column keys (`total, due_within_1_year×4, due_1_to_5_years, due_after_5_years`) against the

## labels.csv — the Ework dispute v060 raised, resolved by this lane's bbox reconstruction

v060 flagged that `eval/labels.csv`'s Ework figures (`due_within_1_year=154732` = 0+153,761+971,
`due_1_to_5_years=1677`) might not match the PDF's true column structure. This lane's bbox-verified column order
(above, cross-checked against the table's own Total-row arithmetic) confirms **v060 was right**: the true 8-column
order is `Due, <1 month, 1-3 months, 3-12 months, 1-5 years, >5 years, Total undiscounted value, Carrying amount`.
Under that order, the report's own `1-5 years` column for this row is nil (`–`), and `1,677` is the row's own
**`3-12 months`** column — a month-granularity column, not `due_1_to_5_years` at all. `labels.csv`'s own
`due_1_to_5_years=1677` therefore labels the wrong bucket (schema semantics aside: `due_within_1_year`'s own
description says a first-year split like "3-12 months" should be *summed into* `due_within_1_year`, not read as
`due_1_to_5_years`). The schema-consistent reading is `due_within_1_year = 0+153,761+971+1,677 = 156,409`
(within ±1 rounding of the row's own `total_debt=156,410`) and `due_1_to_5_years = 0` (the report's own `1-5
years` column is nil for this row) — not `154,732`/`1,677`. Flagging for whoever owns `eval/labels.csv` next, per
the work order; not edited here (out of this lane's territory, and a labels-file edit deserves its own review).
