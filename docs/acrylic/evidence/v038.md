## 0. Owner complaint this fixes

14:50: "窗口无法拖拽,只能钉在屏幕中央" (window can't be dragged, stuck pinned to screen center).
Root cause, already diagnosed in the work order: `desktop/main.js`'s `titleBarStyle: 'hidden'`
removes the system titlebar, and nothing in the frontend's own `Titlebar.tsx` declared
`-webkit-app-region: drag`, so Chromium had no drag region at all — every hit-test in the custom
titlebar resolved to plain `HTCLIENT`, indistinguishable from clicking inside the page.

## 3. Why 138px is conditional, not unconditional

Work order acceptance explicitly requires "浏览器里标题条外观不变" (titlebar look in the browser
must not change). `window.arp` is only ever defined inside the Electron shell (`preload.js`'s
`contextBridge.exposeInMainWorld`); a browser tab never has it, so `isWindowsDesktopShell` is always
`false` there and `pr-[138px]` never applies — the header's classes reduce to exactly what they were
before this lane, plus `app-titlebar`. `-webkit-app-region` itself has no visual/layout effect (it's
an OS drag-region hint, not a rendering property), so `app-titlebar` alone is inert in a browser tab
too. Not screenshotted for this specific claim — it follows from the condition being structurally
unreachable outside Electron (same pattern `main.tsx` already relies on for `data-material`), not
from empirical comparison.

## 4. Verified live (Windows message-level, not read from source)

Launched `desktop` in dev mode for real (`electron .` against this worktree's `backend`/`frontend`,
isolated with `--user-data-dir` pointed at this lane's scratch dir — see §6 for why) and queried the
real window's real `HWND` directly with `user32.dll` P/Invoke from PowerShell — chosen over actually
moving the shared machine's mouse cursor, which would be a real, disruptive input event on a box the
owner is using live (LESSONS.md #31 same spirit, extended from screenshots to input injection).
`WM_NCHITTEST` is a query message (asks "what's at this point", doesn't require the cursor to
actually be there); `WM_NCLBUTTONDOWN`/`UP`/`DBLCLK` sent directly to the window's `HWND` via
`SendMessage` exercise the exact same code path a real click does (Chromium's `WM_NCHITTEST` handler
answers from the draggable-region info the renderer already reported; Windows' own `DefWindowProc`
owns the maximize/restore toggle on `HTCAPTION` double-clicks — none of this is our code, we're
verifying the region is wired so Windows' native behavior applies) — but neither call moves the real
cursor or generates real global input, so nothing else on the shared desktop is touched.

**Drag region wiring** (window at `L=240,T=126,R=1680,B=1026`):

| Point | Where | `WM_NCHITTEST` result |
|---|---|---|
| title text (left+100, top+20) | over "Annual Report Parser" | `HTCAPTION` (draggable) |
| subtitle text (left+300, top+20) | over the subtitle span | `HTCAPTION` (draggable) |
| reserved corner (right-100, top+5) | inside the 138px caption reserve | `HTMENU` — Electron's own `titleBarOverlay` hit-test marker for its native button area, not ours to set; confirms that zone is correctly ceded to the OS overlay rather than double-claimed by our CSS |
| content area (left+100, top+80) | below the titlebar, in the app body | `HTCLIENT` (not draggable) — confirms the drag region is scoped to the titlebar only, not the whole window |
| right edge / bottom edge / left edge | window border | `HTRIGHT` / `HTBOTTOM` / `HTLEFT` — resize borders still live |

`GetWindowLongPtr(GWL_STYLE)` = `0x14C70000`, `WS_THICKFRAME` bit set → resizable, confirming item 4's
"拉伸" without needing a code change (nothing in this lane touches sizing).

**Double-click maximize/restore** (no `onDoubleClick` handler added anywhere — this is item 2's
"Windows 上拖拽区默认支持,实测确认" branch): `IsZoomed` before = `false`. Sent
`WM_NCLBUTTONDOWN`+`UP`+`WM_NCLBUTTONDBLCLK` (`wParam=HTCAPTION`) at the title-text point →
`IsZoomed` = `true`, window rect became `L=-8,T=-8,R=1928,B=1160` (full-screen-minus-invisible-border,
the normal Windows maximized geometry). Recomputed a titlebar point against the **new** bounds (a
point valid before maximizing is usually not inside the titlebar band after — the maximized window is
larger and repositioned) and repeated the same message sequence → `IsZoomed` = `false`, window rect
back to the **exact** pre-maximize values (`L=240,T=126,R=1680,B=1026`). Full round trip, native,
zero lines of app code.

## 7. Environment note for later lanes (not a code change, just flagging)

Running `desktop`'s dev mode a second time on this machine while another copy is already live (even
a different lane's) makes the new instance's `app.requestSingleInstanceLock()` fail and the whole app
silently `app.quit()` at start — no dialog, no log line, exit code 0, easy to mistake for "it launched
and closed itself" instead of "it never got a lock". Cause: `app.getPath('userData')` defaults to
`%APPDATA%\annual-report-parser-desktop` (from `desktop/package.json`'s `name`) for every worktree
that doesn't override it, so any two concurrent dev-mode launches — this lane's own retry included —
collide on the same lock regardless of which checkout they're running from. Worked around here with
`electron . --user-data-dir=<lane-scratch>\userdata` (Electron's own built-in switch, no code change)
to get an isolated instance for the §4 tests. Not fixed in `main.js` — out of scope for this lane's
territory and not something the owner's reported bug needs — just recording it in case another lane
hits the same silent-exit-0 shape.
