# v081 — a second model ask for the IR page when direct links fail; prefer the complete report over a summary

Branch `ao/vivicta-seb-65/v081-fetch-model-retry`, off `origin/acrylic` at dispatch (`d0a2d64`). Backend
only: `pipeline/fetch.py` (the `SEARCH_SYSTEM`/user-prompt wording, a new second model ask, and the
fourth source's candidate ranking), `pipeline/test_fetch.py` (4 new assertion groups, `16`-`19`). No
frontend, no other pipeline module, no `data/reports/index.json` changes. Real Codex **web-search**
calls: **4 of the 6 allowed** (2 kept in reserve) — full accounting in Green, below.

## The two fixes

**(a) Second ask.** Once every fourth-source (v074) direct-link candidate has failed (404, not a PDF,
or failed validation) *and* the fifth source's (v080) generic `_IR_PATHS` guesses have also found
nothing, `fetch_report` now asks the model once more — a new, narrower system prompt (`IR_PAGE_SYSTEM`)
that asks only for the company's investor-relations or annual-report-archive **page** (never a PDF,
at most 2 URLs) — and feeds whatever it returns into the same `_ir_page_report` crawl v080 already
built. At most one extra call: **two model calls total per `fetch_report()` call**, enforced by
construction (the second ask sits behind `if p:`, the same provider flag the first ask already set,
never behind a loop).

**(b) Prefer the complete report.** `SEARCH_SYSTEM` now explicitly asks for "the complete annual report
(the full document), not a summary, highlights, at-a-glance, or annual review excerpt". The fourth
source's own candidate loop no longer returns on the first candidate that downloads and validates —
it now tries all of them (still capped at `MAX_MODEL_CANDIDATES=3`) and, once every one has been tried,
picks the best by `(pages >= 80, a clean filename, page count)` — a summary/highlights/at-a-glance/
short/in-brief excerpt is only ever accepted when nothing among the candidates clears that bar, and
when it is, `note` says so (`"model search (codex); summary volume"`).

## What actually changed in `fetch.py`

- `SEARCH_SYSTEM` gained one sentence (the complete-report preference), placed before the existing v080
  sentence about an IR-page URL being acceptable as a direct-link fallback.
- New `IR_PAGE_SYSTEM` + `MAX_IR_PAGE_CANDIDATES=2`, and `_ir_page_candidates()` — the second ask itself:
  same shape as `_model_candidates` (same `(urls, note)` return, same country/hint prompt), but a
  candidate that is itself a `.pdf` is dropped (this ask is for a page; a PDF answer means the model
  ignored the instruction and would just duplicate what the first ask already tried).
- New `FULL_REPORT_MIN_PAGES=80`, `SUMMARY_WORDS` regex, `_label_clean()`, `_is_full_report()`,
  `_best_model_candidate()` — the ranking itself. `_label_clean` checks the URL's own filename only:
  the model's `title` field isn't retained past `_model_candidates` today, and threading it through
  would have changed that function's return shape for every caller and test; the filename is what
  "标题/文件名" resolves to in practice, and it is sufficient for both live targets (page count alone
  already demotes Nestlé's real Annual Review, 67p, well under the 80-page floor).
- `fetch_report`'s fourth-source loop: `hits.append((url, data, text, doc.page_count))` in place of an
  immediate register-and-return; once the loop is exhausted, `_best_model_candidate(hits)` (if `hits`
  is non-empty) picks the survivor, and `_is_full_report` decides the `note` suffix. Every other branch
  of that loop (the two `page_seeds` bookkeeping lines, the `tried` list, the cap) is untouched.
- `fetch_report` gained one new block, after the pre-existing (v080) fifth-source attempt and before
  the final `raise`: if a provider was configured (`p`, the same flag the first ask already set), call
  `_ir_page_candidates`, drop anything already in `page_seeds` (no point re-crawling a page the first
  attempt already tried and failed), and if anything new is left, run it through `_ir_page_report` —
  succeed exactly like the fifth source's first attempt (`note: "IR page crawl"`, `tags: ["fetched",
  "foreign"]`), or fold the second ask's own failure note (if it errored) into the final `LookupError`.
- `_ir_page_report`, `_ir_links`, `_crawl_ir_page`, `_host_guesses`, `_IR_PATHS`, `_stub_pages`,
  `_model_candidates`'s own filtering, `_filename_clear`, and every source above the fourth are
  **untouched** — the second ask only ever calls the existing crawler with new seeds, and the ranking
  only ever reorders what the fourth source's loop already downloaded.

## Tests

`backend/pipeline/test_fetch.py` — 15 pre-existing assertion groups (v074 + v080 + its follow-up) plus
4 new (v081), all against the loopback server, zero real model calls:

- **16.** The second ask fires only once every direct-link candidate *and* the first IR-page crawl
  attempt have both failed — the model's only "direct link" answer is itself an IR page with nothing
  useful on it, so the first crawl genuinely runs (not skipped for lack of seeds) and finds nothing;
  the second, narrower ask then names the real reports page, and exactly two model calls happen in
  total (asserted on `fake.calls`' length and each call's `system` prompt: `SEARCH_SYSTEM` then
  `IR_PAGE_SYSTEM`) — never a third.
- **17.** When more than one model candidate downloads and validates, the complete report wins even
  when the summary-shaped one is listed *first* — proves the fix is a real ranking, not just an
  outright rejection of anything summary-shaped.
- **18.** A lone candidate that validates but stays under the 80-page floor is still accepted (better
  than nothing) but `note` flags it as a summary volume — using a filename with no
  summary/highlights/at-a-glance/short/in-brief word at all (`nestle-annual-review-2025-en.pdf`), i.e.
  page count alone is enough to demote it, mirroring Nestlé's real shape exactly.
- **19.** Unit-level: `_is_full_report` at the exact page-count boundary (79 vs 80) and against a
  long-but-summary-named filename; `_best_model_candidate` picking the one candidate (of three) that
  is both long enough *and* cleanly named; `_ir_page_candidates` dropping a `.pdf`-shaped answer
  outright and capping at `MAX_IR_PAGE_CANDIDATES`.

Groups 1-15 pass unchanged. Two fixture changes were needed for group 2/3/9/10/12/14's *existing*
assertions to keep holding under the new 80-page floor: `_write_pdf`'s default page count moved from
45 to 90 (so `GOOD_PATH` and `SHELL_SHAPE_PATH`, which both use the default and are meant to represent
a genuine full report in those scenarios, clear the new floor and keep registering with a plain
`"model search (codex)"` note, no summary suffix) — `REVIEW_PATH`/`FULL_PATH` keep their own explicit
`pages=45`/`pages=60` (group 11's own "which of two is bigger" logic, level 5, untouched by this lane).
Three new fixtures: `EMPTY_IR_PAGE_PATH` (a page with nothing on it, for group 16), `SUMMARY_PATH` and
`REVIEW_SHAPE_PATH` (two distinct summary shapes — one flagged by filename, one only by page count —
for groups 17/18). `_FakeWebLookup` now picks `FAKE_WEB_REPLY_IR_PAGE` over `FAKE_WEB_REPLY` when the
call's `system` is `IR_PAGE_SYSTEM` *and* that env var is set; every pre-v081 test never sets it, so
both asks in those tests still read the same single scripted `FAKE_WEB_REPLY`, unchanged.

## Green — live Shell + Nestlé (`LLM_PROVIDER=codex`)

Full account, every URL the model returned, and the exact failure shape for each:

| Target | Result | Calls used |
|---|---|---|
| Shell 2025 | **404** — direct link is the same expired-token URL v074/v080 already recorded; the second ask correctly surfaces two real, specific Shell IR-section URLs (distinct from the generic guess list) but neither page's static HTML exposes a scrapeable PDF link to this lane's crawler | 2 (direct-link ask + second ask) |
| Nestlé 2025 | **200**, 67 p, unchanged from v074/v080 — now correctly labelled `note: "model search (codex); summary volume"` instead of an unqualified hit | 1 (only the direct-link ask; it succeeded, so the second ask never runs) |

**Shell is not fixed by this lane, with the failure shape now precisely diagnosed one level deeper than
v080 left it.** v080 diagnosed *why* the model's direct link fails (an expired token). This lane adds
the second ask, confirms live that it does exactly what it is supposed to — ask a narrower question,
get a narrower, more specific answer (two real Shell IR-section URLs, not just the generic
`_IR_PATHS` list) — and then, by crawling those two URLs directly at zero extra model cost (see
`green-results.txt` §3-4), confirms the *next* obstacle: neither page's server-rendered HTML contains
a plain `<a href="...pdf">` this lane's regex-based one-hop crawler can find, nor a same-domain hop it
recognises. Shell's real report link most likely loads client-side (JS); going further (a headless
browser, recursive multi-hop crawling) is outside this lane's scope (work order: 不加依赖, and the
fifth source's crawl mechanism itself is v080's territory, not touched here).

**Nestlé's summary volume is unchanged, now honestly labelled.** This is the *third* consecutive real
call, across three separate lanes (v074, v080, this one), to return the exact same 67-page Annual
Review URL as Nestlé's only candidate — including after `SEARCH_SYSTEM` was given an explicit
instruction to prefer the complete report. The instruction only has candidates to choose between when
the model actually returns more than one; with a single candidate there is nothing to rank, so this
lane's actually-new behaviour for this exact case is the honest `summary volume` label, not a
different file. The ranking logic itself (choosing the complete report over a summary when *both* are
offered) is proven working — just in `test_fetch.py`'s groups 17-18, deterministically, since neither
live company handed back a competing pair today for it to choose between (the same situation v080
documented for its own fifth-source mechanism).
