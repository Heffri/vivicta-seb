## 6. Real bugs hit this lane — all in the test harness, none in shipped code

1. **A CDP test driver can silently defeat the app's first-launch data seed.** The driver created
   `<userData>/data/reports/` (to copy the atlas PDF into) before the shell's
   `ensureUserData()` had run; the shell then saw `data/` already existing and **skipped the entire
   one-time seed** — no `companies.json`, no `data/kb/`, no `data/reports/index.json` — after which
   the fixture upload 500'd (`FileNotFoundError ... reports/index.json`, read from backend.log).
   The app's own code is correct and v032/v055's flows just happened to copy later; any automated
   double-click test that touches `<userData>/data` before the seed finishes can hit this. Fixed in
   the driver: wait for the seed's own markers (`data/companies.json` +
   `data/reports/index.json`) before copying anything into the profile.
2. **`button:has-text("Extract")` clicks the rail tab, not the action button.** The rail's tabs are
   `<button role="tab">` elements that come first in DOM order, and Playwright's CSS engine
   resolves a multi-match `page.click` to the first — so the driver "clicked Extract" twice while
   really clicking the already-active tab (two silent 120 s timeouts before diagnosis). Same trap
   for "Ask". Fixed with `getByRole('button', { name, exact: true })` (role=tab is not role=button).
3. **An async `taskkill` + immediate `process.exit` orphans the tree.** The first driver's
   success-path cleanup spawned the kill and exited before it ran; four Electron processes
   survived (found via `Get-CimInstance` on my own profile path, killed by PID). All kills are
   `spawnSync` now, and every run end verifies zero survivors.
4. **Assertions on rendered numbers must match `fmtValue`, not the JSON.** The Results view
   formats thousands separators as spaces (`168 343`), so a `168,343` substring check fails on a
   correct screen — caught by looking at the actual screenshot, not by trusting either the boolean
   or my first reading of it (same discipline as v055 §6-2).
5. **Finding, not fixed (out of territory):** after Settings → Save, the bottom status bar keeps
   its mount-time config until the app is relaunched — `App.tsx` fetches `/api/config` once on
   mount, so the footer shows the *previous* provider (e.g. `fixture · bge-m3`) in the window
   between Save and next launch, while the Settings strip is already correct. Pre-existing behavior
   (v056 changed what the footer renders, not when it refreshes); check (f) passes via the natural
   user flow (relaunch), and a refresh-on-save would be a one-line `frontend/src` change for a
   future lane, noted not done here.
