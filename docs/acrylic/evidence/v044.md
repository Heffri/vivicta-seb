## The gap (v041 finding 3)

`maturity_sums_to_total`'s `null_as_zero` (v011) counts a null bucket as 0 once at least one sibling bucket is
real, so the identity can still be checked against whatever the report does print. That conflates two different
situations a null value cannot otherwise distinguish: a bucket the report genuinely never prints (Ericsson: no
`>5y` row — a real 0) and a bucket the report prints but the model failed to extract (MedCap/Ependion, v041's
own seed 3: the model *correctly computed* the bucket's value but had no literal quote for it, so the pipeline
correctly dropped it as "computed, not read" — the row is there, only the number-extraction step didn't land).
Zero-filling the second case fails the identity outright (not "missing"), which caps every other operand's
confidence at 0.5 for a gap that isn't theirs.

## What changed (2 files, +97/−11 before the v043 merge)

- **`backend/pipeline/extract.py`, `_check`** — gains four optional, keyword-only args: `texts`, `pages`,
  `fields`, `schema`. When a listed operand is null and at least one sibling is real (the existing gate,
  unchanged), each null operand is now checked individually: search the pages the check's *other*, real
  operands were sourced from, plus the full candidate-page list, for the null field's own synonym label — same
  `normalize_ws` digit-gluing v012/v014 already use to make `"Within 1 year"` and `within1year` compare equal,
  applied per `_page_rows` row (not the model's `_row_label` prefix-isolation, which truncates at the first
  bucket boundary and would miss a label sitting after a unit token like `"MSEK <1 år"` — see Design notes).
  Found → leave the key out of the substitution, so `eval` raises `NameError` and the check reads
  `"missing: <field>"`, byte-identical in shape to the pre-existing "every listed operand is null" missing case
  (same downstream consumers, see Compatibility). Not found → 0, exactly as before. The four new args default to
  `None`; every call site that doesn't pass them (unchanged) gets the pre-v044 unconditional zero-fill.
- **`backend/pipeline/extract.py`, `extract()`** — the 6 call sites that recompute a check from the *current*
  `values` (no hypothetical override) now pass `texts=texts, pages=pages, fields=fields, schema=schema`. The 4
  call sites that test a *hypothetical* substituted value for one field (deciding whether to accept a repair)
  are deliberately left as 2-arg calls: their boolean result is unaffected either way (`missing` and `failed`
  are both `passed: False`), and not exposing them avoids the new label-search flipping a repair-probe's verdict
  on a still-null *sibling* bucket that has nothing to do with the field being probed.
- **`backend/pipeline/test_confidence.py`** — the cases below, plus one pre-existing case's expectation updated
  (see Regression note).

## Design notes

- **Row-level, not whole-page-blob.** Search is `normalize_ws(synonym).lower() in normalize_ws(row).lower()`
  per `_page_rows(text)` row, not one join of the whole page — collapsing everything through `normalize_ws`
  (which drops every space touching a digit and folds newlines to spaces) before splitting into rows would let
  a number at the end of one line glue to a bucket word at the start of the next, a straightforward source of
  false positives.
- **Substring, not `_label_known`'s prefix match.** MedCap's own contractual-table column header prints
  `"MSEK <1 år 1 – 2 år 2 – 4 år 4 – 5 år >5år"` as one physical line (`_page_rows` returns it whole, no
  per-column split — this is a header, not a labelled row). `_row_label` cuts this down to `"MSEK <1 år"` (the
  first number not followed by a lowercase word), and `_clean_label` then strips `"MSEK"` as a currency token —
  leaving a **leading space** (`" <1år"`) that breaks a prefix match against the synonym's cleaned form
  (`"<1år"`). Reusing `_label_known(_row_label(row), sf)` as originally planned misses this row entirely;
  a plain substring test over the row's own `normalize_ws` form does not, and needs neither function.
- **`normalize_ws` only, not the full `_clean_label` pipeline.** `_clean_label` also does currency-stripping,
  `result`→`profit`, and footnote-marker removal — useful for isolating *one* label, but applied to a whole page
  of running prose those extra steps are more likely to manufacture an accidental match than a genuine one, and
  none of `debt_maturity`'s 22 synonyms need them (`_clean_label(s) == normalize_ws(s).lower()` for every one of
  them — verified, see Gates). `normalize_ws` is the one piece of `_clean_label` this task actually needs: the
  digit-gluing that makes `"< 1 år"` and `"<1 år"` compare equal.

## Regression note: one pre-existing case's expectation changed, correctly

`test_confidence.py`'s own XANO Industri case (v035/v036, real Note text) hits this exact mechanism. Its header
line prints `"...Summa Mellan 1 Mellan 3 Efter 5 år Totalt"` whole — `"Efter 5 år"` is a complete, unwrapped
column header (only `"Summa"`/`"Mellan 1"`/`"Mellan 3"`'s continuations wrap to the next physical line, the
`_page_rows` scrambling the original case documents) — so `due_after_5_years`'s own label genuinely is on the
page, even though the safety valve correctly refuses to attribute any number to it (column order is unrecoverable
once the header wraps). Before v044: `due_1_to_5_years` and `due_after_5_years` both zero-filled,
`51,075 ≠ 904,522`, hard **failed**, `total_debt`/`due_within_1_year` (both independently quote- and
label-verified) capped at 0.5 for a gap that is provably not theirs. After: `due_1_to_5_years` stays a confirmed
0 (no matching synonym anywhere — its own header words wrapped away entirely, unrecoverable), but
`due_after_5_years`'s presence turns the check into `"missing: due_after_5_years"`, and the two verified fields
reach 1.0. This is precisely the class of case this lane exists to fix, so the test's own expectation was
updated (with a comment explaining why) rather than treated as a regression to avoid — see the file for the
full reasoning inline.

## Finding: the work order's Ependion premise doesn't hold — reported, not routed around

The work order groups MedCap and Ependion as one red case expected to both flip to `missing`. MedCap does.
Ependion does not, and cannot under this lane's territory: its bucket table (p.155) prints its second and third
buckets as **`"Within 12 months"` / `"Between 1 and 2 years"` / `"Between 2 and 3 years"`** (spelled out, and
scrambled across separate `_page_rows` fragments by a sidebar TOC column glued onto the same physical lines —
v041's own diagnosis, "parser gap", out of scope both then and now). `debt_maturity.json`'s synonyms for
`due_1_to_5_years` are all digit-form (`"1-5 years"`, `"1-2 years"`, `"between 1 and 5 years"`, …) — verified
offline, by hand and by the row-search this lane adds, that **no synonym of either null bucket appears anywhere
on Ependion's candidate pages** (155, 156, 122 — full text read and checked), digit-glued or not: `"between 1
and 2 years"` normalizes to `"between1and2years"`, which is not a substring of, and does not start with,
`"between1and5years"` (the schema's only spelled-out synonym) — a different number, not a normalization gap.
v041 already flagged this exact shape as a schema-vocabulary gap ("the spelled-out … wording doesn't exist in
the schema at all yet regardless"), separate from the null-vs-missing conflation this lane fixes. Fixing it
would mean adding schema synonyms, explicitly out of this lane's territory (`不碰 schema`) — recorded as a
locked-in "stays red, correctly" test case (case 4 above) rather than silently only doing the achievable half.

## Compatibility

`score_field`'s `missing:`-prefix check (`not c["detail"].startswith("missing:")`) and the repair loop's exact-key
parse (`c["detail"].split(": ", 1)[1]`, used to target a `_between_rows` repair attempt at the named field) both
see `"missing: <field>"` in exactly the pre-existing shape — deliberately not annotated further (an annotation
would corrupt that split's exact-key match). The two situations ("all buckets null" vs. "this specific bucket's
label is on the page") are distinguished by which of the two response *shapes* a check ends up in (the
substituted-expression detail's `"0 (<key> null)"` annotation for a confirmed zero, vs. the bare
`"missing: <key>"` for this lane's new case) — both already existed; nothing new needed exposing.

## Contract

`docs/API.md` untouched: no response field, check, or endpoint changed. The only response-visible difference is
the `detail` string for a check that hits this exact shape (real bucket present but a sibling bucket's label
also findable), and the resulting confidence for that check's other, verified operands.
