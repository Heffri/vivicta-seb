## Concrete failure paths found and fixed

Although the machine-specific exit was not reproducible, the audit found three real faults that
either produce the reported ghost shape or make a renderer loss look like a whole-app exit:

1. `library_index()` accepted any existing filename. A truncated `%PDF...` file plus an index row
   was listed as cached, then PyMuPDF failed when the row was opened.
2. A valid JSON Codex reply with the wrong top-level type escaped candidate parsing as an unhandled
   `AttributeError`/500 instead of becoming the existing bounded search-failure response.
3. The desktop shell had no global `render-process-gone` handler, so a renderer loss had no
   `crash.log` classification or recovery choice.

Downloaded bytes now go to a same-directory temporary file, are flushed and `fsync`ed, opened from
disk with PyMuPDF, atomically renamed to the final PDF name, opened again from that final path, and
**only then** added to `index.json`. A publish/index failure removes its temporary/final artifact
and returns HTTP 503 with `retry download`; cleanup trouble cannot mask that explicit error. A
corrupt old cache hit is removed and discovery runs again. `/api/library` and `/from-library`
independently refuse unreadable PDFs, so an old partial file cannot surface before the retry.

All PyMuPDF documents opened during fetch validation are closed on rejection and success paths.
Model discovery validates the JSON container before reading `candidates`, turning a wrong-shaped
reply into the same explicit failure note as malformed JSON, timeout, nonzero CLI exit or missing
output. After merging v194, success/failure/cache events continue to settle the same search job.

The first packaged smoke of the merged tree exposed one integration corner without crashing: a
cached PDF is resolved by `app.py` before `pipeline.fetch.fetch_report()`, so its fresh v194 job id
was never created and the renderer console logged a final progress-poll 404 even though fetch
returned 200. `2d1449a` now settles that fast path in `app.py`; its route regression requires a
terminal `done`/`already cached` event. After rebuilding the packaged app at `2d1449a`, the full
Nvidia UI path returned discover 200 in 19.9 s, cached fetch 200 in 1.3 s and **Done** in 22.1 s with
zero renderer console/page errors, zero unexpected lifecycle events, one live window, and no
`crash.log`. [Final merged packaged smoke](v193/final-merged-nvidia-done.png).

The desktop main process now records `child-process-gone` and unexpected `render-process-gone`
details in `logs/crash.log`. It leaves the main process and backend alive and presents a native
dialog offering **Reload window** or a deliberate close; clean shutdown is ignored.

UAW was searched for the same lifecycle pattern. Its
`src/workbench-shell/electron/main.ts` has window-scoped terminal listeners, and modules such as
`history-recovery-ipc.ts` use `render-process-gone` to clean up sender state, but it has no equivalent
global reload dialog to port. This app follows the same direct WebContents-listener shape and adds
the shell-specific recovery choice.

## Red → green regression evidence

Red observations on the pre-fix implementation:

- `python -m pipeline.test_fetch` failed because `library_index()` returned a row for a file
  containing only `%PDF-partial`.
- `node desktop/packaging.test.js` failed because `main.js` had no `render-process-gone` listener.

Green coverage proves:

- unreadable indexed files are absent from `/api/library` and rejected by `/from-library`;
- a corrupt cache hit is removed and re-enters discovery rather than being returned;
- an injected failure at the PDF atomic rename leaves no final PDF, index row, or `.tmp` file;
- storage failure is HTTP 503 with an explicit retry message, not an unhandled 500;
- a wrong-shaped but valid JSON search reply becomes a bounded `LookupError` note;
- v194's job events remain present across the integrated discover/fetch paths;
- a cached fetch settles its v194 job instead of generating a renderer-side progress 404;
- the packaged shell contains renderer crash logging and the reload dialog path.
