## Packaged-app reproduction: the reported crash did not reproduce locally

I rebuilt the shared unpacked **packaged app** from the untouched dispatch baseline, then launched
the packaged executable with a new, pre-created and quoted `--user-data-dir` whose path contains a
space. Its saved provider was Codex (`gpt-5.6-terra`), and the packaged `backend.exe` was the process
serving the app. These were real Codex web searches, not fixture responses.

| Baseline action | Result |
|---|---|
| Search `Nvidia` | HTTP 200, about 35 s, one NVIDIA Corporation candidate |
| Search `Intel` | HTTP 200, 27.8 s, one Intel Corporation candidate |
| Search `AMD` | HTTP 200, 22.8 s, one Advanced Micro Devices, Inc. candidate |
| Confirm/download NVIDIA | HTTP 200, 6.1 s, 130 pages, 1,274,715 bytes |
| Confirm/download Intel | HTTP 200, 26.7 s, 149 pages, 75,871,684 bytes |
| Confirm/download AMD | HTTP 200, 5.6 s, 154 pages, 5,801,947 bytes |

After all six requests the Electron main process, renderer and packaged backend were still alive.
There was no `crash.log`; all discover/fetch requests in `backend.log` ended in 200. Therefore the
specific colleague-machine exit cannot honestly be assigned a proven root cause from this machine.
The relevant redacted log shape was:

```text
launch … (isDev=false)
backend source: <packaged app>/resources/backend/backend.exe; llm provider: codex
POST /api/reports/discover … 200 OK
<official PDF URL> -> ok (<pages> pages, <seconds>s, confirmed url)
POST /api/reports/fetch … 200 OK
```

The audit did find three concrete failure paths that previously obscured or amplified such a report:

1. `library_index()` accepted any existing filename. A truncated `%PDF…` file plus an index row was
   listed as a cached report, then PyMuPDF failed when the row was opened — the reported ghost shape.
2. A valid JSON Codex reply with the wrong top-level type escaped candidate parsing as an unhandled
   `AttributeError`/500 instead of becoming the existing bounded search-failure response.
3. The desktop shell had no global `render-process-gone` handler. A renderer loss produced no
   `crash.log` classification or recovery choice, so a blank/vanished page was indistinguishable from
   a whole-app exit to the user.

## Fix

Downloaded bytes now go to a same-directory temporary file, are flushed and `fsync`ed, opened from
disk with PyMuPDF, atomically renamed to the final PDF name, opened once more at that final path, and
only then added to `index.json`. A publish/index failure removes its temporary/final artifact and
returns HTTP 503 with `retry download`; a corrupt old cache hit is deleted and discovery runs again.
`/api/library` and `/from-library` independently refuse unreadable PDFs, so an old partial file cannot
be surfaced even before the user retries. Every PyMuPDF document opened by fetch validation is now
closed on both rejection and success paths.

Model discovery also validates the JSON container before reading `candidates`, turning a wrong-shaped
reply into the same explicit search failure note as malformed JSON, timeout, nonzero CLI exit or a
missing output.

The desktop main process now records `child-process-gone` and unexpected `render-process-gone`
details in `logs/crash.log`. It keeps the main process/backend alive and shows a native dialog offering
to reload the window (or close deliberately); clean exit during app shutdown is ignored.

UAW was searched first for the same lifecycle pattern. Its
`src/workbench-shell/electron/main.ts` documents many window-scoped terminal listeners, and modules
such as `history-recovery-ipc.ts` use `render-process-gone` to clean up sender state, but it has no
equivalent global reload dialog to port. This app keeps UAW's direct WebContents lifecycle-listener
shape; the user-facing recovery is specific to this shell.

## Red → green regression evidence

Red observations on the pre-fix implementation:

- `python -m pipeline.test_fetch` failed because `library_index()` returned a row for a file containing
  only `%PDF-partial`.
- `node desktop/packaging.test.js` failed because `main.js` had no `render-process-gone` listener.

Green coverage now proves:

- unreadable indexed files are absent from `/api/library` and rejected by `/from-library`;
- a corrupt cache hit is removed and re-enters discovery rather than being returned;
- an injected failure at the PDF atomic rename leaves no final PDF, index row, or `.tmp` file;
- storage failure is HTTP 503 with an explicit retry message, not an unhandled 500;
- a wrong-shaped but valid JSON search reply becomes a bounded `LookupError` note;
- the packaged shell contains renderer crash logging plus the reload dialog path.

## Fixed packaged-app verification

The app was rebuilt again from `30e9fa2` and launched with a second clean, quoted user-data directory.
The same three real Codex searches and confirmed downloads completed as follows (candidate URLs can
change between live searches, so page counts differ from the baseline run):

| Query | Discover | Download + register | Total | PDF | Pages |
|---|---:|---:|---:|---:|---:|
| Nvidia | 29.0 s | 17.8 s | 46.8 s | 49,970,589 bytes | 181 |
| Intel | 21.0 s | 11.2 s | 32.2 s | 34,639,749 bytes | 126 |
| AMD | 20.5 s | 4.4 s | 24.9 s | 5,801,947 bytes | 154 |

For every row, a fresh PyMuPDF open reported `is_pdf=true` with the same page count as the API; there
was exactly one index row, zero report-cache `.tmp` files, and `GET /api/reports/{id}` succeeded. The
Electron main process and packaged backend remained alive and `crash.log` was still absent. The
screenshot [`v193/packaged-nvidia-downloaded.png`](v193/packaged-nvidia-downloaded.png) is the packaged
backend's live UI filtered to the newly downloaded NVIDIA entry (181 pages); it was visually checked
after capture.
