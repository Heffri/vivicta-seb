## What changed

- **`backend/pipeline/llm.py`** — `chat()` grows an opt-in gate: with `LLM_STRICT_SCHEMA=1` set, the
  CLI providers now hand the caller's `schema` onward, the same way `_openai_chat()` has always passed
  it as `response_format={"json_schema": ...}`:
  - `codex exec` gets `--output-schema <file>` — per its own `--help` this is a FILE path ("Path to a
    JSON Schema file describing the model's final response shape"), so the schema is written to
    `response-schema.json` inside the call's own `-C` temp dir (inside the read-only sandbox, never the
    repo).
  - `claude -p` gets `--json-schema <inline JSON>` — its `--help` shows `--json-schema <schema>` with an
    inline JSON object as the example, i.e. a string value, **not** a file path; it goes on argv as one
    element (subprocess list form, so no quoting).
  - Fallback: if the strict attempt fails — a CLI build without the flag, or any non-zero exit /
    timeout — `chat()` retries once **without** the flag and issues a `warnings.warn` naming the
    fallback. The switch can therefore only add a retry; a reply today's code would have gotten is
    unchanged, and the fallback's own failure is what the caller sees (extract.py's timeout-shaped
    retry logic keeps working: the fallback re-raises `TimeoutExpired` as-is).
  - Parsing is unchanged: same `<think>` strip, same fence strip, same `json.loads` upstream.
  - `web_lookup()` is untouched (no schema flag there; its budget was not this lane's to spend).
  - Default (`LLM_STRICT_SCHEMA` unset or anything but `1`): byte-for-byte today's argv.
- **`backend/pipeline/test_llm.py`** — the fake CLIs learned one new mode (`reject-schema`: exit
  non-zero iff the schema flag is present, answer normally on the flag-less retry) and now record the
  schema they received (codex: the file `--output-schema` points at, parsed back; claude: the
  `--json-schema` value itself) into their debug dump. New assertions in `demo_codex()` and
  `demo_claude()`: flag absent by default; flag present + schema content round-trips (and for codex,
  the schema file lives inside the `-C` sandbox dir); fallback returns the same reply with exactly one
  `LLM_STRICT_SCHEMA` warning; a failure with the switch on raises the fallback's own error.
- **`backend/README.md`** — one paragraph in the Claude provider section (cross-referencing Codex).

## Findings

- The two CLIs disagree on the flag's *shape*, not just its name: codex wants a file path, claude
  wants the schema inline. Any teammate wiring both should expect that asymmetry.
- On stable reports the strict flag changed nothing here (byte-identical values, ~same time) — which
  is the point: it is a guardrail you can switch on without perturbing results, not a quality lever.
- The flag's real value shows precisely where this lane could not demonstrate it: a decline/refusal
  (v088-Karnell-style prose instead of JSON) becomes structurally impossible under `--output-schema`,
  turning an unparseable reply into a schema-valid one. v095 has since fixed Karnell's specific
  refusal at the schema/prompt level, so the flag stays opt-in — the work order's "若真调证明稳定且
  不慢再讨论默认" gate is met on stability and speed, but the default flip is the supervisor's call.
- `claude --help` documents `--json-schema` but this lane spent zero real calls on it (budget
  reserved by order); its unit coverage asserts the inline-string argv shape, so if a future claude
  build expects a file path instead, the reject-schema fallback catches it at runtime with one warning
  and today's behavior.
