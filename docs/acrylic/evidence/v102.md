# v102 — date-form year headers ("31 Dec 2025 31 Dec 2024") parse as a year run: the fiscal-year column by position (Ambea)

Lane `ao/vivicta-glm-43/v102-date-year-headers`, off `origin/acrylic` (`ef97f1d` at dispatch; pre-delivery
fetch found the baseline unmoved). Territory: `backend/pipeline/extract.py` (only the new `_DEC_DATE` regex plus
`_year_column` / `_row_year_column` — no other function touched), `backend/pipeline/test_confidence.py` (one new
block after the v052 end-to-end case), this file. Zero model calls, zero API calls, zero fetches; `data/`,
schemas, parse.py, locate.py, frontend untouched.

## The defect (red, observed separately before any edit)

Ambea p.119 Note G18 (`data/kb/ambea_2025/pages.jsonl`) prints `SEK million 31 Dec 2025 31 Dec 2024` — the
fiscal year is the FIRST column. On baseline `ef97f1d`:

- `_year_run("SEK million 31 Dec 2025 31 Dec 2024")` → `[]`. The day token `31` between the years is a digit,
  so the run-extension rule (gap ≤ 12 chars, no digits — the rule that lets Telia's "2025 Jan-Dec 2024" be one
  header) breaks the run; the date-form header forms NO run at all.
- Page-level, the scan does not stop: it falls through to the next bare-year pair on the page — the note's own
  closing sentence "… was issued in 2024 or 2025." — so `_year_run(p.119)` → `['2024', '2025']` and
  `_year_column(…, 2025)` → `(1, 2)`: the fiscal year "is" the SECOND column, which is actually the 2024
  comparative.
- End to end (real p.119 text + v088 pass 1's correct model answer 12,643 / 2,308): the year correction fired
  twice — `total_debt: 12643 is not the 2025 column, 10757 is`, `due_within_1_year: 2308 is not the 2025
  column, 1879 is` — output 10,757@1.0 / 1,879@0.9, both stamped `period_ok`. The stored
  `data/kb/ambea_2025/extractions/debt_maturity.json` carries exactly this wrong-year state (v088's own
  "year-column corrected", overturned by v099 Finding 1: 10,335 + 2,308 = 12,643 closes in the first column,
  8,878 + 1,879 = 10,757 in the second; p.126's prose "commercial paper … SEK 1,232 million (1,039)" puts the
  current year leftmost — 1,232 is a component of 2,308).

A wrong-year value is the most dangerous miss the pipeline can ship: high confidence, plausible number,
invisible on a slide.

## The fix (green)

`_DEC_DATE` — a December balance date ("31 Dec 2025" / "31 dec. 2025" / "31 december 2025" / "Dec 31, 2025",
either order, Swedish or English, optional punctuation) is reduced to its bare year **inside `_year_column` and
`_row_year_column`**, before their `_year_run` call. The day/month tokens are then neither amount columns nor
run-breakers; the years keep print order, so the first column is the first year printed; `per`/`at` prefixes
ride the existing one-word gap rule once the digits are gone; the ISO ("2025-12-31") and slash ("31/12/2025")
spellings were already reduced by `_year_run`'s own subs. After: `_year_column("SEK million 31 Dec 2025 31 Dec
2024", 2025)` → `(0, 2)`; the same end-to-end stub stays **12,643@1.0 / 2,308@0.9** (period_ok,
value_in_quote, no correction warning), buckets 1–5y/>5y honestly null, check `missing: due_1_to_5_years`
(current/non-current shape; the shipped `require_explicit_values` rule keeps null buckets "missing", the team
ruling recorded in test_confidence).

**December only, deliberately.** A non-December balance date stays as printed: its calendar year is not the
fiscal year. Rusta's FY2025 ends 30 Apr 2026, so its maturity header "30 Apr 2026 30 Apr 2025" would name the
fiscal year's column as "2025" — the prior year. v096 kept that header a non-run on purpose (the report's own
"2025/26 2024/25" header, the `_SPLIT_YEAR` rule, is the authority there); this lane keeps it that way, with a
test assert.

**Why the selectors, not `_year_run`.** The first implementation put the reduction inside `_year_run` itself.
It fixed Ambea identically — but it also changed what `_segment_column` sees on Proact p.103 (v066's fixture):
the page's first run became the true repeated date pair `31 Dec 2025 31 Dec 2024 31 Dec 2025 31 Dec 2024`
instead of the footer's `[2025, 2025, 2025]`, `_segment_column`'s Group/Parent branch then returned `(0, 4)`
instead of `(0, 3)`, and the v066 identity_kept guard — which requires `len(amounts) == ncols` — no longer
fired for the 3-amount instrument row, so the model's correct computed 312,458 was dropped as "computed, not
read" and the v066 case went red. The work order names `_year_column`/`_row_year_column` as both the defect and
the territory; reducing there leaves `_segment_column`, `_bucket_row_prior_year`, `_operand_table_rows` and
`_bucket_year_hits` (all `_year_run` callers) seeing the page exactly as before. The v066 case and every other
existing case is green again; the replay delta did not move (still only Ambea).

## Counterexamples (unchanged behaviour, asserted)

- bare `2025 2024` headers: untouched (the whole existing suite is the assert).
- `Note 20 Borrowings / MSEK / 2025` — a lone year is one column, no run: `None`.
- Cloetta's `Note 21 Borrowings 31 Dec 2025` — a single date names one column: still no run, still the
  bucket-column mechanism's own page.
- Rusta's `30 Apr 2026 30 Apr 2025`: no run (December-only rule, above).
- Repeated date-form pairs (Proact prints Group | Parent side by side) flow into the v052 machinery unchanged:
  page-level `_year_column` declines the repeated fiscal year; `_row_year_column` takes the Group side when
  Group is named before Parent on the run's row or the one above it (`(0, 4)` on the synthetic pair page).
- MedCap (v041/v052) untouched: the v052 block passes byte-identical.

## For the group

- The `_year_run`-wide variant of this fix (reducing dates inside the scan itself) is the more general shape
  and would also let `_bucket_row_prior_year` read date-form prior-year tables — but it moves `_segment_column`
  on repeated-date-pair pages and needs the v066 guard's `len(amounts) == ncols` admission widened (extract()'s
  segment loop). Out of this lane's territory; recorded here with the repro above for whoever picks it up.
- The prose-pair fallback (`"in 2024 or 2025"` forming a page's year run when no header does) is what made this
  defect quiet. It is now shadowed by a real header wherever one prints, but on pages with NO header at all it
  still decides `_year_column` — unchanged, flagged as a known sharp edge.
