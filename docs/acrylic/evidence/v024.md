## Premise overturned

The brief: `kb.save_report` rewrites `data/kb/<stem>/{meta.json,pages.jsonl}` on every open, even when the
PDF's sha256 and `PARSER_VERSION` are unchanged, and needs a guard added. Checked the write path first
(`git log --oneline -- backend/pipeline/kb.py`): `save_report`'s guard —

```python
meta = {**meta, "parser": PARSER_VERSION}
if _meta(stem).get("sha256") == meta["sha256"] and _meta(stem).get("parser") == PARSER_VERSION and (d / "pages.jsonl").exists():
    return d
```

— already exists, and has existed since commit `c8b01a1` ("parser: rebuild column-major pages from word
positions; strip currency tokens from labels"), the second commit ever to touch `kb.py`. That commit is part
of the original backend foundation (`27d106c`..`3a78f71`), merged into `acrylic` before any frontend lane
started — nobody on this branch wrote it or needs to. `app.py` never writes `data/kb` directly; `register_library`
and `upload_report` both go through `kb.save_report` exclusively (confirmed by reading both call sites), so the
write point matches the brief even though the "always rewrites" premise doesn't.

Empirically verified rather than trusted from the read (per LESSONS #10, source-reading alone doesn't prove a
defect either way): wrote `backend/pipeline/test_kb.py` per item 1 of the brief (temp `KB_DIR`, save/re-save,
assert bytes+mtime unchanged) *before* touching any code, and ran it against the unmodified baseline first —
it passed immediately, no red state. **No change to `kb.py` was made** — there was nothing to fix in the
save-path logic itself.

## What the test suite locks in — `backend/pipeline/test_kb.py`

`python -m pipeline.test_kb`, temp `KB_DIR` (env var, absolute path — confirmed this overrides `kb_dir()` on
Windows too, pathlib drops the joined base when the right side is absolute):

1. Save once, save again with the same `(sha256, parser)` → `meta.json`/`pages.jsonl` byte-identical **and**
   `mtime_ns` identical (0.01s sleep between saves as an mtime-resolution guard) — the no-op case.
2. sha256 changes → rewrite (re-parse path stays live).
3. `PARSER_VERSION` bumped (monkeypatched, restored in `finally`) at the same sha256 → rewrite once, matching
   the new version — **the v2→v3 upgrade path is preserved**, then a same-version re-save after the bump is a
   no-op again.
4. Meta with no `"parser"` key at all (simulates the actual state of committed `data/kb/` entries, see below)
   → writes once (legitimate upgrade), then a second save is a no-op.

## Root cause of "5 lanes each hit this" (README's contract-gap entry)

`data/kb/atlas_copco_2025/meta.json` as committed in the repo has **no `"parser"` key at all** — not a stale
version, an absent one (confirmed by reading the tracked file directly). `save_report`'s guard correctly
treats that as "needs the (allowed) upgrade write" on first sight. Since every lane works from an independently
fresh `git worktree`, each one's *first* open of Atlas Copco re-triggers that same one-time legitimate write —
v005's evidence (`evidence/v005.md`) shows it happening with `"parser": 2` (the version at that time); this
lane sees `"parser": 3`. Each lane correctly `git restore`s it before committing per `common.md`, which means
the committed file never picks up the key, so the *next* lane's fresh worktree hits the identical "first open"
write again. It reads as "opening a KB report always rewrites tracked files" from five independent one-shot
observations, but it's the same one-time event recurring because the fix for *that* (committing the upgraded
`data/kb/atlas_copco_2025/{meta.json,pages.jsonl}` once) touches `data/kb/**`, which is explicitly out of every
lane's territory including this one's — nobody was allowed to commit it.

**Not done, flagged for the supervisor:** committing the one-time-upgraded `data/kb/atlas_copco_2025/meta.json`
+ `pages.jsonl` (and, ideally, running `python -m pipeline.kb build` once for all 102 bundled reports so none
of them carry a pre-`parser`-key `meta.json`) would stop future fresh worktrees from re-observing this. That's
a `data/kb/**` change, outside this lane's territory by the brief — left to the supervisor to decide whether
and when to land it, rather than doing it here.
